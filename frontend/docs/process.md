## 2. Процесс по шагам

### Шаг 1. Контракт → моки, которые не врут

1. Прочитали `docs/api-contract.md`, `openapi.json`, спеки в `openspec/specs`, `src/api/routes.py`.
2. **Подняли настоящий бэк без Docker** (SQLite):
   `POSTCODE_DATABASE_URL=sqlite+aiosqlite:///tmp/t.db uv run uvicorn src.main:app --port 8765`.
3. **Сценарий из 38 запросов** (импорт, план, факт, повтор факта → 409, пересчёт, приоритет, отмена, 404/422) прогнали по бэку и по моку и **сравнили ответы по значениям**, а не только по структуре.
4. Мок устроен как бэк, а не как «примерные данные»:
   - данные сняты с ответов бэка после импорта;
   - логика планировщика, пересчёта, предупреждений, метрик и Bus Factor построчно перенесена с Python (`frontend/src/mocks/engine.ts`);
   - те же статусы, тексты ошибок, форматы дат, хранение строк плана;
   - состояние переживает перезагрузку, сброс — `?mock-reset`.
5. **Итог:** из 38 ответов расходятся 2 значения — там, где бэк расходится со спекой (раздел 5).

**Что дала сверка:** старый «примерный» мок скрывал особенности реального бэка, из-за которых фронт сломался бы на демо:
- одна задача может стоять в нескольких спринтах: 36 задач дают 99 строк плана;
- выполненные задачи приходят в `not_planned` с номером спринта;
- спринт без запланированных задач пропадает из ответа;
- предупреждений о дефиците ролей десятки.

Под это сделан слой нормализации `frontend/src/lib/planModel.ts`.

### Шаг 2. Исследование референсов

- Смотрели реальные продукты через Lazyweb MCP (скриншоты): бэклог и issue view Jira, Linear, ClickUp Workload, Float/Square (люди × периоды), Dealfront/Aboard (фильтры + таблица), импортеры CSV (OpenPhone, Midday).
- Правило: **структуру экрана берём из того, как задачу решают рабочие инструменты**, а не придумываем.

### Шаг 3. Дизайн-система и анимации по гайдам

Использовали признанные руководства (подборка Lazyweb):

- [interface-design](https://github.com/Dammyjay93/interface-design) — иерархия, токены, плотность, одна стратегия глубины;
- [emil-design-eng](https://github.com/emilkowalski/skills) — анимации: только `transform`/`opacity`, 120–260 мс, ease-out, выход быстрее входа, `prefers-reduced-motion`;
- [ui-ux-pro-max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) — приоритеты UX-правил: доступность, зоны нажатия, состояния.

Анимируется каждое действие пользователя, меняющее страницу: панели, вкладки, раскрытие секций, пересчёт (числа и шкалы доезжают), диалоги, шаги импорта, смена темы.

### Шаг 4. Оценка удобства — методиками, а не «на глаз»

1. **Когнитивный разбор** ([NN/g](https://www.nngroup.com/articles/cognitive-walkthroughs/)). Сценарии из продукт-плана: первый вход, «почему задача не попала в квартал», приоритеты, факт спринта, отмена задачи, риски Bus Factor для CTO, поиск людей по навыку, метрики. На каждом шаге 4 вопроса:
   - поймёт ли, что делать;
   - заметит ли элемент;
   - свяжет ли с целью;
   - увидит ли результат.
2. **10 эвристик Нильсена** ([NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)) с серьёзностью 0–4 ([шкала](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)).
3. **Законы UX** ([lawsofux.com](https://lawsofux.com/)): позиция в ряду, фон Ресторфф, Хик, близость; рекомендации NN/g для [таблиц](https://www.nngroup.com/articles/data-tables/) и [дашбордов](https://www.nngroup.com/articles/dashboards-preattentive/).
4. **Замеры:** высота страниц, число действий на сценарий, скриншоты на 1440 / 1024 / 390 px, светлая и тёмная тема.

Главные находки серьёзности 3 и что сделали:

| Проблема | Решение | Результат |
|---|---|---|
| «Не помещаются в квартал» на 6-м экране | Секция первой, раскрыт только текущий спринт, остальные — сводкой | Страница 6008 → 2273 px |
| Красный риск у 29 из 33 задач — сигнал не работает | Риск в строках приглушён, красный только в сводке | — |
| После загрузки факта результат не виден | Итоги сразу сверху | — |
| CTO видел 95 навыков по алфавиту | Колонка «Задач плана под угрозой», сортировка по влиянию | — |

## 3. Ошибки процесса — чтобы не повторять

| Что случилось | Почему | Вывод |
|---|---|---|
| Первый вариант UI — «ИИ-декор» (градиенты, граф-созвездие) | Дизайн делался «красиво», а не от задач пользователя | Сначала референсы и сценарии, потом визуал |
| «Половина кнопок не работает» | Автотест нажимал кнопки, но не проверял результат. Причина — несколько `setSearchParams` подряд в React Router затирают друг друга | Тест обязан проверять эффект действия |
| Мок не совпадал с бэком | Мок писался по описанию контракта, без запуска бэка | Мок сверять с живым бэком по значениям |
| Склеенные блоки не заметили | Отступы проверял только человек по скриншотам | Автопроверка отступов + единое правило ритма в CSS |

## 5. Расхождения бэка со спекой (для бэкенд-команды)

1. `confirm-cancel` не меняет `decision` — задача остаётся `cancelled_pending`.
2. Метрики пересчитанной версии не учитывают факт родительской версии: все спринты — «прогноз».
3. Пересчёт берёт факты только текущей версии: при втором факте закрытые ранее задачи планируются заново, повтор факта того же спринта в дочерней версии не даёт 409.
4. `POST /data/jobs/{id}/confirm` после `/data/import` дублирует часы ролей и историю команд.
5. `recompute` по умолчанию `after_sprint=0` перепланирует прошедшие спринты. Фронт сам передаёт номер последнего спринта с фактом.
6. «Дефицит роли» сравнивает роли с учётом регистра и только внутри команды: десятки предупреждений «доступно 0 ч».
7. Нужна пакетная ручка приоритетов: сейчас сохранение порядка — 33 запроса подряд.
