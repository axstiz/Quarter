# workspace Specification

## Purpose
Несколько компаний (workspace-ов) в одной инсталляции (spec-only): текущее поведение (один датасет → общие таблицы) переходит в «workspace по умолчанию»; пользователь может создавать другие компании со своим датасетом, людьми, задачами, планами и настройками. Роли и доступ внутри workspace управляет владелец компании (соединяется с capability auth: роли admin/editor/reader — по workspace-ам, матрица прав — capability permissions, change 009).

## Requirements

### Requirement: Несколько компаний в одной инсталляции

Сервис SHALL поддерживать произвольное число workspace-ов; каждая сущность (задачи, инициативы, инженеры, зависимости, history velocity, планы/версии, факты, job-ы онбординга) принадлежит одному workspace. Данные разных workspace MUST быть логически изолированы (в одной БД, отдельная БД на компанию — вне рамок).

#### Scenario: Две компании

- **GIVEN** созданы workspace A и workspace B, каждый со своим датасетом
- **WHEN** пользователь в контексте A открывает задачи
- **THEN** видны только задачи компании A, задачи B не видны и не считаются в планах/метриках A

### Requirement: Создание и переключение workspace

Пользователь SHALL иметь возможность создать workspace (он становится владельцем — role admin в нём) и переключаться между своими workspace-ами; сущности API работают в выбранном контексте. На фронте активный контекст SHALL храниться в клиентской сессии и передаваться заголовком `X-Workspace-Id` на все `/api/v1`-запросы (задание по умолчанию — без заголовка). При смене workspace обновление состояния MUST сбрасывать URL-состояние контента (`?plan=`, `?task=`), потому что данные другого workspace не пересекаются (измаль­ненний контекст не должен притворяться состоянием нового). Переключение доступно в любой момент через селектор (возврат на onboarding-экран выбора).

#### Scenario: Переключение контекста

- **GIVEN** пользователь участник workspace A и владелец workspace B
- **WHEN** он переключается на B и вызывает GET /tasks
- **THEN** ответ содержит задачи B; повторный вызов с контекстом A — задачи A

#### Scenario: Сброс состояния при смене

- **WHEN** пользователь переключается со старого workspace (?plan=X, ?task=Y) на новый
- **THEN** URL-state контента сброшен, UI развивается с данными нового workspace

### Requirement: Доступ в компанию — только у создателя и приглашённых

Доступ к workspace-у — и на правку, и на просмотр — SHALL иметь только его создатель и приглашённые участники: не-участник НЕ видит чужую компанию в списке своих и получает 403/404 на любые ручки её данных (детали чужого workspace не раскрываются). Роли участников (admin/editor/reader) определяют только объём действий внутри, участие — определяет владелец.

#### Scenario: Не-участник ничего не видит

- **GIVEN** пользователь X не участник workspace B
- **WHEN** GET /workspaces (список своих) или итог ручек контекста B
- **THEN** B не появляется в списке; обращения к его данным — 403/404 без раскрытия содержимого

### Requirement: Владелец управляет доступом в компании

Доступ в workspace SHALL управлять владелец этого workspace (role admin) — через UI-экран участников: список (имя/email, роль), приглашение по email c выдачей роли (editor/reader), удаление пользователем; роль пользователя MAY различаться по workspace-ам. Опциональная необходимость: UI отражает роли участников участникам их текущих ролей после изменений (re-fetch).

#### Scenario: Приглашение участника по email

- **GIVEN** владелец workspace B
- **WHEN** он приглашает lead@company.ru с ролью editor через POST /workspaces/{id}/members
- **THEN** участник появляется в списке с ролью editor и после входа имеет её в данном контексте

#### Scenario: Разные роли в разных компаниях

- **GIVEN** пользователь X — editor в workspace A, не участник B
- **WHEN** он вызывает ручку правки в контексте B
- **THEN** 403/404 (не участник B); роль reader в A не влияет на доступ к B

### Requirement: Workspace по умолчанию

Сервис SHALL обеспечивать workspace по умолчанию: демо-датасет и существующие записи переезжают в него при миграции; запросы без указания контекста идут в default workspace — прежнее одно-датасетное поведение сохраняется.

#### Scenario: Совместимость без заголовка

- **GIVEN** фронтенд/curl-скрипты по docs/api-contract.md без workspace-контекста
- **WHEN** POST /data/import, POST /plans/generate
- **THEN** работают как сейчас, в default workspace

### Requirement: Импорт и план в контексте workspace

Ручки данных и планирования SHALL работать в контексте выбранного workspace: POST /data/import затирает и пересоздаёт данные только этого workspace (не соседних); планы/снапшот-цепочки/факты/метрики считаются и хранятся в его границах.

#### Scenario: Импорт не задевает соседей

- **GIVEN** workspace A и B, в обоих есть планы
- **WHEN** POST /data/import в контексте A
- **THEN** данные/планы B не затронуты

### Requirement: Список и CRUD workspace

API SHALL предоставлять ручки workspace-ов: список своих workspace-ов, создание (создатель — владелец), переименование (admin), удаление (admin; с подтверждением).

#### Scenario: Создание компании

- **GIVEN** аутентифицированный пользователь
- **WHEN** POST /workspaces {name}
- **THEN** 201; пользователь — владелец; новый workspace пуст (без задач/людей)

### Requirement: Привязка снапшотов и метрик к workspace

Снапшот-цепочки планов и показатели SHALL рассчитываться только внутри одного workspace: знаменатель метрик (первоначальный план) берётся из initial-плана этого же workspace.

#### Scenario: Метрики по компании

- **GIVEN** два workspace с планами
- **WHEN** GET /plans/{id}/metrics в контексте B
- **THEN** база — initial-план компании B, данные A не входят

### Requirement: Экран выбора рабочего пространства

После успешного входа UI SHALL первым экраном показывать экран «Выбор рабочего пространства» — всегда, включая случай единственного (default) workspace. Экран SHALL показывать список workspace-ов пользователя (название, владелец) и действие «Создать рабочее пространство»; ролевые пометки на карточках SHALL NOT отображаться (024). Создатель нового workspace становится его админом и попадает в пустой контекст («чистый лист»), где UI предлагает начать работу: загрузить файл датасета или использовать демо-датасет одной кнопкой. Возврат к списку SHALL быть доступен из интерфейса (селектор компании) в любой момент.

#### Scenario: Вход и выбор

- **GIVEN** пользователь с двумя workspace (default и собственный)
- **WHEN** после входа одной кнопкой
- **THEN** первым экраном открывается список его workspace'ов без ролевых бейджей, а после выбора — соответствующий контент (план/пустой лист)

#### Scenario: Создание с чистого листа

- **GIVEN** пользователь на экране выбора
- **WHEN** он создаёт новое рабочее пространство с названием «Проект Альфа»
- **THEN** POST /workspaces создаёт workspace (создатель — админ), UI открывает «чистый лист» с предложением загрузить файл датасета или демо-датасет одной кнопкой

### Requirement: Импорт датасета в существующий workspace

В существующий workspace SHALL быть доступна загрузка (повторный импорт) нового файла в текущий контекст: бэFormatException обновит импортированные записи, ручные (source=manual) сохранятся (capability data). Форма загрузки MUST явно подписывать последствия («импортированные записи будут обновлены; ручные правки останутся»), а после импорта UI SHALL показать баннер «данные изменились — постройте план заново» (human-in-loop, как в 019).

#### Scenario: Дов. загрузка в текущий контекст

- **GIVEN** в workspace есть задачи, инжинеры и вручную исправленный профиль
- **WHEN** пользователь загружает обновлённый файл датасета
- **THEN** импортированные записи обновляются, ручные остаются, после — баннер пересборки плана
