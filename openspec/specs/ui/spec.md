# ui Specification

## Purpose
Поведение пользовательского интерфейса сервиса (страницы по user flow v0.4 — docs/product-plan.md, раздел 4). Спека фиксирует, что обязан показывать и как обязан вести себя UI; дизайн и стек — за фронтендером. Контракт данных — capability api, openapi.json.

## Requirements

### Requirement: Причины решений видны всегда

UI SHALL показывать для каждой задачи плана причину её решения (включена / перенесена / отменена / выполнена) из reason и decision ответа GET /plans/{plan_id}; клик по задаче MUST открывать карточку с summary, инициативой (parent_id), SP/часами, часами по ролям и причиной.

#### Scenario: Перенесённая задача

- **GIVEN** задача с decision postponed и непустым reason
- **WHEN** пользователь смотрит спринт-колонку
- **THEN** причина доступна без знания API (tooltip/раскрытие/карточка)

### Requirement: Статусы различимы не только цветом

UI SHALL визуально различать decision (planned/postponed/cancelled_pending/cancelled/done_actual) так, чтобы цвет не был единственной индикацией (иконка/текст/подпись тоже).

#### Scenario: Задача у дальтоника

- **GIVEN** задаче запланирован зелёный цвет и planned
- **WHEN** пользователь смотрит колонку спринта
- **THEN** статус задачи различим без восприятия цвета

### Requirement: Приоритеты выставляет человек

UI SHALL предоставлять изменение priority задачи (drag-n-drop или числовое поле — деталь реализации: контракт число, меньше = раньше) и после несохранённых изменений подсказывать действие «пересчитать план» (POST /plans/{id}/recompute).

#### Scenario: Смена приоритета

- **GIVEN** пользователь меняет priority задачи A с 100 на 10
- **WHEN** план пересчитан
- **THEN** новая версия плана учитывает новый порядок, UI переключается на неё

### Requirement: Двухшаговая отмена

UI SHALL реализовывать отмену в два шага: предложение отмены (cancel-request → cancelled_pending, оранжевая индикация) и подтверждение лидом (confirm-cancel → cancelled); отменённые задачи MUST оставаться видимыми с причиной.

#### Scenario: Подтверждение отмены

- **GIVEN** задача в статусе cancelled_pending
- **WHEN** лид нажимает подтверждение
- **THEN** задача decision=cancelled, видна в блоке с причиной

### Requirement: Переключение на новую версию плана после факта

После успешной загрузки факта спринта UI SHALL переключаться на new_plan_id из ответа ручки факта; повторная отправка того же факта MUST блокироваться по коду 409.

#### Scenario: Факт спринта 1

- **GIVEN** загружается факт спринта 1
- **WHEN** ответ содержит new_plan_id
- **THEN** UI показывает новую версию плана (спринт 1 зафиксирован, 2–6 пересчитаны)

### Requirement: Риски со списком задач

UI SHALL показывать предупреждения из GET /plans/{id}/warnings (4 вида) с затронутыми task_ids и связью «факт → следствие» (что не выполнено — что сдвинулось).

#### Scenario: Сдвиг цепочки

- **GIVEN** warning dependency_shift со списком task_ids
- **WHEN** пользователь открывает блок рисков
- **THEN** видны сдвинутые задачи (из diff: спринт X → Y) и их причины

### Requirement: Метрики с подписью факт/прогноз

UI SHALL показывать показатели метрик с явной текстовой подписью «факт» или «прогноз» (согласно sprint_completion_is_forecast / quarter_completion_is_forecast); подпись MUST быть текстом, не только цветом; база сравнения — первоначальный план (initial в цепочке снапшотов).

#### Scenario: Середина квартала

- **GIVEN** загружены факты спринтов 1–2, идут спринты 3–6
- **WHEN** пользователь открывает страницу метрик
- **THEN** значения спринтов 1–2 подписаны «факт», 3–6 — «прогноз» (или пусто)

### Requirement: Звёздная карта с фильтрами

UI SHALL предоставлять звёздную карту с фильтрами (команда, роль, грейд, навык, ставка → GET /engineers), показом инженеров в нескольких командах (parttime-пометка в обеих) и подсветкой компетенций с единственным носителем.

#### Scenario: Инженер в двух командах

- **GIVEN** ENG-405 состоит в Team-L и Team-Alpha (по 0.5 ставки)
- **WHEN** пользователь смотрит карту
- **THEN** ENG-405 отображён в обеих командах с пометкой частичной занятости

### Requirement: Методика Bus Factor рядом с показателем

UI MUST показывать текст методики расчёта Bus Factor (поле methodology из GET /bus-factor) рядом с показателем, не в отдельном скрытом разделе.

#### Scenario: Открытие Bus Factor

- **GIVEN** пользователь открывает блок Bus Factor
- **WHEN** смотрит на фактор компетенции
- **THEN** методика и область расчёта (company/team) видны рядом с показателем

### Requirement: План как диаграмма Ганта

Дашборд SHALL отображать план в виде диаграммы Ганта (не колонки-столбика): ось шкалы — спринты 1–6 (до реализации change 010) либо календарные даты спринтов (после реализации change 010); каждая задача — горизонтальный бар от спринта первого размещения до последнего; задача, разбитая между несколькими спринтами, разметается **одной полосой через несколько ячеек шкалы** с видимыми границами частей и подписями долей SP, а не как отдельные задачи. Задачи вне плана (postponed/cancelled) отображаются за правой границей шкалы с причиной. Строки барa группируются по командам (фильтр сохраняется) и сворачиваются в группы по инициативам; клик по полосе = карточка задачи (прежний drill-down); индикация статуса (цвет + не только цвет) сохраняется. До реализации change 010 шкала строится по номерам спринтов (данные для дат ещё не возвращаются API).

#### Scenario: Полоса через два спринта

- **GIVEN** задача запланирована в спринтах 2–3 (частями по SP)
- **WHEN** план отображается Гантом
- **THEN** задача — одна горизонтальная полоса через ячейки спринтов 2–3 с подписями долей SP каждой части, не две независимые строки

#### Scenario: Разбитая задача с пометкой

- **GIVEN** задача размещена частично (остаток — за пределами квартала, reason содержит «выполнится частично»)
- **WHEN** полоса отрисована
- **THEN** на полосе видна пометка частичного размещения

#### Scenario: Шкала до и после calendar-изменения

- **GIVEN** change 010 (календарь квартала) ещё не реализован
- **WHEN** дашборд открыт
- **THEN** ось шкалы — спринты 1..6 по номерам; после реализации 010 ось — даты (start/end спринтов из sprint_dates), полосы проходят на их дат-интервалах

### Requirement: Погружение квартал → спринт → задача

UI SHALL предоставлять навигацию от плана квартала вниз: клик по спринтовой колонке (или выбор спринта в селекторе) открывает экран спринта — состав задач спринта с их датами-интервалами, причины решений и привязанные к спринту предупреждения; клик по задаче открывает её карточку (причина, SP/часы, разбивка по ролям, зависимости, прогнозный интервал); возврат — на вид квартала. Разные оси: спринт — окно времени (не часть работы), инициатива — уровень состава работ (состоит из задач, а не спринтов).

#### Scenario: С нижних уровней

- **GIVEN** пользователь смотрит дашборд плана квартала
- **WHEN** кликает колонку спринта 3 → задачу в нём
- **THEN** открывается экран спринта 3 (состав/причины/риски), затем карточка задачи; возврат ведёт обратно на вид квартала

### Requirement: Группировка задач по инициативам

Задачи в спринтах и в блоке «вне плана» SHALL сворачиваться в группы по инициативе (parent_id) с прогрессом группы («X из Y задач запланированы», частично включённая инициатива помечена); группа раскрывается до отдельных задач.

#### Scenario: Частично включённая инициатива

- **GIVEN** в план попали 2 из 6 задач инициативы BR-151
- **WHEN** пользователь смотрит группы спринта
- **THEN** группа BR-151 помечена «2 из 6 в плане» и раскрывается до обеих задач

#### Scenario: Завершённая инициатива

- **GIVEN** все запланированные задачи инициативы выполнены (done_actual)
- **THEN** группа помечена как завершённая (в метриках инициатива числится завершённой)

### Requirement: Вид «Роли по спринтам»

UI SHALL предоставлять на `/plan` вкладку «Роли по спринтам», которая SHALL отображать план как матрицу строк (команда × роль) × колонок (спринты 1–6):

- строка роли показывает её носителей в команде (инженер, грейд, ставка — раскрываются), агрегатный лимит Σ (80 ч × capacity_rate носителей) и загруженные часы роли в каждом спринте (шкала часы/лимит);
- чип задачи в ячейке показывает её ключ и часы потребности роли в этом спринте (для разбитой задачи — долю SP части); клик по чипу открывает карточку задачи;
- потребность роли задачи, отсутствующей в команде задачи, SHALL отображаться как кросс-командный заём: в команде с наибольшим свободным лимитом носителей этой роли, пунктирным чипом с пометкой «из команды X»;
- если носителей роли нет ни в одной команде, в команде задачи SHALL отображаться красная пометка «носителей нет во всей компании · виртуальный держатель» (согласуется с правилом planning о виртуальных держателях, change 003);
- группировка команд завершается и сворая: каждая секция показывает по спринтам суммарные SP задач команды против ёмкости (velocity × 0,8).

UI MUST подписывать в интерфейсе, что распределение по носителям ролей вычисляется на клиенте из потребности задач (role_hours) и ставок инженеров; бэкенд людей не назначает.

#### Scenario: Роль берёт задачи чужой команды

- **GIVEN** задача команды Team-L требует роль, носителей которой в Team-L нет
- **WHEN** пользователь смотрит вид «Роли по спринтам»
- **THEN** часы задачи отображаются в строке этой роли у команды-носителя пунктирным чипом с пометкой «из Team-L», а в метре роли учитываются

#### Scenario: Роль без носителей

- **GIVEN** роль задачи не имеет носителей ни в одной команде
- **WHEN** пользователь смотрит вид «Роли по спринтам»
- **THEN** в команде задачи видна красная пометка «виртуальный держатель» с описанием дефицита и задачами

### Requirement: Единый редактор раскладки

Ручное редактирование раскладки (переносы частей задач между спринтами) SHALL выполняться только в виде «Роли по спринтам»; Гант по задачам SHALL оставаться read-only по раскладке. Перетаскивание чипа роли SHALL двигать часть задачи целиком (включая SP, часы и остальные роли части). Отпускание чипа вызывает `POST /plans/{id}/tasks/{task_id}/pin {sprint_no, engineer_id?}` — сервер перемещает задачу немедленно (строки задачи и assignments фиксируются в БД в целевом спринте, change 039), фронт перечитывает план и показывает чип в целевой колонке: из старой колонки элемент исчезает, в целевую появляется — без дублирования, optimistic-слоёв, бейджей и баннеров. Конфликт ёмкости/зависимости (409) отклоняется с текстом причины, чип остаётся на месте; «вернуть» — `DELETE /plans/{id}/tasks/{task_id}/pin`. Клиентские хранилища раскладки (localStorage по planId, in-memory override-слои) для переносов не используются. Раскладка SHALL быть синхронной между видами «Роли по спринтам» и «Диаграмма Ганта» (единая раскладка читается из плана). Недопустимые цели (спринт зафиксирован фактом, вне квартала, в целевом спринте уже есть другая часть той же задачи) MUST отклоняться на клиенте до вызова пина с текстом причины. Тост операции подтверждает результат («закреплено/возвращено»).

#### Scenario: Оптимистичный перенос

- **GIVEN** пользователь перетащил чип роли задачи из спринта 2 в спринт 4
- **WHEN** POST pin успешен
- **THEN** чип немедленно отображается в спринте 4 с бейджем «пин», SP/часы колонок 2 и 4 пересчитаны локально; соседние незакреплённые задачи стоят на месте; после «Пересчёта'/факта раскладка сервера консистентна, бейдж снят

#### Scenario: Оптимистичный перенос отклонён сервером

- **GIVEN** pin вернул 409/ошибку
- **WHEN** onError
- **THEN** чип остаётся в исходной колонке (слой не применяется), причина видна и повтор на ту же цель заблокирован

#### Scenario: Недопустимая цель

- **GIVEN** целевой спринт зафиксирован фактом / вне квартала
- **WHEN** пользователь отпускает чип
- **THEN** перенос отклонён на клиенте с текстом причины, POST не отправлялся

#### Scenario: Немедленный перенос через пин

- **GIVEN** задача частями размещена в спринтах 2 и 3, backend доступен
- **WHEN** пользователь перетаскивает чип роли из спринта 2 в спринт 4
- **THEN** фронт вызывает POST pin {sprint_no: 4}; пин фиксируется как намерение (без пересборки версии), появляется тост «закреплено · снять», а после пересчёта часть задачи размещается в спринте 4

#### Scenario: Конфликт ёмкости на живом бэке

- **GIVEN** целевой инженер в спринте 4 уже загружен (лимиты заняты)
- **WHEN** пересчёт
- **THEN** конфликт отражается по pre-occupancy спеки planning; раскладка не нарушает hard-правил

#### Scenario: Возврат переноса

- **WHEN** пользователь нажимает «снять закрепление» в тосте
- **THEN** вызывается DELETE pin (без пересборки), чип возврашается к раскладке предыдущего пересчёта

#### Scenario: Перенос части задачи из вида ролей

- **GIVEN** задача частями размещена в спринтах 2 и 3
- **WHEN** пользователь перетаскивает её чип роли из спринта 2 в спринт 4 и затем нажимает «Пересчитать»
- **THEN** часть целиком переезжает: все её ролевые чипы и SP переносятся в спринт 4 в этом и в виде «Диаграмма Ганта»

#### Scenario: Синхронность видов

- **GIVEN** часть задачи закреплена в спринте 5 пином и план пересчитан
- **WHEN** пользователь открывает «Диаграмму Ганта»
- **THEN** та же часть отображается в спринте 5, статистика SP и загрузка ролей пересчитаны

#### Scenario: Баннер неприменённых пинов

- **GIVEN** есть ≥1 закрепление, чей целевой спринт отличается от текущей расстановки
- **WHEN** пользователь видит редактор раскладки
- **THEN** баннер «Есть N закреплений, не применённых к плану — Пересчитать», действие открывает пересчёт

#### Scenario: Перенос части задачи — без немедленной пересборки

- **GIVEN** задача частями размещена в спринтах 2 и 3
- **WHEN** пользователь перетаскивает её чип роли из спринта 2 в спринт 4
- **THEN** пин зафиксирован (намерение: спринт 4), соседние чипы не сдвигаются немедленно, на элементе метка «закреплено (ожидает пересчёт)» и чип отображается в спринте 4 локально с бейджем «пин»; после «Пересчёта»/факта часть целиком переезжает: все её ролевые чипы и SP переносятся в спринт 4 в этом и в виде «Диаграмма Ганта»

### Requirement: Bus-риски плана из ручки

Виджет «Зависят от одного носителя» и панель рисков SHALL читать данные из единой ручки `GET /plans/{id}/bus-risk` (список задач плана, затронутых ролями/компетенциями с единственным носителем). Клиентские расчёты рисков (склейка `/bus-factor` с `role_hours` задач) SHALL быть удалены; фронт не вычисляет факторы сам — это обязанность бэкенда (согласуется с bus-factor.requirement «Риски плана в терминах задач» и поддержкой scopes 014). Ошибка ручки MUST показываться как ошибка панели, а не вырождаться в «0 рисков».

#### Scenario: Виджет из ручки

- **WHEN** фронтенд открывает дашборд плана
- **THEN** счётчик и список задач под угрозой приходят из GET /plans/{id}/bus-risk; фронт не соединяет /bus-factor с role_hours

#### Scenario: Панель рисков на пустой ручке

- **GIVEN** план не содержит задач с одно-носительными ролями
- **WHEN** пользователь открывает риски
- **THEN** панель показывает «рисков нет» (не клиентский расчёт, а ответ ручки)

### Requirement: Граница вычислений (данные — фронт, действия — бэк)

UI SHALL следовать разделению ответственности: **фронтенд только отображает данные** (витринные проекции уже принятых бэком решений: «Роли по спринтам», LoadView, группировки по инициативам, URL-состояние — все со обязательной подписью, что расчёт клиентский), а **любая операция, изменяющая данные (переносы, отмена, приоритет, факт, пересчёт, генерация плана) MUST выполняться штатной бэкенд-ручкой с фиксацией в БД**. Клиентские in-memory/persistent override-слои для бизнес-действий не допускаются: пользователь не может думать, что «перетащил», а данные на сервере остались прежними. Витринные расчёты MUST быть детерминированными проекциями данных плана и отмечаться подписью в UI (как в требовании «Вид „Роли по спринтам"»).

#### Scenario: Бизнес-операция сохраняется в БД

- **GIVEN** пользователь выполняет перенос, отмену, смену приоритета или загрузку факта
- **WHEN** операция завершена успешно
- **THEN** изменение зафиксировано бэкенд-ручкой (БД/история версий), а не в localStorage компонента

#### Scenario: Витрина без подписи недопустима

- **GIVEN** витринный разрез («Роли по спринтам», LoadView) вычисляется на клиенте
- **WHEN** пользователь смотрит экран
- **THEN** виден поясняющий текст, что распределение расчёт клиента и не меняет план

### Requirement: Онбординг-экран рабочей области

После успешного входа (пароль или демо-вход) первый экран SHALL быть «Выбор рабочего пространства» — всегда, включая единственный (default) workspace: список пространств (название, роль, владелец), действие «Создать рабочее пространство», для создателя нового — «чистый лист» с двумя путями старта: загрузить файл датасета или **демо-датасет одной кнопкой**. Возврат к списку — селектор в топбаре/сайдбаре; не-участник при прямом переходе к чужому workspace SHALL получать понятный тост (404/403) и возврат на экран выбора.

#### Scenario: Первый экран после демо-входа

- **GIVEN** demo-вход reader
- **WHEN** успешная аутентификация
- **THEN** открывается экран выбора workspace (не /plan напрямую), default workspace виден с ролью reader

#### Scenario: Чистый лист предлагает старт

- **GIVEN** создан новый workspace «Проект Альфа»
- **WHEN** открыт его контекст
- **THEN** экран показывает пустые данные и два действия: загрузить файл или демо-датасет одной кнопкой

### Requirement: Смена компании в интерфейсе

Топбар/сайдбар SHALL предоставлять действие «сменить рабочее пространство», возвращающее на экран выбора; при смене текущее URL-состояние контента (?plan=, ?task=) сбрасывается. Активный workspace помечен везде, где виден (например, рядом с селектором версии плана). Интерфейс SHALL NOT отображать бейджи ролей пользователя и навигацию по admin-экранам участников/прав (изменение 024): доступ к контенту определяется бэком, UI-гейтингов по ролям не показывается.

#### Scenario: Быстрое переключение

- **GIVEN** пользователь внутри workspace A на странице плана
- **WHEN** открывает смену компании и выбирает B
- **THEN** контент перезагружается данными B, старая ссылка ?plan= не передаётся; ролевых бейджей и ссылок на участников/права в навигации нет

### Requirement: Обработка чужих/недоступных workspace

Ошибка 404/403 при обращении к контексту, в котором пользователь не участник, SHALL показываться тонко понятным тостом с возвратом на onboarding-экран выбора (не раскрывая содержимого чужого workspace, по 008); состояние выбора запоминается, чтобы повтор включённый entry не зависал.

#### Scenario: Ссылка на недоступный контекст

- **GIVEN** пользователь открывает страницу с X-Workspace-Id чужого пространства
- **WHEN** бэк отвечает 404/403
- **THEN** тост «этой компании нет в доступе» + экран выбора

### Requirement: Панель советов AI-советника (из change 015)

На странице плана UI SHALL предоставлять действие «Советы» (GET /plans/{id}/advice) с **полем для одноразового комментария-контекста** («что важно учесть», например «ENG-405 заболел»): весь контекст прогона передаётся в **одном комментарии** (≤ 500 симв.); интерфейс MUST показывать подпись «Совет одноразовый: дозапрос/диалог недоступны — советы перегенерируются заново с новым комментарием». Карточки советов SHALL показывать тип (task_move/staffing_shift/initiative_rescue/sprint_priority), затронутые задачи, численное обоснование (numeric_basis) и ожидаемый эффект (expected_effect); для закреплённых (pin) задач советы на перенос не отображаются (фильтр бэка). Поле комментария НЕ персистентно: после перегенерации очищается, старый текст нигде не хранится. Rights: reader — просмотр советов без поля комментария (или доступного для чтения только).

#### Scenario: Совет с одним комментарием

- **GIVEN** пользователь открыл панель советов
- **WHEN** вводит «ENG-405 заболел до конца спринта» и нажимает «Получить советы»
- **THEN** карточки советов учитывают комментарий (pass-through в GET /plans/{id}/advice), поле не сохраняет текст после перегенерации

#### Scenario: Подпись об одноразовости

- **GIVEN** панель советов открыта
- **WHEN** пользователь видит поле комментария
- **THEN** подпись «Совет одноразовый: весь контекст — в одном комментарии» присутствует рядом с полем, повторный клик «Получить советы» очищает поле

### Requirement: Вкладка прогноза рисков

Звёздная карта SHALL иметь вкладку «Прогноз рисков» (view=forecast) на данных `GET /plans/{plan_id}/bus-forecast`: таблица людей с плановой загрузкой — человек (переход в профиль инженера), команды и роль, загрузка по спринтам (визуально к личному лимиту, перегруженные спринты отмечены), критичные роли (единственный носитель, бейдж), уровень риска (high/medium/low как бейдж) и основание-текст с числами; для каждого человека формулировка «если уйдёт: N задач / M ч» — прогноз потерь плана. Данные ручки строятся на версии плана — инвалидируются вместе с планом (при пересчёте/факте). Пока плана или загрузки нет — пустое состояние с пояснением; ошибка ручки показывается как ошибка вкладки, не «рисков нет».

#### Scenario: Просмотр прогноза

- **GIVEN** построен план с загрузкой людей (assignments)
- **WHEN** пользователь открывает «Звёздная карта» → «Прогноз рисков»
- **THEN** таблица содержит инженеров с загрузкой, отсортированных по уровню риска и объёму; клик по человеку открывает его профиль

#### Scenario: Пустое состояние

- **GIVEN** плана в workspace нет (или ни у кого нет плановой загрузки)
- **WHEN** открыта вкладка «Прогноз рисков»
- **THEN** показано пояснение («нет плана — постройте план, чтобы увидеть прогноз» / «загрузки нет»), а не нулевые строки

### Requirement: Редактор данных таблицей

UI SHALL предоставлять страницу «Данные» с редактируемыми субтаблицами загруженных данных: Задачи, Люди, Команды, Зависимости (4 субтаблицы, переключение вкладками). Правки SHALL быть in-place: клик по ячейке переключает её в режим ввода, сохранение по фиксации значения; добавление и удаление записей — явными действиями строки; часы по ролям задачи редактируются в detail-виде строки задачи (список «роль → часы»). Інлайн-валидация MUST показывать ошибку у проблемной ячейки/строки без потери введённого значения. Права: reader — только просмотр (поля заблокированы); editor/admin — правки, добавление, удаление.

#### Scenario: Правка ячейки и сохранение

- **GIVEN** пользователь редактирует таблицу задач
- **WHEN** он меняет «оценка, ч» на 260 и уходит из ячейки
- **THEN** значение сохраняется через PUT /tasks/{id} без отдельной кнопки сохранения; при ошибке 422/409 — текст ошибки у ячейки, введённое значение остаётся

#### Scenario: Дозаполнение кв. Задачи

- **GIVEN** задача без часов по ролям
- **WHEN** пользователь открывает detail-вид роли
- **THEN** может добавить роль с суммой часов, в списке видны все роли компании и носители (какой роли нет носителей — отмечено)

### Requirement: Навигация редактора из плановой задачи

Из карточки задачи и профиля инженера на страницах плана MUST быть переход к соответствующей записи в редакторе данных (по task_id / engineer_id) для правки причин и данных без повторной загрузки файла.

#### Scenario: Связь с планом

- **GIVEN** пользователь открыл карточку задачи в плане
- **WHEN** нажимает «редактировать данные»
- **THEN** открывается таблица «Данные» с подstride строкой этой задачи

### Requirement: Прогресс оптимизации виден до терминального статуса

Кнопка оптимизации SHALL оставаться в состоянии загрузки до терминального статуса job'а (ready|failed): фронт опрашивает GET /plans/optimize/{job_id} с интервалом (2 c) до терминала; при превышении бюджета показывается ошибка (не вечное ожидание). Тост результата SHALL показываться один раз по терминальному статусу с верным режимом (solver|heuristic) и degradation_reason при деградации.

#### Scenario: Очередь — прогресс виден

- **GIVEN** job в статусе queued/solving
- **WHEN** пользователь на странице плана
- **THEN** кнопка в состоянии busy («Solver работает…»), данные плана прежней версии, никаких «готов»-пометок

#### Scenario: Терминальный статус — один тост

- **GIVEN** job перешёл в ready (mode solver) или failed
- **WHEN** polling завершён
- **THEN** toast с верным режимом/причиной деградации (и NewVersion переключение селектора); при failed — error toast с причиной

### Requirement: Вуаль «идёт перестройка» с блокировкой страницы

На время тяжёлых перестроек плана (оптимизация, генерация, пересчёт, загрузка факта) страница SHALL показывать полноэкранную вуаль: spinner + текст статуса процесса. Интерактивный контент под вуалью SHALL быть приглушён (серый) и не отвечает на пользовательский ввод до завершения операции; тост результата появляется после снятия вуали.

#### Scenario: Оптимизация через очередь

- **GIVEN** job optimize в статусе queued/solving
- **WHEN** пользователь на странице плана
- **THEN** вуаль со статусом «в очереди…»/«Solver перестраивает расстановку…», контент серый и неинтерактивен; после ready — вуаль уходит, показан тост результата

#### Scenario: Факт и пересчёт

- **GIVEN** загружается факт спринта / нажат «Пересчёт»
- **WHEN** мутация в полёте
- **THEN** вуаль «Загрузка факта…» / «Пересчёт оставшихся спринтов…», под ней блокировка

### Requirement: CREATED (сереая навигаци до датасета)

До загрузки датасета пункты навигации планирования (план/факт/карта/метрики) SHALL отображаться диаметрически приглушёнными (disabled) и не вести на страницы; активны «Данные» и «Рабочие пространства».

#### Scenario: Серый пункт меню

- **GIVEN** датасет не загружен
- **WHEN** пользователь смотрит навигацию
- **THEN** пункты планирования — ND серые, aria-disabled; «Данные» активна

### Requirement: Список статусов файлов при импорте

Страница импорта SHALL отображать список выбранных файлов со статусами каждого job'а (uploaded/mapping/questions/ready/failed) и прогрессом, ошибка одного файла не валит оставшиеся.

#### Scenario: Статус per-file

- **GIVEN** два файла загружаются
- **WHEN** первый попал в failed (парс-ошибка)
- **THEN** второй продолжаетWAIT, тост по каждому; failed-строка с причиной

### Requirement: Баннер-сводка управляемого improvement после optimize

После успешного optimize (job ready) на странице плана SHALL показываться закрываемый баннер со сводкой: «что изменилось» по реальным числам из отчёта (σ SP, хвост квартала, role-дефициты, transferred moves); при heuristic/degradation — причина честно. Баннер не перекрывает контент.

#### Scenario: solver улучшил

- **GIVEN** optimize job ready, mode=solver
- **WHEN** готов отчёт с split_by_team_role
- **THEN** баннер «Оптимизация улучшила план: σ→…; хвост задействован …»; контент плановой страницы открыт, селектор на новую версию

#### Scenario: эвристика honesty

- **GIVEN** solver не уложился
- **WHEN** advice ready in heuristic
- **THEN** баннер «построен эвристикой (reason)», без красного

### Requirement: История советов с версией плана

Панель советов SHALL содержать секцию «История советов»: список прогонов по версии плана (version_label, время, режим, комментарий если был). Раскрытие записи показывает advice items прогона. Переключение версии плана меняет список истории.

#### Scenario: Перечитать совет позже

- **GIVEN** советы были запрошены ранее на версии плана
- **WHEN** пользователь открывает панель советов
- **THEN** история показывает прошлые прогоны с версией и комментарием; раскрытие — советы прогона

### Requirement: Фронт работает только с реальным бэком

Фронт SHALL ходить только в реальный API (Vite proxy → backend); мок-режим (src/mocks, VITE_API_MOCKS) SHALL быть удалён целиком. Локальная разработка требует поднятый бэк (docker compose api/db).

#### Scenario: Без бэка — без моков

- **GIVEN** бэк недоступен
- **WHEN** пользователь открывает фронт
- **THEN** ошибка сети видна (не подменённый мок-ответ); мок-режим не подменяет отказ
