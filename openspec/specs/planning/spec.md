# Planning — квартальное планирование работ

## Purpose

Квартальное планирование: распределение задач по шести двухнедельным спринтам (12 недель) с учётом производительности команды, рабочего времени специалистов, ролей и зависимостей. Покрывает первую часть пользовательского сценария сервиса — построение плана и объяснение решений (включение / перенос / отмена задач).

## Requirements

### Requirement: Формирование квартального плана

Сервис SHALL формировать план на шесть двухнедельных спринтов на основе загруженного датасета.

#### Scenario: План из 48 задач

- **WHEN** пользователь загружает предоставленный датасет
- **THEN** сервис формирует план на 6 спринтов и показывает распределение задач по спринтам

### Requirement: Ресурс команды по производительности

Сервис SHALL рассчитывать ресурс команды на спринт по средней фактической производительности за прошлые спринты с коэффициентом 0,8.

#### Scenario: Расчёт по velocity

- **GIVEN** для команды в `team_history.csv` есть velocity за прошлые спринты
- **WHEN** планируется ресурс следующего спринта
- **THEN** доступный объём работ = средняя фактическая производительность × 0,8, переведённая в Story Points

### Requirement: Ограничения рабочего времени специалистов

Специалист SHALL быть доступен максимум 80 часам за спринт при полной занятости (capacity_rate 1.0) и максимум 40 часам при занятости 0,5 (capacity_rate 0.5).

#### Scenario: Специалист на полставки

- **GIVEN** инженер ENG-405 имеет capacity_rate 0.5 в двух командах
- **THEN** в каждой команде ему доступно не более 40 часов за спринт

### Requirement: Потребность в ролях

Задача SHALL включаться в спринт только если суммарно свободного времени специалистов требуемых ролей достаточно, в соответствии с `dataset/task_role_requirements.csv`.

#### Scenario: Ресурс есть, роли не хватает

- **GIVEN** у команды есть свободный общий ресурс
- **WHEN** для задачи не хватает времени специалиста необходимой роли
- **THEN** задача НЕ включается в план данного спринта с указанием причины

### Requirement: Зависимости задач

План SHALL соблюдать зависимости из `dataset/task_dependencies.csv`: зависимая задача не планируется раньше завершения блокирующей.

#### Scenario: Зависимая цепочка

- **GIVEN** MP-101 блокирует MP-102, MP-102 блокирует MP-103
- **WHEN** MP-101 не завершена в спринте
- **THEN** MP-102 и MP-103 не могут быть запланированы в этом спринте

### Requirement: Объяснение решений

Для каждой задачи сервис SHALL показывать причину решения: включена / перенесена (причина) / отменена (причина), с формулировкой, понятной пользователю.

#### Scenario: Перенесённая задача

- **GIVEN** задача не попала в спринт из-за нехватки роли
- **WHEN** пользователь смотрит план
- **THEN** для задачи отображена причина переноса

### Requirement: Кросс-командный заём специалистов

Требуемая роль задачи SHALL закрываться инженерами не только своей команды, но и инженерами других команд, чей суммарный лимит (80 ч при полной ставке capacity_rate=1.0; 40 ч при 0.5) распределён по всем обязательствам во всех командах.

#### Scenario: Роль со специалистом другой команды

- **GIVEN** задача Team-L требует «Архитектор решений», а специалист этой роли — в Team-Platform (0.5 ставки)
- **WHEN** planner планирует задачу
- **THEN** часы роли закрываются инженером Team-Platform, если за этот спринт его суммарная загрузка ≤ 40 ч

### Requirement: Статусы задач в плане

Планировщик SHALL учитывать статусы задач: задачи `Done` вне планирования; для `InProgress` объём = остаток часов (`estimated_hh − spent_time`), при `estimation_sp` пропорционально; задачи `ToDo` — полный объём.

#### Scenario: InProgress с остатком

- **GIVEN** InProgress задача estimated_hh=200, spent_time=150
- **THEN** в план идёт счёт часов 50, SP пропорционально

#### Scenario: Просроченный InProgress

- **GIVEN** InProgress задача с spent_time ≥ estimated_hh
- **THEN** задача не помечается завершённой, планируется остаток с пометкой «просрочена» (overdue)

### Requirement: Приоритеты задач (human seed)

Планировщик SHALL расставлять задачи в порядке поля priority (меньше — раньше); seed-значения определяются сервисом при первом импорте (флаг заказчика → верх; остальные — исходный порядок файла), а далее уточняются пользователем (ручки ручки — здесь, UI — в frontend change).

#### Scenario: Приоритет управляет спринтом

- **GIVEN** две задачи, обе влезают только в один спринт (по SP или часам)
- **WHEN** у задачи A приоритет ниже, чем у B
- **THEN** A планируется раньше B

### Requirement: Отмена с подтверждением сервиеsv

Сервис MUST предлагать отмену задач, не поместившихся даже в спринт 6, с причиной; отмена вступает в силу после подтвержения ЛИДА вне ручки confirm-cancel.

#### Scenario: Отмена кандидата

- **GIVEN** задача не влезая ни в спринт квартала
- **WHEN** лид подтверждает отмену
- **THEN** задача получает decision=cancelled с причиной, остаётся видимой

### Requirement: Календарь квартала

Сервис SHALL строить календарь квартала по правилу решения №12: демо-квартал — следующий незавершённый квартал после `max(planned_end)` (fallback: `actual_end`) датасета; квартал = 6 спринтов × 2 недели с вычисленными датами (`sprint_dates`: start/end каждого спринта). отсутствие дат у датасета НЕ блокирует работу — календарь строится по доступным датам, иначе с текущего дня.

#### Scenario: Демо-квартал от датасета

- **GIVEN** max(planned_end) в датасете — 2026-10-30
- **WHEN** план генерируется
- **THEN** календарь квартала используется следующий (зависящий от календаря квартала) незавершённый после 2026-10-30 квартал (Q4 2026: старт после 2026-10-30, 6 спринтов по 2 недели, известные start/end каждого)

#### Scenario: Даты недоступны

- **GIVEN** в датасете не заполнены planned_end
- **WHEN** план генерируется
- **THEN** квартал строится от первого дня следующего квартала относительно текущей даты; функционал не падает

### Requirement: Прогнозные даты задач

Каждая запланированная задача SHALL иметь прогнозный интервал дат плана (start = дата старта её первого спринта, end = дата конца её последнего спринта с учётом разбития); перенос задачи при пересчёте сдвигает интервал.

#### Scenario: Задача в спринте 2

- **GIVEN** спринт 2 календаря — 2026-11-02..2026-11-15
- **WHEN** GET /plans/{id}
- **THEN** задача, целиком запланированная в спринте 2, показывает forecast интервал 2026-11-02..2026-11-15

### Requirement: Метрическая стратегия планирования

При генерации плана сервис SHALL поддерживать выбор стратегии: `priority` (дефолт, как раньше) и `metrics`. При стратегии `metrics` порядок планирования задач определяется целевой функцией: 1) стратегические задачи (флаг заказчика `planned_in_sprint='Да'`, инициативы PRODF) — первыми; 2) затем задачи, полное выполнение которых закрывает инициативу до конца квартала (дающие числитель KPI % выполнения квартала); 3) далее по убыванию потенциала частичного продвижения инициатив; поле `priority` — тайбрейкер внутри равных групп. Состав плана определяется ТОЛЬКО емкостью и зависимостями: скоринг влияет на очерёдность, не на то, какие задачи включаются в план (знаменатель KPI не управляется).

#### Scenario: Стратегия metrics замыкает инициативу

- **GIVEN** инициатива BR-151: задачи A (запланирована первой по priority) и B; завершение только обеих даёт закрытие инициативы
- **WHEN** план генерируется со стратегией `metrics` и ёмкость позволяет спланировать лишь одну из задач в ранние спринты
- **THEN** планировщик отдаёт раннее место задаче, которая вместе с уже запланированными задачами инициативы закрывает её (числитель KPI растёт), а не задаче с наименьшим priority

#### Scenario: Стратегические задачи первыми

- **GIVEN** задача заказчика (planned_in_sprint=Да, инициатива PRODF-7120) и другая задача с меньшим priority
- **WHEN** план генерируется со стратегией `metrics`
- **THEN** задача заказчика размещается раньше, независимо от поля priority второй

#### Scenario: Дефолт не меняется

- **GIVEN** вызов POST /plans/generate без strategy
- **WHEN** план генерируется
- **THEN** поведение идентично прежнему (стратегия priority), существующие тесты не меняются

### Requirement: Рекомендации перераспределения людей (human-in-loop)

Сервис SHALL предоставлять рекомендации по переносу долей ставок инженеров между командами: симуляция «инженер X, доля ставки D, из команды A в команду B» с расчётом влияния на план (достигаемость ролей, закрываемость инициатив, метрики KPI п. metrics). Рекомендации НЕ подбирают перенос носителей единственных компетенций (Bus Factor ≤ 1 в принимающей команде). Применение рекомендации — только решение человека: правка инженера через существующий CRUD (`PUT /engineers/{id}`) и пересчёт плана.

#### Scenario: Симуляция переноса ставки

- **GIVEN** инженер ENG-405 работает 0.5 ставки в Team-L и Team-Alpha; в Team-L не хватает часов роли «Дизайнер»
- **WHEN** GET /plans/{id}/staffing-suggestions
- **THEN** рекомендации содержат вариант «перенос 0.5 ставки ENG-405 из Team-Alpha в Team-L» с ожидаемым эффектом (какие задачи/инициативы станут планируемыми раньше), без автоматического изменения профиля

#### Scenario: Защита Bus Factor

- **GIVEN** инженер является единственным носителем компетенции в своей команде (Bus Factor = 1)
- **WHEN** формируются рекомендации по людям
- **THEN** вариант его переноса отсутствует (или помечен отказ с причиной)

### Requirement: Назначение по людям

Планировщик SHALL закреплять за каждой запланированной задачей конкретных инженеров по требуемым ролям: назначение описывается четвёркой `task × role × engineer × sprint` (для разбитых задач — по каждой части). Ёмкость инженера (80 ч при полной ставке, 40 ч при 0.5; суммарно за спринт для parttime) расходуется его назначениями; кросс-командный заём сохраняется: инженер MAY быть назначен на задачу другой команды, суммарные назначения за спринт не превышают его лимита. Назначения SHALL выводиться в ответе плана (в каждой части задачи — engineers/role).

#### Scenario: Персональное разбиение задачи

- **GIVEN** DB-202 требует 130 ч роли «Разработчик .NET», в команде один носитель роли с лимитом 80 ч
- **WHEN** план строится
- **THEN** назначения: спринт 1 — 80 ч engineer-E, спринт 2 — 50 ч engineer-E; обе части задачи одной полосой с указанием исполнителя

#### Scenario: Заём с суммированием лимита

- **GIVEN** инженер ENG-419 (0.5 ставки, команды L и Platform) назначен на задачи обеих команд в одном спринте
- **WHEN** проверяются пределы
- **THEN** суммарные назначения ENG-419 за спринт ≤ 40 ч (обе команды суммируются)

### Requirement: Персональный порядок работ

Каждому инженеру план SHALL формировать последовательность его работ: список назначений по спринтам, упорядоченных внутри спринта и между спринтами. Порядок незакреплённых позиций определяется планировщиком (зависимости, стратегия 013, последовательность). Человек MAY закрепить порядок (весь или отдельные позиции) — пересчёт сохраняет закреплённые позиции; незакреплённые планируются вокруг закреплённых (pre-occupancy).

#### Scenario: Личный план

- **GIVEN** ENG-405 назначен на задачи во 2-м и 3-м спринтах
- **WHEN** GET /plans/{id}/people/ENG-405
- **THEN** личная очередь: спринт 2 — [задача A (закреплена человеком), задача B], спринт 3 — [задача C]; порядок A → B сохраняется пересчётом

#### Scenario: Авто-порядок без закреплений

- **GIVEN** ни один порядок не закреплён
- **WHEN** пересчёт
- **THEN** порядок планируется планировщиком (зависимости и стратегия 013) — личная очередь выводится, но не фиксирована пользователем

### Requirement: Закреплённые назначения (pin) — жёсткие якоря

Человек MAY закрепить (pin) назначение (задача–человек–спринт) и/или позицию в личном порядке. Pin applied SHALL немедленным перемещением: строки задачи в текущем версии плана обновляются (sprint_no = целевой) вместе с assignments (инженеры/часы части с целевым спринтом) — без пересборки остального плана; neighborsже не сдвигаются. Пересчёт (кнопка/факт) сохраняет закреплённое как pre-occupancy и расставляет остальных на остатке ёмкости. Лёгкие валидации при закреплении: спринт в границах квартала, факт-спринт закрыт, 409 при недостатке часов у целевого инженера в целевом спринте (плановая загрузка + перемещаемые часы > лимит), конфликт с зависимостью закреплённого блокера — 409. Конфликтные закрепления (нет допустимости на перееханной позиции) отбрасываются с предупреждением compute_warnings при пересчёте; молчаливый сдвиг pinned исключён. Снятие pin — человеческое действие (unpin) — также немедленно (без пересборки).

#### Scenario: Оптимистичный экран и БД согласны

- **GIVEN** пользователь перетащил чип задачи из спринта 2 в спринт 4
- **WHEN** POST pin успешен
- **THEN** строка задачи в БД сразу в спринте 4 (assignmeants тоже), GET /plans/{id} показывает то же — optimistic слой фронта совпадает с сервером

#### Scenario: Ёмкость инженера — 409 на пине

- **GIVEN** целевой инженер в спринте 4 уже загружен свыше лимита добавленными часами
- **WHEN** POST pin
- **THEN** 409 с текстом «нужно X ч, свободно Y», задача не перемещается

#### Scenario: Перетащил — соседи не уехали

- **GIVEN** план построен, пользователь перетащил задачу A в спринт 3 (pin)
- **WHEN** POST pin успешен
- **THEN** задача перемещается немедленно без пересборки версии целиком: соседние задачи стоят на месте; GET /plans/{id} показывает A в спринте 3 сразу

#### Scenario: Пересчёт вокруг pin

- **GIVEN** задача A закреплена (спринт 2, инженер E); после факта спринта 1 у Team-L изменилась нагрузка
- **WHEN** пересчёт
- **THEN** A остаётся в спринте 2 у того же инженера (pre-occupancy); незакреплённые задачи планируются на остатке ёмкости; соседние сдвиги отражены в diff с причиной

#### Scenario: Конфликт pin и зависимости

- **GIVEN** задача B закреплена (спринт 2), но её блокирующая задача после пересчёта завершается в спринте 2
- **WHEN** пересчёт выполнен
- **THEN** конфликт помечен предупреждением (dependency_shift с задачей B и пояснением); человек выбирает вариант (снять/передвинуть pin)

#### Scenario: Pin не влезает

- **GIVEN** закреплённое назначение превышает свободные часы инженера после изменения данных
- **WHEN** пересчёт
- **THEN** закреплённая позиция сохранена (pre-occupancy), соседние задачи отодвигаются; предупреждение указывает на закреплённый элемент

#### Scenario: Пересчёт игнорирует снятый pin

- **GIVEN** pin снят (DELETE /pin)
- **WHEN** пересчёт
- **THEN** задача расставляется планировщиком на общих основаниях

### Requirement: Оптимальная расстановка запускается по кнопке и применяется сразу

Уточнение целевой функции: вес «заполняемости команд per sprint» (teamUtilizationPenalty) оценён бенчмарком на одном исходном плане: подъём 50 → 100 НЕ улучшает выравнивание (σ 10.77 vs 9.91, score идентичен) — вес остаётся 50 (benchmark-driven решение лида). Ёмкостные hard-гейты сохраняются company-wide (change 026/029); кросс-командный заём остаётся законной раскладкой (спека 003).

#### Scenario: Разбивка отчёта

- **GIVEN** optimize job ready
- **WHEN** GET /plans/optimize/{job_id}
- **THEN** report содержит split_by_team_role (before/after: team × role × sprints → SP/часы/limit_hours/within_norm)

#### Scenario: Пустые спринты, выравнивание

- **GIVEN** план, где часть спринтов не заполнена
- **WHEN** оптимизация
- **THEN** доставляемая раскладка показывает более ровное распределение SP по спринтам; нарушений hard нет (hard=0)

#### Scenario: Оптимизация создаёт новую версию

- **GIVEN** существует план на 6 спринтов
- **WHEN** пользователь запускает оптимизацию и solver завершает расчёт успешно
- **THEN** создаётся новая версия плана с заполненными assignments (инженеры на ролях), UI переключается на неё, предыдущие версии открыты через селектор

#### Scenario: Повторная оптимизация не перезаписывает историю

- **GIVEN** было две успешные оптимизации подряд
- **THEN** история содержит обе новые версии (parent_plan_id прежней), обе открываются

#### Scenario: Пер-специалистов сдвиг части

- **GIVEN** solver поместил часть задачи в спринт 3, но носители роли в спринте 3 загружены (80/40 исчерпаны)
- **WHEN** бэк выполняет пер-специалистов распределение
- **THEN** часть сдвигается на следующий свободный спринт/в заём; если конец квартала — «выполнится частично», версия не отклоняется

#### Scenario: Оптимизация после факта не переигрывает выполненное

- **GIVEN** загружен факт спринта 1 с completed_task_ids, план пересчитан
- **WHEN** пользователь запускает оптимизацию пересчитанной версии
- **THEN** выполненные по факту задачи отсутствуют в новой версии (не planned), ни один item не находится в спринтах ≤ 1

#### Scenario: Оптимизация без фактов не меняется

- **GIVEN** факты не загружены
- **WHEN** оптимизация запущена
- **THEN** расстановка доступна по всем спринтам 1..6, все не-Done задачи участвуют

### Requirement: Жёсткие ограничения оптимизации

Solver SHALL соблюдать правила планирования change 003 как hard-ограничения: ёмкость команды по SP (velocity × 0,8); часы ролей против лимитов специалистов (80 ч при полной ставке, 40 при 0,5) с кросс-командным заёмом по остатку лимитов; потребность в ролях каждой задачи (role_hours); зависимости задач (зависимая задача стартует после последнего спринта блокера); статусы — Done вне планирования, InProgress по остатку часов (estimated_hh − spent_time) с пропорциональным SP; роли без носителей планироваться через виртуального держателя с полной ставкой; разбиение задачи между несколькими спринтами разрешено (SP/часы пропорционально, остаток помечается «выполнится частично»). Бэк MUST валидировать черновик solver'а по этим правилам до записи версии: при нарушении версия не создаётся (HTTP 422), текущий план остаётся действующим.

#### Scenario: Черновик без нарушений принимается

- **GIVEN** solver вернул расстановку, в которой все hard-ограничения соблюдены
- **WHEN** бэк проверяет черновик
- **THEN** создаётся новая версия плана

#### Scenario: Черновик с нарушением отклоняется

- **GIVEN** solver вернул черновик, где сумма SP команды в спринте превышает velocity × 0,8
- **WHEN** бэк валидирует черновик
- **THEN** версия не создаётся (422), старый план остаётся актуальным, ошибка объясняется пользователю

### Requirement: Целевая функция по метрикам ТЗ

Целевая функция оптимизации SHALL максимизировать в порядке приоритета: (1) число инициатив (parent_id), полностью завершённых в пределах 6 спринтов; (2) запланированные SP стратегических задач заказчика (`planned_in_sprint = Да`); (3) предсказуемость плана — соответствие нормы PI 80–100 %. При равенстве SHALL минимизироваться: незакрытые человеко-часы ролей, переносы людей между командами (тяжёлый штраф), нарушения порядка human priority (меньше priority — раньше). SP-гейт и часовой гейт MUST оставаться независимыми: Story Points и трудозатраты не конвертируются друг в друга.

#### Scenario: Стратегическая задача важнее поздней редкости

- **GIVEN** в один спринт помещается либо задача заказчика, либо не связанная с ней удобная задача
- **WHEN** оптимизация завершена
- **THEN** в план включена задача заказчика, а распределение остальных подчинено

#### Scenario: Человек-часы ролей обязательны в расстановке

- **GIVEN** задача требует часы ролей, чьи носители на данном спринте перегружены
- **WHEN** расстановка построена
- **THEN** задача не занимает этот спринт по этой роли (либо «выполнится частично»), а не создаёт перегруз носителя сверх 80/40 ч

### Requirement: Переносы людей между командами — крайняя мера оптимизации

Оптимизация MAY предлагать перенос части ставки инженера в другую команду, только если это повышает целевую функцию сверх заданного порога. Перенос SHALL быть запрещён для инженеров, которые являются единственными носителями какой-либо компетенции в своей команде (Bus Factor = 1 в масштабе команды итога переноса не может стать 1 там, где был > 1). Перенос MUST быть виден: в оптимизация-отчёте (кто, откуда, куда, эффект на метрики), в версии плана (применённые переносы) и в профиле инженера на звёздной карте.

#### Scenario: Профитный перенос применяется сразу

- **GIVEN** перенос части ставки закрывает стратегическую инициативу, которая иначе не помещается в квартал
- **WHEN** оптимизация завершена
- **THEN** перенос применён в новой версии, отчёт показывает эффект на метрики

#### Scenario: Единственный носитель не переносится

- **GIVEN** инженер — единственный носитель компетенции в своей команде
- **WHEN** solver рассматривает его перенос
- **THEN** перенос отклоняется на уровне ограничений

### Requirement: Деградация без solver

Планировочная схема SHALL поддерживать двe причины ухода в эвристику: (1) сайдкар недоступен (транспорт/HTTP/таймаут — change 018); (2) solver завершился, но не достиг выполнимости раскладки (`score.hard != 0` — change 029). Обе причины SHALL сопровождаться `degradation_reason` в отчёте и не возвращать 422; 422 при записи версии остаётся только для нерепарируемых структурных нарушений после repair-шага. Кейс «solver отдал hard=0, Python нашёл нарушение» SHALL восстанавливаться repair-шагом (сдвиг зависимых частей за конец блокера, та же семантика, что в replanning) с обязательной повторной hard-валидацией.

#### Scenario: Solver не поднят

- **GIVEN** solver-сайдкар недоступен (команда запускает бэк без compose-профиля optimizer)
- **WHEN** пользователь запускает оптимизацию
- **THEN** план создаётся жадной стратегией 013, отчёт помечает режим «эвристика», ошибки нет

#### Scenario: Честный флаг неуспеха

- **GIVEN** solver вернул черновик с score.hard != 0
- **WHEN** бэк обрабатывает черновик
- **THEN** эвристика-версия с mode=heuristic, degradation_reason в отчёте — без 422

#### Scenario: 422 только для нерепарируемого

- **GIVEN** после repair Python-валидация находит структурное нарушение
- **WHEN** записывается версия
- **THEN** 422 failed, текущий план остаётся действующим (change 018)

### Requirement: AI-советник пересчёта (human-in-loop)

Сервис SHALL предоставлять одноразовые советы по сводке состояния плана (риски, KPI, optimization-report, кадровые предложения) в двух режимах: LLM через провайдер env (GigaChat/Ollama/none) и fallback на детерминированных отчётах ядра. Совет одноразовый: весь контекст прогона — один комментарий (≤ 500 символов). **Изменение семантики (change 043)**: прогон советов SHALL сохраняться в истории вместе с комментарием, режимом, версией плана и временем; история доступна по версии плана (per-plan_id) с version_label (номер версии + дата). Комментарий теперь сохраняется (прежнее требование «никогда не сохраняется» отменяется). Применение советов — только человеком через существующие ручки (пересчёт, приоритеты, закрепления); советы не меняют план, пересчёт или записи плана в БД.

#### Scenario: Совет сохраняется в историю с версией

- **GIVEN** пользователь запросил советы с комментарием «ENG-405 заболел»
- **WHEN** прогон завершён
- **THEN** запись в истории содержит: version_label (версия плана), mode, comment, advice items, created_at; GET /plans/{id}/advice/history отдаёт её по этой версии плана

#### Scenario: История по версии плана

- **GIVEN** две версии плана, советы запрошены на обеих
- **WHEN** GET /plans/{v1}/advice/history и GET /plans/{v2}/advice/history
- **THEN** каждая история содержит только прогоны своей версии, с version_label своей версии

#### Scenario: Переключение вкладок не слетает

- **GIVEN** запрос советов в полёте (спиннер)
- **WHEN** пользователь перешёл на другую вкладку и вернулся
- **THEN** запрос завершился, советы видны (react-query кэш глобальный)

#### Scenario: История советов с комментарием

- **GIVEN** запрошенные советы с комментарием
- **WHEN** пользователь открывает историю советов
- **THEN** видно комментарий прогона (если был), режим, версию плана и время

#### Scenario: Совет о переносе

- **GIVEN** после факта спринта 1 изменились сроки; инициатива BR-151 может закрыться, если задача A переедет в ранний спринт
- **WHEN** пользователь открывает советы
- **THEN** виден совет `task_move`: переместить A, с численным обоснованием (сколько часов роли высвободится, какой KPI поднимется) и affected_task_ids

#### Scenario: Агент не двигает закреплённое

- **GIVEN** задача pinned (закреплена человеком, см. 016)
- **WHEN** формируются советы
- **THEN** варианты, смещающие закреплённую задачу, отсутствуют

#### Scenario: Применение совета человеком

- **GIVEN** совет «перенести задачу A в спринт 2»
- **WHEN** человек принял совет
- **THEN** изменение делается существующими ручками (например POST /plans/{id}/recompute после смены приоритета); новых ручек мутации советник не требует

#### Scenario: Комментарий-контекст учитывается

- **GIVEN** пользователь вызвал советы с comment «ENG-405 заболел до конца недели»
- **WHEN** советы формированы
- **THEN** советы учитывают комментарий (например, не предлагают переносить дополнительную нагрузку на ENG-405), причём комментарий не сохраняется: повторный вызов без comment даёт советы без учёта, а план и БД неизменны

#### Scenario: Дозапрос недоступен

- **GIVEN** совет показан, пользователь продолжает диалог («а почему эту?»)
- **WHEN** UI/ручка советов
- **THEN** видно предупреждение, что совет одноразовый и перегенерируется заново с новым комментарием; все обстоятельства указываются в одном комментарии прогона

### Requirement: Деградация советника без LLM

Без доступного ключа GigaChat советник SHALL отдавать детерминированные подсказки, построенные из отчётов планировщика (топ-риски, optimization-report, staffing-suggestions) — в том же формате советов; демо MUST работать без LLM.

#### Scenario: Нет ключа на демо

- **GIVEN** GIGACHAT_* не заданы
- **WHEN** запрошены советы
- **THEN** советы собраны из детерминированных отчётов (не пустые), формат идентичен LLM-советам

#### Scenario: Невалидный ответ LLM

- **GIVEN** ответ LLM не проходит pydantic-валидацию
- **WHEN** рендеринг советов
- **THEN** retry ≤ 2, затем fallback на детерминированные подсказки (правила capability onboarding соблюдаются)

### Requirement: Пер-специалистов распределение в solver-версиях

После успешной optimize-версии каждая запланированная часть задачи SHALL содержать назначения task×role×engineer×sprint: часы ролей закреплены за конкретных носителей жадным распределителем (лимит 80 ч × ставка на инженера, заём из других команд при нехватке в команде задачи, виртуальный держатель для ролей без носителей). Диапазон пер-специалистов лимитов MUST гарантироваться перед записью версии; при фиктивных аномалиях (роль с суммой часов, не размещаемой ни в каком спринте до конца квартала) — «выполнится частично», а не вырожденный план. Личные планы (`GET /plans/{id}/people/{engineer_id}`) и звёздная карта SHALL показывать solver-версии так же, как жадные.

#### Scenario: Распределение по специалистам

- **GIVEN** solver разместил 100 ч роли в спринте, носителями которой являются два инженера (80 ч + 40 ч лимитов)
- **WHEN** бэк выполняет пер-специалистов распределение
- **THEN** часы закреплены (напр., 80 + 20), assignments Patrimoine версия содержит engineer_id, личные планы обоих инженеров показывают назначения

#### Scenario: Честный частичный остаток

- **GIVEN** часть роли 100 ч, носитель один с лимитом 80 ч, конец квартала в следующем спринте
- **WHEN** перестройка завершается
- **THEN** 40 ч переносится в следующий спринт, 20 ч остаток — «выполнится частично» с причиной; план не отклонен (не вырожден)

#### Scenario: Структурные нарушения по-прежнему 422

- **GIVEN** черновик solver'а нарушает зависимость или переносит единственного носителя
- **WHEN** бэк валидирует
- **THEN** 422, версия не создаётся (как и раньше)

### Requirement: Pre-split частей в снапшоте

Перед отправкой в solver каждая задача SHALL разрезаться на k = ⌈потребность в часах ÷ 80⌉ частей (округление вверх, максимум 6 частей), SP и роль-часы делятся между частями пропорционально; solver раскладывает части независимо. Непомещённые части (unassigned) SHALL интерпретироваться как «вне квартала», а часть задач с частью assigned и частью unassigned — как «выполнится частично» (частичная раскладка легитимна).

#### Scenario: Растяжение по спринтам

- **GIVEN** задача с потребностью 190 ч (не влезает в один спринт даже полностью)
- **WHEN** снапшот отправлен в solver
- **THEN** задача представлена 3 частями (например 80+80+30), solver может распределить их по 2–3 спринтам, план содержит полосу, растянутую через ячейки

#### Scenario: Частично не поместившаяся задача

- **GIVEN** из 3 частей задачи solver разместил в квартале только 2
- **WHEN** версия записана
- **THEN** задача помечена «выполнится частично» с причиной и числом непоместившихся часов

### Requirement: Объяснение пустой генерации при отсутствии team_history

Если у команды, чьи задачи планироваться, нет строк в team_history (velocity=0), генерация плана SHALL создавать Explanation для каждой задачи этой команды: «истории velocity нет — capacity=0; задачи не запланированы». Ручка也可能 возвращать предупреждение noise composition_change. Юзер SHALL видеть причину, а не молчаливый пустой план. README MUST документировать это ограничение (наполнить team_history или задать velocity).

#### Scenario: Новый workspace без истории

- **GIVEN** задачи добавлены руками, team_history отсутствует
- **WHEN** POST /plans/generate
- **THEN** план содержит только explanations с явной cause «истории нет», никаких «молчаливых» пропусков; юзер понимает, что нужно задать velocity

### Requirement: Приоритет своей команды при закрытии ролей

При закрытии ролевых часов задачи сервис SHALL предпочитать инженеров **своей команды задачи** (по свободным часам) перед заёмными из других команд; заём берётся только при нехватке своих носителей в данном спринте. Pinned/preferred-инженер приоритетнее любого выбора.

#### Scenario: Своя команда свободна — заём не берётся

- **GIVEN** задача требует 40 ч Тестировщика, свободный тестировщик есть в своей команде и в чужой
- **WHEN** планирование
- **THEN** часы закрываются инженером своей команды, заём не берётся

#### Scenario: Заём только при нехватке своих

- **GIVEN** задача требует 120 ч Тестировщика, свой носитель даёт только 80 ч в спринте
- **WHEN** планирование
- **THEN** 80 ч — свой инженер, остаток — заём (приоритет своей команды сохранён)

### Requirement: Концентрация займа в одной донорской команде

При займе ролевых часов из других команд сервис SHALL закрывать часы из **одной донорской команды** с максимальным суммарным свободным лимитом роли в данном спринте; при её нехватке — из **одной запасной** (второй по лимиту); третья и последующие команды SHALL NOT использоваться — остаток часов переносится в следующий спринт. Виртуальные держатели ролей без носителей и pinned/preferred-инженер этим ограничением не затрагиваются.

#### Scenario: Займ из одной донорской

- **GIVEN** задача требует 100 ч роли, своя команда не может закрыть, донорские команды B (160 ч свободно), C (40 ч), D (30 ч)
- **WHEN** планирование
- **THEN** все 100 ч закрываются инженерами команды B, команды C и D не затрагиваются

#### Scenario: Запасная донорская при нехватке первой

- **GIVEN** задача требует 100 ч роли, донорская B даёт 60 ч, запасная C — 50 ч, есть ещё D (40 ч)
- **WHEN** планирование
- **THEN** 60 ч — команда B, 40 ч — команда C; команда D не используется

#### Scenario: Отложка при нехватке двух донорских

- **GIVEN** задача требует 150 ч роли, донорские B (60 ч) и C (50 ч) суммарно дают 110 ч, есть ещё D (40 ч)
- **WHEN** планирование
- **THEN** в спринте размещается 110 ч из B и C; остаток 40 ч переносится в следующий спринт, команда D не используется

### Requirement: Минимальный размер части роли при pre-split

При разбиении задачи на части (pre-split для solver) сервис SHALL NOT дробить роль на части мельче 2 часов (`MIN_ROLE_PART_HOURS`): если доля роли в части меньше минимума, все часы этой роли назначаются последней части целиком. Роли с долей не меньше минимума делятся пропорционально доле части. Сумма часов роли по частям SHALL сохраняться.

#### Scenario: Мелкая роль не дробится

- **GIVEN** задача на 191 ч с ролями Разработчик 190 ч и Девопс 1 ч (k=3 части)
- **WHEN** pre-split
- **THEN** Девопс 1 ч целиком в части 3; части 1–2 не содержат Девопс; Разработчик делится пропорционально

#### Scenario: Роль выше порога дробится пропорционально

- **GIVEN** задача на 160 ч с ролями Разработчик 150 ч и Тестировщик 10 ч (k=2 части)
- **WHEN** pre-split
- **THEN** обе роли делятся пропорционально доле части; каждая часть Тестировщика ≥ 2 ч

### Requirement: Честная атрибуция команды-исполнителя в API плана

Элемент плана в ответе API SHALL содержать `team_id` команды-исполнителя части (solver может назначить часть другой команде) и `owner_team_id` команды-владельца задачи. Таблицы загрузки по командам SHALL группироваться по команде-исполнителю, чтобы SP атрибутировались той команде, чья ёмкость реально потребляется.

#### Scenario: Часть исполняет другая команда

- **GIVEN** solver назначил часть задачи T-1 (владелец Team-A) команде Team-B
- **WHEN** GET /plans/{id} оптимизированной версии
- **THEN** элемент T-1 содержит team_id=Team-B и owner_team_id=Team-A

### Requirement: Отображение команды-исполнителя на фронте

Фронтенд SHALL атрибутировать SP и отображение задач командам-**исполнителям** частей (поле `team_id` строк плана): статистика загрузки по командам считается по исполнителю каждой части; при группировке по командам задача с частями у нескольких исполнителей показывается в группе каждого из них и находится фильтром по любому; для задач, где владелец (`owner_team_id`) отличается от исполнителей, панель задачи показывает обоих.

#### Scenario: Cross-team задача на Ганте

- **GIVEN** части задачи X исполняют Team-A и Team-B
- **WHEN** группировка Ганта по командам
- **THEN** задача X видна в группах Team-A и Team-B; фильтр по любой из команд находит X

#### Scenario: SP mini-stats по исполнителям

- **GIVEN** части задачи X (10 SP) исполняют Team-A (6 SP) и Team-B (4 SP)
- **WHEN** отображение статистики команд в «Ролях по спринтам»
- **THEN** Team-A получает 6 SP, Team-B — 4 SP (не 10 SP одной команде)

### Requirement: «Роли по спринтам» отображают реальные назначения

Вкладка «Роли по спринтам» SHALL строить чипы из поля `assignments` ответа плана (реальные инженер × роль × часы, вычисленные бэкендом), а не пересчитывать часы из `role_hours` задачи и SP-доли части. Дорожка чипа — команда инженера из назначения; признак займа — команда инженера отличается от команды-владельца задачи; назначения виртуальных держателей (`VIRTUAL-*`) отображаются как дефицит в дорожке команды-владельца. Чипы SHALL агрегироваться по (дорожка, задача, роль, заём): один чип на комбинацию с суммарными часами и числом инженеров; номер части отображается по разным спринтам задачи.

#### Scenario: Часы соответствуют бэкенду

- **GIVEN** часть задачи имеет назначение: инженер ENG-1 (Team-B), роль Аналитик, 13.2 ч, владелец задачи Team-A
- **WHEN** отображение «Ролей по спринтам»
- **THEN** чип 13.2 ч в дорожке (Team-B, Аналитик) с признаком займа; пересчёт по SP-доле не применяется

#### Scenario: Агрегация назначений

- **GIVEN** одна роль задачи в спринте закрыта двумя инженерами одной команды (13.2 ч + 13.2 ч)
- **WHEN** отображение
- **THEN** один чип 26.4 ч с указанием 2 инженеров, а не два чипа

#### Scenario: Две части в одном спринте — один чип

- **GIVEN** задача имеет две части в спринте 1 (и больше нигде)
- **WHEN** отображение
- **THEN** один агрегированный чип без пометки «1/2»

### Requirement: Закрепление части задачи

`POST /plans/{id}/tasks/{task_id}/pin` SHALL принимать необязательное поле `from_sprint_no`. Если оно задано, SHALL перемещаться только строка задачи из спринта `from_sprint_no` (её SP и assignments), остальные части задачи остаются на своих спринтах; если строки задачи в этом спринте нет — 404. Без `from_sprint_no` перемещаются все строки задачи (прежнее поведение). После перемещения строки задачи в целевом спринте SHALL сливаться по команде-исполнителю: одна строка на (задача × спринт × исполнитель) — `planned_sp` суммируется, assignments объединяются с `sprint_no` целевого спринта, лишние строки удаляются; строки разных команд-исполнителей остаются раздельными (048: SP атрибутируется реальному исполнителю). Закрепление (`pinned_sprint`) ставится на пережившие строки. Проверки границ квартала, факта (`done_actual` → 409), зависимостей и ёмкости инженера сохраняются; ёмкость считается по часам перемещаемой части. `DELETE .../pin` снимает закрепление со всех частей задачи.

#### Scenario: Перенос одной части

- **GIVEN** задача размещена частями в спринтах 2, 3 и 4
- **WHEN** POST pin `{sprint_no: 2, from_sprint_no: 4}`
- **THEN** в спринте 4 задачи больше нет, часть из спринта 3 на месте, в спринте 2 — по одной строке задачи на каждую команду-исполнителя с суммой SP её частей и assignments с `sprint_no = 2`

#### Scenario: Нет части в исходном спринте

- **GIVEN** задача размещена только в спринте 2
- **WHEN** POST pin `{sprint_no: 3, from_sprint_no: 5}`
- **THEN** 404, план не меняется

#### Scenario: Перенос всей задачи

- **GIVEN** задача размещена частями в спринтах 2 и 3
- **WHEN** POST pin `{sprint_no: 2}` без `from_sprint_no`
- **THEN** у задачи одна строка в спринте 2
