# jobs Specification

## Purpose
Фоновая обработка тяжёлых и долгих операций (LLM-нормализация upload, будущие AI-фичи) — вне процесса HTTP-запроса. Спека фиксирует наблюдаемое поведение; конкретный стек очередей (Celery / RQ / arq / …) выбирает исполнитель. Архитектурная рамка — модульный монолит + воркер задач (микросервисы — вне рамок на этом этапе).

## Requirements

### Requirement: Персистентность job-состояний

Состояние job (upload, этапы, вопросы, preview) SHALL храниться в персистентном хранилище (БД или shared-хранилище, не память процесса): job переживает рестарт API и доступна через любой воркер-процесс.

#### Scenario: Рестарт во время обработки

- **GIVEN** job в статусе questions, процесс рестартует
- **WHEN** GET /data/jobs/{job_id}
- **THEN** 200, статус questions сохранён, вопросы доступны

#### Scenario: Второй воркер

- **GIVEN** два uvicorn-процесса за балансировщиком/разделением
- **WHEN** job создан на воркере 1, статус запрошен у воркера 2
- **THEN** состояние одинаковое

### Requirement: Фоновое выполнение LLM-фазы

LLM-нормализация незнакомого формата (capability onboarding) SHALL выполняться фоново (в воркере очереди), не блокируя HTTP-ответ: POST /data/upload остаётся быстрым (возвращает job_id), статус опрашивается GET /data/jobs/{job_id} polling-ом.

#### Scenario: Снимок нормализации не блокирует

- **GIVEN** пользователь загрузил незнакомый файл
- **WHEN** LLM-фаза продолжается
- **THEN** endpoint upload уже вернул 201 с job_id; polling статуса не обрывается из-за долгой операции

### Requirement: Деградация без брокера/воркера

Если брокер/воркер недоступны (не настроены, упали), сервис SHALL выполнять обработку синхронно в том же процессе (как сейчас), без hard-fail — сохраняя все состояния и контракты. Демо и тесты MUST работать без Redis в docker-compose.

#### Scenario: Нет Redis на демо

- **GIVEN** брокер не настроен/недоступен
- **WHEN** загрузка файла
- **THEN** пайплайн выполняется в процессе запроса, функционал полный

### Requirement: Видимые этапы и ошибки

Job SHALL показывать текущий этап (uploaded/mapping/questions/ready/confirmed/failed) и статус ошибок; зависание по таймауту MUST переходить в понятный статус ошибки (failed с причиной), не вечный polling.

#### Scenario: Тяжёлая LLM-фаза зависла

- **GIVEN** LLM-вызов превышает таймаут
- **WHEN** GET /data/jobs/{job_id}
- **THEN** статус failed с причиной «таймаут LLM-нормализации», есть повторный POST /ai/normalize

### Requirement: Контракт API сохранён

Ручки онбординга (upload/jobs/answers/confirm/normalize) SHALL сохранять нынешние запрос/ответ из capability api и документации; change не ломает контракт фронтендера.

#### Scenario: Обратная совместимость

- **GIVEN** фронтенд по docs/api-contract.md
- **WHEN** все ручки онбординга вызваны
- **THEN** форматы запросов и ответов не изменились (только персистентность/фоновость внутри)

### Requirement: Фоновый прогон solver'а и лимит LLM-вызовов

При доступном брокере (Redis, `JOBS_MODE=auto|queue`) запуск оптимизации плана SHALL ставиться в очередь: `POST /plans/optimize` быстро возвращает job со статусом `queued`, воркер ведёт его через `solving → ready | failed` (причины те же, что в синхронном режиме: 422 — невалидный черновик, 403 — переносы без права). Статус опрашивается существующим `GET /plans/optimize/{job_id}`. Если брокер недоступен или `JOBS_MODE=sync`, запуск оптимизации SHALL выполняться синхронно в процессе запроса (как раньше) — контракт деградации change 018 сохраняется. Параллельные LLM-вызовы SHALL ограничиваться лимитом конкурентности (настройкой), превышение — ожидание в очереди семафора, без hard-fail.

#### Scenario: Оптимизация уходит в очередь

- **GIVEN** Redis и воркер подняты, JOBS_MODE=auto
- **WHEN** editor запускает POST /plans/optimize
- **THEN** ответ приходит быстро со статусом queued; через polling GET /plans/optimize/{job_id} статус становится solving → ready с новой версией плана

#### Scenario: Деградация без очереди

- **GIVEN** Redis недоступен или JOBS_MODE=sync
- **WHEN** editor запускает оптимизацию
- **THEN** solve выполняется в процессе запроса (поведение change 018/026), статус ready приходит в том же ответе

#### Scenario: Параллельные optimize — 409

- **GIVEN** в workspace есть job оптимизации со статусом queued или solving
- **WHEN** повторный POST /plans/optimize
- **THEN** 409, как в синхронном режиме

#### Scenario: LLM-вызовы не штурмуют провайдера

- **GIVEN** лимит конкурентности LLM = 2
- **WHEN** 5 запросов советника приходят одновременно
- **THEN** не более 2 одновременных вызовов провайдера, остальные ожидают; ответы корректны, без ошибок
