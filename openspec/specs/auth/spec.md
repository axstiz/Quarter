# auth Specification

## Purpose
Многопользовательность и роли. Спека фиксирует контракт до реализации (spec-only): минимальную auth для демо и публичного сервера — email+пароль, роли admin/editor/reader по workspace-ам, сессии; доступ управляется владельцем проекта, а не саморегистрацией. Данные компании общие для её участников (демо-датасет); доступ к самой компании — и просмотр, и правки — только создателю и приглашённым (capability workspace, change 008). Несколько компаний в одной инсталляции — отдельная change (workspace, 008).

## Requirements

### Requirement: Роли и права

Роли выдаёт админ workspace-а и они SHALL быть локальными по workspace-у: минимум admin (админ), editor (редактор), reader (читатель). Права изменяющих действий: admin — всё (в т.ч. управление участниками и правами); editor — правки планов/приоритетов/отмен/фактов/данных и создание планов; reader — только чтение. Матрица ручек → ролей и настройка прав админом — отдельная capability (permissions, change 009).

#### Scenario: Наблюдатель

- **GIVEN** пользователь с ролью reader в данном workspace
- **WHEN** он пытается загрузить факт спринта
- **THEN** 403 с объяснением роли

### Requirement: Доступ управляет владелец проекта

Доступ пользователей SHALL управляться владельцем проекта (admin), а не саморегистрацией: выдача и изменение ролей — только владелец (или назначенные им админы) через ручки управления; открытая саморегистрация MAY быть отключена (закрытый режим — по приглашениям/одобрению). Пользователь MUST НЕ иметь возможности изменить собственную или чужую роль сам.

#### Scenario: Владелец выдаёт роль

- **GIVEN** админ workspace-а и новый участник
- **WHEN** админ назначает участнику роль editor
- **THEN** участник получает права редактора; в журнале изменяющих действий видно, кто и когда выдал роль

#### Scenario: Самовозвышение запрещено

- **GIVEN** пользователь с ролью reader
- **WHEN** он пытается поднять себе роль (изменить свой профиль/роль)
- **THEN** 403 — изменение ролей доступно только владельцу

### Requirement: Регистрация и вход

Сервис SHALL предоставлять регистрацию и вход (email + пароль, хранение — только хэш), выдающий сессию/токен; вход по другим средствам (OAuth и т.п.) — вне рамок.

#### Scenario: Успешный вход

- **GIVEN** зарегистрированный пользователь с корректным паролем
- **WHEN** POST /auth/login
- **THEN** 200 с токеном; неверный пароль — 401

### Requirement: Демо-пользователь

Сервис SHALL поддерживать «войти как демо-пользователь» (роль editor или admin по решению админа workspace-а) для проверки сценария без регистрации — как на демо-сервере, так и локально.

#### Scenario: Демо-вход

- **GIVEN** пустая БД пользователей
- **WHEN** POST /auth/demo-login
- **THEN** сессия демо-лида, пользователь появляется в списке, правки работают

### Requirement: Закрытые ручки

Без допустимой сессии все ручки /api/v1 SHALL отвечать 401 (ручка /healthz MAY оставаться открытой). Частичный аутентифицированный доступ к изменяющим ручкам НЕ допускается.

#### Scenario: Запрос без сессии

- **GIVEN** нет токена
- **WHEN** POST /api/v1/plans/generate
- **THEN** 401 с идентификатором ошибки в теле

### Requirement: Смена CORS после auth

После включения auth дефолт CORS `*` MUST перестать применяться: `CORS_ORIGINS` задаёт конкретные origin (с учётом credentials); запросы с прочих origin отклоняются.

#### Scenario: Чужой origin

- **GIVEN** CORS_ORIGINS=https://planner.example.com и включён auth
- **WHEN** запрос с Origin http://evil.example
- **THEN** CORS-запрет браузера (нет Access-Control-Allow-Origin с этим origin)

### Requirement: Конкурентные правки плана

Планы SHALL оставаться версионированными (снапшот-цепочка, capability planning/replanning): правки двух пользователей не Last-write-wins — каждая правка создаёт новую версию с родителей; UI показывает обе версии и автора, выбор актуальной — за лидом.

#### Scenario: Два лида правят один план

- **GIVEN** лид A сменил приоритеты и пересчитал (версия v2)
- **AND** лид B после этого загрузил факт (на базе v1)
- **WHEN** план открыли
- **THEN** версии v1, v2, v3 (parent→child) видны с авторами; конфликт решается выбором базы для следующей версии, данные не теряются

### Requirement: Авторство правок

Изменяющие действия (приоритет, отмена, факт, пересчёт, cancel-request/confirm-cancel) MUST записываться с автором (user_id/name) и показываться в ответах связанные с правками (например reason + [автор]).

#### Scenario: Подтверждение отмены с автором

- **GIVEN** лид A подтвердил отмену задачи T1
- **WHEN** пользователь открывает объяснение задачи
- **THEN** в решении видно «отмена подтверждена, автор — A»
