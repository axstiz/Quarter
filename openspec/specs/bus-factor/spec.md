# Bus Factor — зависимость от отдельных носителей компетенций

## Purpose

Bus Factor отражает зависимость работы от отдельных носителей компетенций: пользователь видит, где отсутствие одного сотрудника создаёт риск для выполнения работ. Расчёт по областям, для которых считается показатель (команды / отдельные компетенции) по данным `engineers_profiles.csv`. Конкретную методику и допущения команда договорится после созвона и зафиксирует через change proposal — пока фиксированы рамки из задания.

## Requirements

### Requirement: Расчёт Bus Factor

Сервис SHALL рассчитывать Bus Factor по компетенциям на основе ролей и заявленных навыков инженеров.

#### Scenario: Компетенция с носителем

- **GIVEN** несколько инженеров владеют компетенцией «Java»
- **WHEN** пользователь смотрит Bus Factor компании
- **THEN** для этой компетенции отображается число носителей

### Requirement: Объяснение методики

Сервис SHALL объяснять используемую методику расчёта Bus Factor и область, для которой рассчитывается показатель (команда / роль / вся компания).

#### Scenario: Справка о методике

- **WHEN** пользователь открывает раздел Bus Factor
- **THEN** рядом с показателем видна формулировка методики и область расчёта

### Requirement: Риск одиночной зависимости

Сервис SHALL выделять случаи, когда уход одного сотрудника создаёт риск для планируемых работ: компетенции с единственным носителем в области.

#### Scenario: Уникальный носитель роли

- **GIVEN** в Team-L роль «Дизайнер» имеет только одного носителя (ENG-405, 0.5 ставки)
- **THEN** для Team-L отображается отметка одиночной зависимости по этой роли

### Requirement: Риски в терминах планирования

Сервис SHALL связывать риски Bus Factor с планированием: показывать, какие задачи квартального плана затронутых компетенций оказываются под угрозой.

#### Scenario: Задача под угрозой

- **GIVEN** на задачу требуются часы роли с единственным носителем
- **WHEN** пользователь смотрит риск
- **THEN** виден список задач, зависящих от этого носителя

### Requirement: Риски плана в терминах задач

Сервис SHALL сопоставлять риски Bus Factor с задачами запланированного плана: единая ручка возвращает задачи, затронутые компетенциями/ролями с единственным носителем, для виджета дашборда (user flow v0.4, стр. 1).

#### Scenario: Виджет дашборда

- **WHEN** фронтенд открывает дашборд плана
- **THEN** виджет «N задач под угрозой» берёт данные из одной ручки (без склейки /bus-factor и role_hours на фронте)

### Requirement: Расчёт по каждой команде

Для каждой команды сервис SHALL вычислять отдельный набор факторов Bus Factor по ролям и заявленным навыкам (область team): инженеры одной команды не учитываются в факторе другой; инженер с частичной занятостью (0.5 ставки в двух командах) — носитель в обеих. Командные факторы — первоклассная область расчёта (не побочный продукт company-расчёта), доступная по фильтру и через ручку команды.

#### Scenario: Фактор команды

- **GIVEN** команда Team-L, роль «Дизайнер» — единственный носитель в этой команде (ENG-405, 0.5 ставки)
- **WHEN** расчёт по области team=Team-L
- **THEN** item {scope_type: team, scope_id: Team-L, key: «дизайнер», factor: 1, holders: [ENG-405]}

#### Scenario: Границы команды

- **GIVEN** инженер ENG-999 (не состоит в Team-K) владеет навыком «Spark»
- **WHEN** расчёт по области team=Team-K
- **THEN** ENG-999 (не-человек-команды) не входит в holders фактора «spark» для Team-K

### Requirement: Расчёт в границах workspace

Расчёт Bus Factor SHALL выполняться в границах одного workspace (capability workspace, change 008): engineers разных workspace-ов не смешиваются в одной области. Термин `company` в существующей спеке после реализации 008 читается как «текущий workspace» (дефолт при единственном workspace — прежнее одно-датасетное поведение).

#### Scenario: Одинаковый навык в двух компаниях

- **GIVEN** навык «Spark» — единственный носитель в workspace A (factor 1) и два носителя в workspace B (factor 2)
- **WHEN** расчёт выполняется отдельно в контексте workspace A и в контексте workspace B
- **THEN** области независимы: workspace A → factor 1, workspace B → factor 2; смешения нет

#### Scenario: Дефолт без workspace

- **GIVEN** workspace-контекст не указан (change 008 не реализован или default)
- **WHEN** GET /bus-factor
- **THEN** расчёт по всем инженерам default workspace — прежнее поведение

### Requirement: Прогноз bus factor по плановой загрузке

Сервис SHALL предоставлять ручку `GET /plans/{plan_id}/bus-forecast` — прогноз возможных проблем bus factor в будущем на основе плановой загрузки людей (версия плана, assignments: task × роль × инженер × спринт × часы, change 016/022). Для каждого инженера с загрузкой ответ SHALL содержать: плановые часы по каждому спринту и сравнение с личным лимитом (80 × capacity_rate), суммарный объём (число задач, часов за квартал), роли, в которых он единственный носитель (область «компания», как в «Риски плана в терминах задач»), перегруженные спринты (часы > лимита) и прогнозную оценку: «если носитель уйдёт — N задач / M часов под угрозой» с уровнем риска (high/medium/low) и численным основанием (basis). Уровень high SHALL ставиться, когда инженер единственный носитель хотя бы одной роли и его плановый объём существенен (задач ≥ 3 или часов ≥ 80); medium — единственный носитель с любой загрузкой ИЛИ перегрузка ≥ 1 спринта; low — остальные. Ответ SHALL прикладывать методику расчёта (текстом). Люди без плановой загрузки SHALL NOT попадать в ответ. Ручка доступна любому участнику workspace (read-only), 404 — план не найден.

#### Scenario: Единственный носитель с большой загрузкой

- **GIVEN** план, где инженер X — единственный носитель роли «Dev» в компании и на нём 4 задачи на 120 ч в спринтах 2–4
- **WHEN** GET /plans/{plan_id}/bus-forecast
- **THEN** X в ответе с уровнем high, critical_roles содержит «Dev», affected 2 задачи / 120 ч, basis называет числа

#### Scenario: Загрузка без критичных ролей

- **GIVEN** инженер Y с плановой загрузкой, роль которого носит ещё 3 человека
- **WHEN** GET /plans/{plan_id}/bus-forecast
- **THEN** Y с уровнем low/medium и без critical_roles; уход Y не помечается риском bus factor

#### Scenario: Перегрузка спринта

- **GIVEN** инженер Z со ставкой 0.5 (40 ч/спринт) и 100 плановыми часами в одном спринте
- **WHEN** GET /plans/{plan_id}/bus-forecast
- **THEN** спринт отмечен перегруженным (hours > limit), уровень риска не ниже medium
