# Data — правила обращения с данными

## Purpose

Однозначные правила для людей и AI-агентов: что является источником истины, что можно менять, как проверять воспроизводимость. Защищает от типичной ошибки — ручных правок производных CSV.

## Requirements

### Requirement: Источник истины

Источником истины по данным SHALL считаться файл `Датасет_с_правками_основной.xlsx`. Все содержательные изменения данных вносятся только в него (и документируются), никогда — в `dataset/*.csv`.

#### Scenario: Нужна новая колонка в данных

- **WHEN** команде нужны новые данные по задачам
- **THEN** вносятся изменения в xlsx-источник и/или `scripts/split_dataset.py`, а не в CSV напрямую

### Requirement: Происхождение CSV

Все файлы `dataset/*.csv` SHALL быть производными от xlsx исключительно скриптом `scripts/split_dataset.py`; ручное редактирование CSV запрещено.

#### Scenario: Agent правит dataset

- **GIVEN** AI-агент получил задачу, затрагивающую данные
- **WHEN** изменение касается CSV
- **THEN** агент меняет xlsx/скрипт и перегенерирует dataset, а не правит CSV

### Requirement: Воспроизводимость

Команда `uv run scripts/split_dataset.py` SHALL воспроизводить все CSV из текущего xlsx детерминированно: повторный запуск без изменения источника даёт byte-identical файлы.

#### Scenario: Повторный запуск

- **WHEN** скрипт запущен дважды без изменений
- **THEN** содержимое `dataset/*.csv` идентично

### Requirement: Актуальность README

При изменении состава или допущений датасета README SHALL обновлять раздел «Dataset» (состав таблиц, число строк, допущения) — это критерий оценивания задания.

#### Scenario: Скрипт меняет число строк

- **GIVEN** PR, меняющий `scripts/split_dataset.py`
- **THEN** в том же MR обновлены числа строк в README

### Requirement: Различия величин

При обработке данных SHALL различаться оценки в Story Points (`estimation_sp`) и трудозатраты в часах (`estimated_hh`, часы ролей); способ их связывания фиксируется в отдельном change proposal после созвона команды.

#### Scenario: Оценка и трудозатраты в одной задаче

- **GIVEN** в tasks.csv для задачи есть и `estimation_sp`, и `estimated_hh`
- **THEN** при загрузке данных обе величины сохраняются раздельно и не смешиваются при расчётах

### Requirement: Ручные записи не затираются

Последующие импорты dataset SHALL не перезатирать записи с source=manual; обновляются только записи, пришедшие из импорта.

#### Scenario: Ручной профиль и повторный импорт

- **GIVEN** engineer отредактирован вручную (source=manual)
- **WHEN** повторный импорт файла
- **THEN** профиль остаётся ручной версии; импортированные поля обновляются отдельно

### Requirement: Импорт справочников

Importer SHALL импортировать `dataset/reference_values.csv` в таблицу справочников (типа: итоги разработки, причины расхождения планов, результаты закрытия задач) при POST /data/import; повторный импорт обновляет справочники целиком (source=imported, ручных правок справочников не предусмотрено в MVP).

#### Scenario: Импорт датасета включает справочники

- **GIVEN** dataset полный (7 файлов)
- **WHEN** POST /api/v1/data/import
- **THEN** counts содержит "reference_values": 19; повторный импорт даёт тот же состав (idempotent)

### Requirement: Автодополнение задач-сирот

Если `task_role_requirements.csv` или `task_dependencies.csv` ссылаются на задачу, отсутствующую в `tasks.csv`, importer SHALL создать такую задачу со статусом `Done` (политика «упомянута — значит реализована»): сметы и зависимости остаются консистентными, задача не участвует в планировании. Ответ импорта содержит `tasks_auto_done` — число таких дополненных задач.

#### Scenario: Смета ссылается на задачу вне списка

- **GIVEN** в матрице смет есть колонка задачи SRV-XXXX, которой нет в списке задач
- **WHEN** POST /api/v1/data/import
- **THEN** задача импортирована со статусом Done и пометкой в summary; counts["tasks"] считает только задачи из списка, counts["tasks_auto_done"] = число дополненных; импорт не падает по FK

### Requirement: Импорт фактических часов по ролям

Importer SHALL импортировать `dataset/task_role_hours.csv` (фактические часы по ролям для задач, где данные есть) — витринно: карточка задачи показывает фактическую разбивку часов по ролям; данные НЕ участвуют в планировании (решение: planner не меняется).

#### Scenario: Карточка задачи с фактическими часами

- **GIVEN** задача из шести с фактическими разбивками по ролям
- **WHEN** GET /tasks/{task_id}
- **THEN** ответ содержит фактические часы по ролям (role_hours_actual); для задач без данных — поле отсутствует/пустое

# Update capability: replanning

### Requirement: Причины расхождений из справочников

При формировании объяснений расхождения планов (по факту спринта) сервис SHALL привязывать объяснение к справочной категории причин из `reference_values.csv` (импорт capability data): пользователь видит понятную формулировку причины (дата из справочника), а не только технический diff.

#### Scenario: Расхождение с понятной причиной

- **GIVEN** факт спринта показал недобор SP
- **WHEN** пользователь смотрит объяснения пересчёта
- **THEN** рядом с технической причиной указан справочный класс причины расхождения (например «недостаток времени роли», «повышение сложности задач» — формулировка из датасета)

### Requirement: Мульти-загрузка файлов последовательна

Загрузка датасета SHALL поддерживать несколько выбранных файлов: фронт ставит их в очередь последовательно (POST /data/upload per file), каждый файл — собственный job со своим статусом; confirm выполняется по каждому готовому job'у, merge по ключам сохраняется (change 025 идемпотентность).

#### Scenario: Несколько файлов подряд

- **GIVEN** выбраны 3 файла
- **WHEN** оператор запускает загрузку
- **THEN** job'ы идут последовательно, по каждому — собственный статус и toast, дубликатов нет

### Requirement: Display-имена ролей в данных и назначениях

Фактические часы ролей (`task_role_hours`) SHALL импортироваться с display-именами ролей: машинные имена колонок секции часов xlsx («разработчик_java») маппятся на display-имена из секции требований («Разработчик Java») по каноническому ключу (игнорируя пробелы, подчёркивания, скобки, слэши, регистр); колонки без маппинга сохраняются как есть. Assignments оптимизированного плана SHALL содержать display-имя роли из данных задач/инженеров, а не нормализованный ключ части solver.

#### Scenario: Импорт фактических часов

- **GIVEN** xlsx с колонкой «тестировщик_автотестирование» в секции часов и ролью «Тестировщик (Автотестирование)» в секции требований
- **WHEN** импорт датасета
- **THEN** фактические часы записаны с ролью «Тестировщик (Автотестирование)»

#### Scenario: Assignments оптимизации

- **GIVEN** часть solver с нормализованным ключом роли «тестировщик(автотестирование)»
- **WHEN** ступень 2 закрепляет часы за инженерами
- **THEN** assignment содержит role «Тестировщик (Автотестирование)»

### Requirement: Ручное добавление строк данных через UI

Вкладка «Данные» SHALL позволять добавлять строки задач, инженеров и команд через формы под соответствующими таблицами. Созданные записи помечаются `source=manual` и SHALL NOT затираться повторным импортом датасета. После добавления пользователь SHALL видеть напоминание перестроить план. Поля-привязки (команда, роль) SHOULD предлагать существующие значения (автодополнение).

#### Scenario: Добавление инженера

- **GIVEN** вкладка «Данные → Люди»
- **WHEN** заполнены engineer_id, команда, роль и нажата «Добавить»
- **THEN** инженер создан с source=manual и виден в таблице; после повторного импорта датасета запись сохраняется

#### Scenario: Добавление задачи и команды

- **GIVEN** вкладки «Данные → Задачи» и «Данные → Команды»
- **WHEN** создана команда Team-X и задача с team_id=Team-X
- **THEN** обе записи созданы с source=manual; задача участвует в следующем построении плана

### Requirement: Документированные допущения обработки данных

README SHALL содержать явный раздел допущений: правила обработки пропусков в исходных данных (InProgress без spent_time, висячие зависимости, витринные фактические часы, преобразования дат), способ соотношения Story Points и часов (независимые шкалы с обоснованием), правила приоритизации, переноса и отмены задач, допущение о назначении по роли (вместо фильтра по стеку) и ограничения реализации.

#### Scenario: Проверяющий находит допущения

- **GIVEN** внешний проверяющий (жюри) читает README
- **WHEN** ищет обоснование поведения на пробеловых данных
- **THEN** раздел «Допущения» перечисляет все правила обработки пропусков и их мотивировку; таблица «Соответствие ТЗ» связывает критерии с поведением сервиса
