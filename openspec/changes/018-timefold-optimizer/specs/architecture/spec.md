# Delta capability: architecture

## ADDED Requirements

### Requirement: Сайдкар-сервис optimizer

Платформа SHALL включать отдельный сервис `optimizer` на Java/Kotlin со Timefold Solver, доступный через docker-compose profile `optimizer` (как Redis-воркер в change 007): бэкенд общается по HTTP на внутреннем порту. Контракт solve: бэк отправляет снапшот задачи оптимизации (плановые задачи с role_hours, SP, зависимости, инженеры с командами/ставками/компетенциями, история velocity, параметры целевой функции) и получает черновик расстановки (части задач по спринтам + переносы людей) шара score за отведённый лимит времени. Отсутствие или сбой сайдкара SHALL восприниматься как штатная деградация — бэк не теряет функцию (планирование продолжается жадной стратегией), благодаря деградации change 018 planning.

#### Scenario: Solver поднят через профиль

- **GIVEN** `docker compose --profile optimizer up` поднят
- **WHEN** бэк получает `POST /plans/optimize`
- **THEN** снапшот уходит в optimizer, черновик возвращается бэку для валидации

#### Scenario: Solver не поднят — работоспособность сохраняется

- **GIVEN** сайдкар не запущен
- **WHEN** бэк стартует и пользователь запускает оптимизацию
- **THEN** работа продолжается в режиме «эвристика» (жадная стратегия 013), запуск бэка и остальной планирования не затронуты

### Requirement: Конфигурация оптимизатора

Seed, лимит времени решения, порог прироста для переноса людей и таймауты HTTP-контракта SHALL задаваться конфигурацией (env/файл), а не константажами в коде. Повторный solve с тем же seed и доменом SHALL давать одинаковую выборку черновика на стороне optimizer (детерминизм в пределах лимита времени; специфика Timefold — стресс-тест не прерванный по таймауту).

#### Scenario: Конфигурация переноса

- **GIVEN** конфиг задаёт порог прироста для переноса людей
- **WHEN** solver находит улучшение ниже порога
- **THEN** перенос не включается в черновик
