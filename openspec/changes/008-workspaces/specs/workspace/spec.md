# New capability: workspace

## Purpose

Несколько компаний (workspace-ов) в одной инсталляции (spec-only): текущее поведение (один датасет → общие таблицы) переходит в «workspace по умолчанию»; пользователь может создавать другие компании со своим датасетом, людьми, задачами, планами и настройками. Роли и доступ внутри workspace управляет владелец компании (соединяется с capability auth: роли admin/editor/reader — по workspace-ам, матрица прав — capability permissions, change 009).

## ADDED Requirements

### Requirement: Несколько компаний в одной инсталляции

Сервис SHALL поддерживать произвольное число workspace-ов; каждая сущность (задачи, инициативы, инженеры, зависимости, history velocity, планы/версии, факты, job-ы онбординга) принадлежит одному workspace. Данные разных workspace MUST быть логически изолированы (в одной БД, отдельная БД на компанию — вне рамок).

#### Scenario: Две компании

- **GIVEN** созданы workspace A и workspace B, каждый со своим датасетом
- **WHEN** пользователь в контексте A открывает задачи
- **THEN** видны только задачи компании A, задачи B не видны и не считаются в планах/метриках A

### Requirement: Создание и переключение workspace

Пользователь SHALL иметь возможность создать workspace (он становится владельцем — role admin в нём) и переключаться между своими workspace-ами; сущности API работают в выбранном контексте (заголовок/путь/параметр — решает реализация, контракт фиксируется в capability api).

#### Scenario: Переключение контекста

- **GIVEN** пользователь участник workspace A и владелец workspace B
- **WHEN** он переключается на B и вызывает GET /tasks
- **THEN** ответ содержит задачи B; повторный вызов с контекстом A — задачи A

### Requirement: Владелец управляет доступом в компании

Доступ в workspace SHALL управлять владелец этого workspace (role admin): приглашение/удаление участников и выдача ролей (editor/reader) — его действие; роль пользователя MAY различаться по workspace-ам (в B — editor, в A — reader).

#### Scenario: Разные роли в разных компаниях

- **GIVEN** пользователь X — editor в workspace A, не участник B
- **WHEN** он вызывает ручку правки в контексте B
- **THEN** 403/404 (не участник B); роль reader в A не влияет на доступ к B

### Requirement: Workspace по умолчанию

Сервис SHALL обеспечивать workspace по умолчанию: демо-датасет и существующие записи переезжают в него при миграции; запросы без указания контекста идут в default workspace — прежнее одно-датасетное поведение сохраняется.

#### Scenario: Совместимость без заголовка

- **GIVEN** фронтенд/curl-скрипты по docs/api-contract.md без workspace-контекста
- **WHEN** POST /data/import, POST /plans/generate
- **THEN** работают как сейчас, в default workspace

### Requirement: Импорт и план в контексте workspace

Ручки данных и планирования SHALL работать в контексте выбранного workspace: POST /data/import затирает и пересоздаёт данные только этого workspace (не соседних); планы/снапшот-цепочки/факты/метрики считаются и хранятся в его границах.

#### Scenario: Импорт не задевает соседей

- **GIVEN** workspace A и B, в обоих есть планы
- **WHEN** POST /data/import в контексте A
- **THEN** данные/планы B не затронуты

### Requirement: Список и CRUD workspace

API SHALL предоставлять ручки workspace-ов: список своих workspace-ов, создание (создатель — владелец), переименование (admin), удаление (admin; с подтверждением).

#### Scenario: Создание компании

- **GIVEN** аутентифицированный пользователь
- **WHEN** POST /workspaces {name}
- **THEN** 201; пользователь — владелец; новый workspace пуст (без задач/людей)

### Requirement: Привязка снапшотов и метрик к workspace

Снапшот-цепочки планов и показатели SHALL рассчитываться только внутри одного workspace: знаменатель метрик (первоначальный план) берётся из initial-плана этого же workspace.

#### Scenario: Метрики по компании

- **GIVEN** два workspace с планами
- **WHEN** GET /plans/{id}/metrics в контексте B
- **THEN** база — initial-план компании B, данные A не входят
