# Proposal: 048-honest-team-and-min-part

## Why

Два дефекта читаемости оптимизированного плана (репорт лида):
1. В таблице «Команда × спринт» фантомные перегрузы (напр. Team-L 17.5/8): solver легально назначает части задач другим командам-исполнителям, а API отдавал `team_id` **владельца задачи** — SP атрибутировались не той команде. По БД перегрузов нет.
2. «Роли по задачам» замусорены осколками по 0.2–0.9 ч: `_split_parts` делил **все** роли пропорционально — роль 1 ч в задаче на 190 ч превращалась в 3 фрагмента по 0.33 ч (20 минут).

## What Changes

- `_split_parts`: роль с долей в части < 2 ч (`MIN_ROLE_PART_HOURS`) не дробится — уходит целиком в последнюю часть; роли с долей ≥ 2 ч делятся пропорционально, как раньше
- Plan API: `team_id` элемента — команда-**исполнитель** части (из PlanItemORM); команда-владелец задачи — новое поле `owner_team_id`; `PlanItem.team_id` в доменной модели
- QA live: осколки <1 ч 18 → 8 (остаток — честные остатки свободных часов ступени 2, не pre-split); 76 частей у команд-исполнителей отображаются честно; SP по исполнителям без перегрузов
- Известное ограничение (не в scope): solver может назначить часть команде без team_history — Java teamSpCapacity inner-join не штрафует, ступень 2 откладывает такую часть («не разместилась по лимитам специалистов»); на демо-датасете у всех команд история есть

## Capabilities

### Modified Capabilities

- `planning` — минимальный размер части роли при pre-split; честная атрибуция команды-исполнителя в API плана.

## Impact
`src/services/optimizer_client.py`, `src/domain/models.py`, `src/api/routes.py`, тесты (`test_snapshot_presplit.py`, `test_optimize_jobs.py`). Фронт без изменений (LoadView/RolesView читают `team_id` — теперь честный).
