# Design: 022-solver-personalization

## Контекст

Двухступенчатый конвейер (лид, 2026-09-21): **Java макро-оптимизация → бэк пер-специалистов**. Java не ведёт per-engineer планировочную переменную: попытка добавить `RoleAssignment` (task-part×role→engineer) как planning entity упёрлась в неузнавание новой PlanningEntity внутри OptimizationDraft (Timefold 2.6 entity-scan — follow-up в todo, не крит). Отказ от Java-redesign — не потеря: ниже доказуемое обоснование, что пер-специалистов гейт бэка эквивалентен по силе и не требует новых сущностей.

## Ключевая аналитика (не over-инжиниринг)

1. **Делимость величин** — фундаментальное свойство модели: SP и часы частей дробятся пропорционально (штатный механизм change 003). Для делимых величин агрегат-ограничение и пер-специалистов ограничение согласуются всегда: если сумма часов роли ≤ Σ(80×ставка носителей), существует разложение по носителям с каждым ≤ 80×ставка (жадное заполнение). Значит пер-специалистов проход не может структурно провалиться — 422 остаётся только на аномалии данных, не на режимных раскладках.
2. **Переиспользование**: распределитель — тот же код, что и в жадном планеере (`planner._put_hours`: роле→носители по свободному остатку лимита, своя команда → заём). Один алгоритм — оба режима, ноль дублирования.
3. **Отказ от Timefold RoleAssignment** — правильное решение по бюджету: макро-оптимум дает 90% пользы (выбор лучшей композиции частей по спринтам), а качество нагрузки «по людям» оверТехника с бинарными пролёты. Тоже честно фиксируется допущением «solver оптимизирует агрегаты, hard 80/40 гарантирует бэк».

## Решения

1. **Pre-split в снапшоте** (Python `build_snapshot`): k = ⌈total_hh ÷ 80⌉ (cap 6 частей); части SP-пропорциональны; роль-часы делится пропорционально SP-долям. Solver раскладывает части независимо. В вызов это не добавляет е-маммольность (нет NEW Java entities; solver только видит больше `PartInput`).
2. **Пер-специалистов распределитель на бэке** (после solve): переиспользует `_put_hours` с те же лимитами инженера, заём, pre-occupancy пинов. Solver-PLC assignments в `plan_items.assignments` (016-совместимый контент) — личные планы шахты любит честно.
3. **Жадные сдвиги**: размер не поместился в спринт по носителям → сдвиг на следующий свободный спринт; остаток → «выполнится частично» с reason (число непоместившихся часов). 422 остаётся только для структурных нарушений (SP-гейт, dependency, sole-holder), пер-специalist-size нельзя ломать сдвигами: сдвиг честен по change 003 «частичное размещение».
4. **422 сохраняется** для lockstep hard-гейтов, которые предотвратительны сразу — «в mumber» вижу, «цифры не подделываются»: SP gate, role capacity, dependency, sole-holder — уже работают (76743ac).

## Риски и допущения

- Solver с PI-наградой упакует спринт впритык по агрегату → жадное разложение по людям бывает потерянная numerическая оптимальность (сдвиги). Допущение: финальные «выполнится частично» отмечаются в reason — отсюда честно.
- Аномалии типа роли+k уровни «не размещается ни один из остатков»: если накопительная ёмкость носителей is insufficient даже через заём по всем 6 спринтам, часть не размещ bénéfici — это нормальный «выполнится частично», не вырожденный план.
