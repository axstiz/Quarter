# Change: 022-solver-personalization (spec-only)

## Why

Solver-режим (018) оптимизирует на уровне **агрегатной ёмкости ролей**: черновик содержит часы ролей по спринтам, но не определяет конкретных носителей, а разбиение задачи между спринтами solver'ом не выполняется (в снапшоте part=1). При этом ТЗ требует лимита **специалиста** («до 80 часов при полной занятости и до 40 при 0,5»), а модель назначений 016 (task×role×engineer×sprint) в solver-версиях пуста. Решение лида (2026-09-21): двухступенчатый конвейер — **Java макро-оптимизация (агрегаты) → бэк пер-специалистов (жадное распределение, сдвиги, частичное выполнение)**; Java-redesign (planning-переменная «инженер») откладывается (follow-up в todo).

Ключевое допущение, снимающее оверинжиниринг: **часы и SP делимы** (разбиение задач — штатная механика change 003), поэтому пер-специалистов распределение структурно невозможно провалить при валидном агрегате; концентр `422` остаётся только защитой от структурных нарушений (зависимости, sole-holder).

## What Changes

1. **planning** (MODIFIED «Оптимальная расстановка…» + ADDED два требования):
   - **Pre-split частей в снапшоте**: перед отправкой в solver каждая задача разрезается на k = ⌈потребность в часах ÷ 80⌉ частей (SP и роль-часы пропорционально) — solver получает делимые единицы и может растянуть задачу по спринтам; «выполнится частично» появляется в solver-версиях честно (unassigned-части = вне квартала).
   - **Пер-специалистов распределение на бэке** (после solve): для каждого (спринт, роль) часы закрепляются за конкретными носителями жадным распределителем change 003 (лимит 80×ставка, заём при нехватке в команде, пины — pre-occupancy);assignments task×role×engineer×sprint заполняются в solver-версиях (016-совместимость: личные планы, звёздная карта, «Роли по спринтам» показывают их).
   - **Жадные сдвиги**: часть, не распределившаяся по пер-специалистов лимитам в своём спринте, двигается на следующий свободный спринт/в заём; остаток, не размещённый в квартале — «выполнится частично» (422 только на структурные нарушения —dependencies, sole-holder, ёмкость SP/ролей).
2. Двухступенчатый раздел: solver — макро-оптимум по целевой функции (инициативы → SP заказчика → PI-норма), бэк — hard-гейт per-специалистов. Java planning-переменная «инженер» — НЕ добавляется (известная проблема Timefold 2.6 entity-scan — follow-up).
3. Валидация сохраняется: бэк валидирует черновик макро-гейтами до записи версии; пер-специалистов распределитель гарантирует, что записанная версия физически исполнима 80/40.

## Non-goals

- Реализации в этом change нет (spec-only) — код отдельным change по tasks.md.
- Planning-переменная «инженер» в Timefold (Java-redesign) — follow-up, не крит для ТЗ.

## Risks

- Solver может упаковать спринт «впритык» по агрегату (PI-награда тянет к максимуму) → пер-специалистов сдвиги теряютnumerическую оптимальность качественно; зафиксировано допущение «часы/SP делимы» ( malaria-изъян редкий округления — сдвиги, не 422).
- Наличие незаполненной части роли в спринте при наличии незадействованных носителей другой роли требует честного сообщения «виртуальный держатель» в reason (не «пустую» команду).
