# Change: 021-workspaces-ui (spec-only)

## Why

Мультитенантность на бэке реализована полностью (008/009 влиты: CRUD workspace, участники, матрица прав, аудит, изоляция 403/404), но фронт о workspaces не знает: `client.ts` не шлёт `X-Workspace-Id`, `endpoints.ts` не зовёт `/workspaces/*` и `/permissions/*` — фронт заперт в default workspace, админ-механики 009 недоступны из интерфейса. Решение лида (2026-09-21): рабочий контекст оформляется как **onboarding-экран** — первый экран после входа: выбор рабочего пространства или создание нового. Семантика: **1 датасет ≈ 1 workspace** — в существующий можно до­полнять данные новыми импортами (бэк уже обновляет imported, ручные записи сохраняет), а «чистый лист» — это создание нового workspace ( файл или демо-датасет одной кнопкой).

## What Changes

1. **workspace-контекст на клиенте** (MODIFIED «Создание и переключение workspace»): активный workspace хранится в сессии; заголовок `X-Workspace-Id` на все `/api/v1`-запросы (для default — без заголовка, что сохраняет контракт «Workspace по умолчанию»); смена workspace сбрасывает `?plan=`/`?task=`.
2. **Экран выбора рабочего пространства** (ADDED): первый экран после входа, показывается **всегда** — даже когда workspace один (default). Список «моих» пространств (название, роль, владелец), активный помечен; «Создать рабочее пространство» → создатель становится админом, попадает в пустой контекст («чистый лист») — где предлагает загрузить датасет: файл или **демо-датасет одной кнопкой** (переиспользование влитой кнопки импорта демо-датасета).
3. **Импорт датасета в существующий workspace** (ADDED): файл можно загрузить в текущий контекст поверх имеющихся данных; в форме — явная подпись последствий («импортированные записи будут обновлены, ручные останутся»); после импорта — баннер «данные изменились — постройте план заново» (как в 019).
4. **Управление доступом из UI** (MODIFIED «Владелец управляет доступом» + ADDED): экран участников — список с ролями, приглашение по email (editor/reader), удаление; всё штатными бэк-ручками 008.
5. **Матрица прав и журнал аудита** (ADDED): admin-экраны поверх `GET /permissions/matrix`, `PATCH /permissions/roles/{role}`, `GET /permissions/audit` (009); перед отключением admin-целевых действий — предупреждение об инварианте.
6. Изоляция (008): не-участник — 404/403 без раскрытия содержимого; UI обрабатывает тостом и возвратом на экран выбора.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `workspace`: ADDED «Экран выбора рабочего пространства», «Импорт датасета в существующий workspace», «Матрица прав на экране», «Журнал аудита»; MODIFIED «Создание и переключение workspace» (клиентский контекст + reset URL-state), MODIFIED «Владелец управляет доступом» (управление через UI-экран).
- `ui`: онбординг-экран, смена компании (топбар), участники, матрица, аудит, edge-404/403.

## Non-goals

- Реализации в этом change нет (spec-only) — исполняет фронтендер (бэк-ручки 005/008/009 влиты).
- Email-рассылка приглашений / link-based приглашения — вне рамок (приглашение работает по email существующего пользователя).
- Массовые операции над участниками (bulk invite).
- Перенос старых данных между workspace'ами вручную (это обязанность импорта, не UI).

## Risks

- Заголовко-зависимость: если клиент не шлёт `X-Workspace-Id` при не-default, запрос سرётся в default — mitigation: заголовок выставляется обвязкой клиента один раз, а не в каждой ручке фронта.
- Матрица прав: admin может отключить своё право на управление; бэк сохраняет инвариант 009 (admin сохраняется у крит issuer целевых действий) — UI показывает предупреждение перед опасной правкой.
- Мок-бэкенд не имеет workspace-ручек — во включение tasks: имитация 008/009 ручек в мока, иначе dev-режим и сверка мока ↔ бэка разъезжаются.
