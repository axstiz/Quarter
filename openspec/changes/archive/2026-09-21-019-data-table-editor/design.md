# Design: 019-data-table-editor

## Контекст

Бэк уже отдаёт CRUD по всем сущностям (`POST/PUT/DELETE /tasks`, `/engineers`, `/teams`, `/dependencies` — openapi.json) — редактор данных не требует нового API-хода, требуются: спецификация поведения фронта (in-place правки, валидация, source=manual, баннер пересборки) и одна реальная интеграция (role_hours обновление задачи; проверка правки ключей).

## Решения

1. **Типизированные субтаблицы**, а не свободная сетка: каждая колонка привязана к полю модели; правка = PUT существующей записи, не диапазонами: это сохраняет контракт и валидацию уже существующими механизмами pydantic.
2. **role_hours как detail**: часы по ролям хранятся long-форматом (task_role_requirements) — фронт редактирует их набором PUT по записи задачи (поле role_hours передаётся целиком) с после пересборкой больших значений; нулевые строки отбрасываются по правилам импорта.
3. **Правка ключей через бэк-защиту**: task_id/engineer_id фигурирует в зависимостях и планах; PUT ключа при наличии ссылок отклоняется 409 с подсказкой (сначала удалить зависимости). Переименование ключа — не требование.
4. **Связка с планом**: никакой инвалидации существующего плана — баннер с метаданом «данные изменились» (стимул build; хранится во внешней характеристике состояния «данные mapper момент» — сравнение отметок изменения данных по времени с созданием активной версии).
5. **Роли в редакторе**: справочник ролей company-wide собирается из существующих задач/инженеров; роль без носителей в detail показывается маркером (согласуется с правилами change 003).
6. **Бэксескasionная честность**: правки публикуют source=manual (требование data), повторный импорт не затирает ручные записи — пайплайн импорта обязан должен бы защите вручную-правки.
7. **Моки**: фронт-мок поддерживает правки поверх in-memory состояния (сброс `?mock-reset`) — dev-сценарий воспроизводим без бэка.

## Риски

- Конкурентные правки несколькими пользователями: 409 с данными другой стороны (как/versioning change 005); не блокирующее MVP-ограничение.
- Объём UI заметен; реализация декомпозируется vào tasks (модель таблицы — переиспользуемые компоненты таблиц из PeopleTab).
