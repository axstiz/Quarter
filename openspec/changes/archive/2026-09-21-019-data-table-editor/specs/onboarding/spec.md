# Delta capability: onboarding

## ADDED Requirements

### Requirement: Правки данных вручную

Загруженные данные SHALL быть доступны для ручного редактирования через CRUD (задачи, инженеры, команды, зависимости): правка любых полей кроме идентификаторов, создание и удаление записей; недостающие данные дозаполняются руками без повторной загрузки файла. Ручная правка записи MUST переводить её в source=manual и защищать от затирания повторными импортами (capability data). Часы потребности ролей задачи (role_hours) SHALL редактироваться в связке с задачей: добавление роли с часами, правка значений, удаление роли; роли без носителей и носители в других командах видны при редактировании.

#### Scenario: Дополнение недостающего

- **GIVEN** после импорта у инженера отсутствуют компетенции, а у задачи отсутствуют часы по роли «Тестировщик»
- **WHEN** пользователь редактирует таблицу данных
- **THEN** он добавляет компетенции инженера и частоту оплаты в часах данные в записи задачи, записи сохраняются и доступны planner'у при следующей генерации

#### Scenario: Удалённая запись не ломает историю

- **GIVEN** задача удалена из таблицы данных
- **WHEN** пользователь открывает старую версию плана
- **THEN** история планов остаётся неизменной; задача продолжает отображаться в её (уже past) версиях

### Requirement: Валидация правок

Сервис SHALL валидировать правки типизированно и возвращать осмысленные ошибки: числовые поля (SP, часы, лимиты) — неотрицательные и разумного диапазона; capacity_rate — из допустимых значений (0,5 / 1,0); дубли ключей — 409/422 с текстом; ссылочные поля (команда задачи, инженер в команде, роли зависимостей) — только на существующие записи. Висячие зависимости (ссылка на несуществующую задачу) допускаются, но MUST быть помечены как «планировщик проигнорирует». Ошибка валидации MUST отображаться у конкретной ячейки/строки редактора, а не только в общем ответе.

#### Scenario: Отрицательные часы отклоняются

- **GIVEN** пользователь вводит в ячейку «оценка, ч» значение −5
- **WHEN** сохраняется ячейка
- **THEN** изменение отклоняется с сообщением у ячейки и данные не меняются

#### Scenario: Висячая зависимость помечается

- **GIVEN** пользователь создаёт зависимость на несуществующий task_id
- **WHEN** зависимость сохранена
- **THEN** строка зависимости помечена предупреждением «планировщик проигнорирует: задача не найдена»

### Requirement: Правки не нарушают существующие планы

Правки данных SHALL применяться к будущим генерациям планов. Существующие версии планов MUST не переписываться. При изменении данных с momenta активной версии плана UI MUST показать постоянный баннер «данные изменились — постройте план заново» с кнопкой перехода к генерации (human-in-loop). Повторная генерация создаёт обычную новую версию в цепочке.

#### Scenario: Баннер после правки

- **GIVEN** существует активный план и пользователь поправил estimate задачи
- **WHEN** он возвращается на страницу плана
- **THEN** видит баннер «данные изменились — постройте план заново» с кнопкой

#### Scenario: Чтение plan версий при правках

- **GIVEN** пользователь правит данные
- **WHEN** открывает первоначальный план (initial)
- **THEN** тот показывает исходные значения (снимок), текущая версия — свою раскладку; правки данных не вносят в уже существующие версии
