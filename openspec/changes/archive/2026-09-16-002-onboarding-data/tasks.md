# Change: 002-onboarding-data

## Why

Демо-сценарий начинается с «загрузите свой файл». Сейчас сервис умеет импортировать только точно `dataset/*.csv` (постраничный формат организаторов). Реальные команды придут со своими xlsx/csv/json в неизвестной разметке (см. разбор в product-plan §"Загрузка из канбан-трекеров": кастомные заголовки, локаль, Excel-serial даты). Плюс: в трекер-экспортах нет профилей людей, ролей-часов и зависимостей — их человек должен доборить руками. Без этого planner по ТЗ не работает.

## What changes

1. **Загрузка файлов** xlsx/csv/json → парсинг → промежуточные таблицы (uploads job state).
2. **Шаблонные маппинги** (детерминированные): формат организаторов (наш датасет) + типовые заголовки Jira-подобных экспортов.
3. **LLM-пайплайн нормализации** ( LangGraph + GigaChat от Сбера ): когда шаблон не совпал — агент сопоставляет колонки, задаёт уточняющие вопросы одним батчем, отвечает дифф-превью; ответ валидируется pydantic-схемой; **без ключа GigaChat — деградация в шаблонный режим + ручные вопросы** (нет hard-fail).
4. **Подтверждение человеком**: превью маппинга/диффа → confirm → импорт (merge; ручные записи не затираются).
5. **Полный CRUD** (команды/ люди /проекты-initiative/задачи/зависимости/история), поля опциональны; недостающее в данных дозаполняется формами; записи с source=manual не перезатираются следующим импортом.
6. Спек-дельта: новая capability `onboarding`; updates `data` (ручные данные маркируются) и `api` (новые ручки).

## Non-goals

- Коннекторы к живым трекерам (Jira REST и т.п.) — после демо.
- AI-советник приоритетов (LangGraph пайплайн `advisor`) — после change 003; здесь каркас `src/ai/` делаем сразу.
- Доступный переработка PDF-онбординга.

## Risks

- LLM-вывод ненадёжен → обязательно валидация схемой, человек подтверждает; «плохой» ответ → вопрос пользователю.
- GigaChat ключ у жюри недоступен → демо всегда может идти по шаблонному маппингу формата организаторов (наш xlsx).
- Полный CRUD расширяет поверхность → все поля optional, валидация консервативная.
