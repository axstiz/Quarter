# New capability: onboarding

## Purpose

Онбординг данных: пользователь загружает файл (xlsx/csv/json) в произвольном близком к трекеру формате; сервис нормализует (шаблонным маппингом или через LangGraph+GigaChat агента), показывает превью, задаёт уточняющие вопросы, после подтверждения импортирует. Недостающее дозаполняется вручную через формы (полный CRUD, поля опциональны).

## ADDED Requirements

### Requirement: Загрузка произвольного файла

Сервис SHALL принимать xlsx, csv, json и показывать превью сопоставления колонок с сущностями сервиса до импорта.

#### Scenario: Загрузка файла

- **WHEN** POST /data/upload с файлом
- **THEN** создается job с превью колонок и предложенным маппингом

### Requirement: Шаблонные маппинги

Сервис SHALL содержать детерминированные шаблонные маппинги: формат организаторов (наш датасет) и типовые заголовки Jira-подобных экспортов.

#### Scenario: Датасет организаторов

- **GIVEN** файл формата организаторов
- **WHEN** пайплайн разбора
- **THEN** колонки сопоставляются без LLM и без ручных вопросов

### Requirement: LLM-нормализация незнакомого формата

Когда шаблонный маппинг не однозначен, сервис SHALL использовать LLM-пайплайн (LangGraph + GigaChat): предложить сопоставление, собрать уточняющие вопросы одним батчем, ответить на них повторным запуском; ответ MUST валидируется pydantic-схемой.

#### Scenario: Незнакомый заголовок

- **GIVEN** колонка 'Сп' неизвестного значения
- **WHEN** пайплайн наткнулся на неоднозначность
- **THEN** пользователю задаётся вопрос (например 'Story Points или часы?') и после ответа маппинг уточняется

#### Scenario: Ответ LLM не валиден

- **GIVEN** ответ LLM не проходит pydantic-валидацию
- **THEN** пайплайн повторяет запрос (loop), затем переходит к ручным вопросам

### Requirement: Деградация без LLM

Без доступного ключа GigaChat пайплайн SHALL снижаться до шаблонных маппингов + ручных вопросов пользователя (нет hard-fail).

#### Scenario: Нет интернета на демо

- **GIVEN** ключ GigaChat не задан
- **WHEN** загружается файл
- **THEN** работа идет по шаблону и ручным сопоставлением (без LLM-вызовов)

### Requirement: приоритет пользовательского решения

Решение о загрузке и сопоставлениях MUST приниматься пользователем; агент только предлагает.

#### Scenario: Подтверждение перед импортом

- **GIVEN** нормализация завершилась
- **WHEN** пользователь смотрит превью
- **THEN** данные не попадают в БД без его подтверждения

### Requirement: Полный CRUD с опциональными полями

сервис MUST предоставлять CRUD по сущностям команда/проект/задача/человек/зависимости: все поля кроме идентификаторов - опциональные; недостающие данные заполняются вручную.

#### Scenario: Добор форм

- **GIVEN** из файла не нашлись професси людей
- **WHEN** пользователь заполняет формы
- **THEN** записи сохраняются и доступны planner'у

### Requirement: Маркировка источник данных

Каждая запись БД МОЖЕТ маркироваться источником (imported/manual); последующие импорты не затирают ручные записи (см. capability data).

#### Scenario: Повторный импорт после ручного правки

- **GIVEN** пользователь вручную отредактировал engineer профиль
- **WHEN** повторный импорт того же файла
- **THEN** ручная запись (manual) сохраняется, импортированная обновляется
