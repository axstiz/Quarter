## Context

Планировщик в терминах «часов ролей»: численно инженеры расходуются (`_put_hours` — распределение часов по носителям), но назначения не сохраняются и не выводятся. Человеко-модель — целевая архитектура (лид, 2026-09-17): «расставлять задачи по спринтам, по людям и по порядку для каждого человека». Связи: 013 (стратегия/скоринг) — ось задач; 015 (советник) — поверх; 014 — bus-области по командам.

## Goals / Non-Goals

**Goals:** назначения task × role × engineer × sprint; личная очередь работ каждого человека; pin (закрепление как жёсткий якорь) с явными конфликтами; backward compatibility (назначения добавляются, порядок планирования по умолчанию не ломается)

**Non-Goals:** автосдвиг закреплённого; смена данных о людях (ставки/команды); реализация в этом change

## Decisions

- **Ориентировано по людям (pre-occupancy)**: pin-резервирование ёмкости выполняется до жадного планирования остальных — человеко-якоря определяют skeleton; это же даёт «отталкивание от загруженности» без изменения гейтов (80/40 по-прежнему)
- **Двухуровневый pin**: (1) назначение (задача–человек–спринт); (2) позиция в личном порядке. Одноуровневого «pin только по спринту» недостаточно — человеко-модель требует фиксации, «кто делает», иначе заём двигает исполнителя
- **Конфликты решаются человеком, не алгоритмом**: молчаливое отключение пина запрещено спекой; варианты развязки (передвинуть/снять/сдвинуть зависимую) выдаются вместе с предупреждением
- **Разбиение задач по людям**: PDF-пример (DB-202, 130 ч одной роли при 80 ч) обрабатывается «тот же человек, спринт 1 → 2» — продолжение частей одной задачи сохраняет исполнителя, если его лимит позволяет иначе — другой носитель роли с пометкой в reason
- **Советы (015) против пинов**: фильтрация по списку pin из версии плана, чтобы совет не предлагать сдвиг закреплённого

## Risks / Trade-offs

- Хранение назначений компактно (in JSON plan item) vs отдельная таблица assignments — выбор за реализацией; спека требует только восстановления назначений из ответа плана
- Появление двух режимов (role-суммарное планирование vs человеко-планирование) — спека выбирает единый people-вывод: новые версии плана получают заполненные назначения (старые версии плана сохраняются исторически в прежнем виде; новые — с назначениями)
