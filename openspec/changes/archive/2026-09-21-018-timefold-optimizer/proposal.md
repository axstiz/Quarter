# Change: 018-timefold-optimizer (spec-only)

## Why

Текущий планировщик расставляет задачи по детерминированным правилам (velocity × 0,8, лимиты ролей, зависимости), но не ищет расстановку, максимизирующую показатели из ТЗ: процент выполнения квартального плана (закрытые инициативы) и предсказуемость плана (норма PI 80–100 % из PDF Демо_онбординга). Решение лида (2026-09-18): добавить режим оптимальной расстановки на **Timefold Solver** — запускается по кнопке, результат применяется **сразу** как новая версия плана (включая предложения переноса людей между командами); полная история версий сохраняется, дефолтная генерация и жадная стратегия 013 не меняются (ноль breaking change).

## What Changes

1. **planning** (ADDED):
   - режим «оптимальная расстановка»: пользователь запускает оптимизацию (`POST /plans/optimize`), solver расставляет задачи (части задач) по 6 спринтам; результат немедленно создаёт новую версию плана без промежуточного черновика и подтверждения;
   - переносы людей между командами — крайняя мера («накрайняк»): solver применяет их только если прирост целевой функции превышает порог; носителей единственных компетенций (Bus Factor = 1) не трогает;
   - жёсткие (hard) ограничения повторяют правила change 003: ёмкость velocity × 0,8; 80 ч / 40 ч по ставкам и кросс-командный заём; потребность в ролях (role_hours); зависимости задач; статусы Done/InProgress (остаток часов); виртуальные держатели ролей без носителей; разбиение задач между спринтами разрешено;
   - целевая функция: максимум закрытых инициатив квартала → SP стратегических задач заказчика (`planned_in_sprint=Да`) → предсказуемость PI в норме; минимизация незакрытых человеко-часов ролей, переноса людей, нарушения порядка human priority;
   - бэк валидирует черновик solver'а своими hard-правилами ДО записи версии: нарушение → 422, существующий план не меняется;
   - каждая версия хранит solver-причины (какие задачи куда и почему, score-обоснование) и пометку источника версии (facts / recompute / optimization); история версий полная и неизменяемая, откаты возможны через селектор версий.
2. **api** (ADDED): `POST /plans/optimize` → персистентный job (по образцу change 007: queued → solving → ready | failed с причиной); успешный job создаёт план-версию сразу; `GET /plans/optimize/{job_id}` — состояние, метрики до/после (`optimization-report` по образцу 013) и итоговый plan_id; права reader — просмотр, editor — запуск, admin — запуск и перенос людей; 409 при параллельной незавершённой оптимизации, 422 при невалидном черновике.
3. **architecture** (ADDED): solver-сайдкар `optimizer` (Java/Kotlin + Timefold Solver) с docker-compose profile `optimizer`; HTTP-контракт solve (снапшот домена → расстановка → черновик); seed и лимиты времени в конфиге; сбой/отсутствие сайдкара → деградация на детерминированную жадную метрическую стратегию 013 (`mode: heuristic`), UI отображает режим.
4. Совместимость: дефолт `POST /plans/generate` и вкладка «Приоритеты» не меняются; метрики по-прежнему сравниваются с initial-планом.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `planning`: режим оптимальной расстановки — hard/soft ограничения, целевая функция по метрикам ТЗ, немедленное применение по кнопке, гарантированное сохранение истории версий, деградация.
- `api`: оптимизационные job-ручки (запуск/статус/результат), права ролей, 409/422-семантика.
- `architecture`: сайдкар optimizer (docker profile), solve-контракт, конфигурация, деградация.

## Non-goals

- Реализации в этом change нет (spec-only) — код отдельным change по tasks.md.
- Замена дефолтной генерации и правил human seed: оптимизация — отдельная кнопка, не переписывает поле priority задач.
- Подтверждение черновика человеком перед версионированием — убрано по решению лида: применяется сразу, история = способ отката.
- Пересчёт SP↔часы коэффициентом: гейты остаются независимыми (change 003, допущение №3).

## Risks

- Недетерминизм solver между прогонами: mitigation — фиксированный seed/лимиты времени в конфиге, строгая пост-валидация черновика до записи версии, причины в версии делают любой принятый результат объяснимым.
- Solver может «оптимизировать знаменатель» (включать в план только лёгкие инициативы): состав включаемых задач определяется только ёмкостью и зависимостями — целевая функция влияет на порядок и распределение, не на состав.
- Перенос людей — влияние на Bus Factor/звёздную карту: hard-запрет на перемещение единственных носителей компетенций; перенос виден в отчёте оптимизации и в профилях star-map (согласуется со spec star-map).
- Двойной счёт SP/часов — запрещён: SP-гейт (velocity × 0,8) и часовой гейт (лимиты ставок) независимы.
