## Context

`compute_bus_factor` уже возвращает items двух областей (company + team по каждой из 6 команд) — пер-командные данные есть, но: не спечены как требование, ручка не фильтруется, фронтенд режет сам; после 008-workspaces «company»-область двусмысленна. Готовый для фронта фильтр убирает лишний слой.

## Goals / Non-Goals

**Goals:**
- Явные, объяснимые области: workspace (бывший company) → team, изоляция расчёта по границам
- Удобный доступ: фильтр на существующей ручке + читательская ручка страницы команды
- Методика Bus Factor не меняется (утверждена)

**Non-Goals:**
- Реализация в этом change (spec-only; team-фильтры MAY реюкать до 008)
- Методика/пороги (уже утверждены), новые области расчёта

## Decisions

- **Фильтрация на уровне items, а не пересчёт**: расчёт уже вычисляет все области; фильтр = выборка items + 404-валидация area; дешёво и идентично с полным ответом (один и тот же расчёт, разные «окна»)
- **Ручка команды — тонкая обёртка** над filtered расчётом (одинаковый код-путь с фильтром; тест равенства ответов)
- **Workspace-семантика через переименование понятия, не кода**: в спеке bus-factor область `company` связывается с workspace текстом (готовность к 008; code rename — за реализацией 008, чтобы не ломать контракт уже отдаваемого фронта)
- **iOS/навыки… ничего не меняем**:разбор skills_declared остаётся для team-области одинаковым с company

## Risks / Trade-offs

- Реализация фильтра до 008 работает на default workspace — спека прямо сие фиксирует (сценарий «Дефолт без workspace»), это не мешает старту на демо-датасете
