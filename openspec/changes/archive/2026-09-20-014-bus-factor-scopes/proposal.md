# Change: 014-bus-factor-scopes (spec-only)

## Why

Требование ТЗ — «объясните методику расчёта и область, для которой рассчитывается показатель»: расчёт Bus Factor должен существовать **по каждой команде отдельно** (сейчас team-scope — деталь формата ответа `items`, а не первоклассное требование) и **в границах workspace** (после change 008 «company»-область без привязки к workspace становится двусмысленной). PDF (KPI №3) требует оценки «Bus Factor > 1 для всех критических технологий» на уровне, где работает бэклог — то есть по командам. Решение лида (2026-09-17): фильтр области на существующей ручке + читательская ручка у команды; формат spec-only (зависимость от 008-workspaces).

## What changes

1. **bus-factor** (ADDED «Расчёт по каждой команде»): для каждой команды — собственный набор факторов по ролям и навыкам как первоклассная область расчёта; границы команд не пересекаются; 0.5-ставочник — носитель в обеих.
2. **bus-factor** (ADDED «Расчёт в границах workspace»): люди разных workspace-ов не смешиваются; после реализации 008 термин `company` в существующей спеке читается как «текущий workspace»; дефолт (один workspace) — прежнее поведение.
3. **api** (ADDED): `GET /bus-factor?scope_type=…&scope_id=…` — фильтр области в ответе (404 на неизвестную область); `GET /teams/{team_id}/bus-factor` — читальня для страницы команды (расчёт, фиксированный этой командой, с методикой).

## Non-goals

- Реализации в этом change нет (spec-only; реализация возможна и до 008 для team-фильтров, workspace-часть — только после 008).
- Изменение методики Bus Factor (число носителей в области, риск при ≤1) — она уже утверждена лидом и зафиксирована.
- Новые области (роль-как-область, проект) — не в этом change.

## Risks

- Зависимость от 008-workspaces: workspace-часть применима только после его реализации; до этого фильтры team работают на единственном (default) workspace.
- Двойной вход (фильтр + ручка команды) должен возвращать одинаковые данные — тест сравнения при реализации.
