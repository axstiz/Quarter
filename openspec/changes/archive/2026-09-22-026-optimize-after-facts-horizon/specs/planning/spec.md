# Update capability: planning

## MODIFIED Requirements

### Requirement: Оптимальная расстановка запускается по кнопке и применяется сразу

Сервис SHALL предоставлять режим оптимальной расстановки задач по спринтам в **две ступени**: (1) макро-оптимизация в solver'е — расстановка частей задач по спринтам и командам против агрегатной ёмкости ролей и SP-гейта (velocity × 0,8) с целевой функцией по метрикам ТЗ; (2) пер-специалистов распределение на бэкенде — часы ролей каждой размещённой части закрепляются за конкретных носителей жадным распределителем change 003 (лимит 80 ч × ставка, заём из других команд по остатку лимитов, пины — pre-occupancy), после чего часть, не распределившаяся по пер-специалистов лимитам, SHALL сдвигаться на следующий свободный спринт/в заём, а остаток — помечаться «выполнится частично». Пользователь запускает оптимизацию явным действием, по завершении расчёта сервис MUST создать новую версию плана без промежуточного черновика; существующие версии MUST оставаться неизменными (полная история версий открывается в любой момент); версия, созданная оптимизацией, MUST содержать reason с обоснованием целевой функции и пометку источника «оптимизация». 422 при записи версии SHALL применяться только к структурным нарушениям (зависимости, sole-holder, SP-гейт, ёмкость ролей).

Снапшот и эвристический черновик MUST строиться от контекста текущей версии плана: задачи, выполненные по фактам спринтов (completed_task_ids) или имеющие статус Done в данных, SHALL исключаться из расстановки; горизонт расстановки SHALL начинаться со спринта, следующего за последним пересчитанным (`recomputed_after_sprint` исходной версии) — части задач MUST NOT размещаться в прошедших спринтах. При отсутствии фактов поведение не меняется (горизонт 1..6, полный набор не-Done задач).

#### Scenario: Оптимизация создаёт новую версию

- **GIVEN** существует план на 6 спринтов
- **WHEN** пользователь запускает оптимизацию и solver завершает расчёт успешно
- **THEN** создаётся новая версия плана с заполненными assignments (инженеры на ролях), UI переключается на неё, предыдущие версии открыты через селектор

#### Scenario: Повторная оптимизация не перезаписывает историю

- **GIVEN** было две успешные оптимизации подряд
- **THEN** история содержит обе новые версии (parent_plan_id прежней), обе открываются

#### Scenario: Пер-специалистов сдвиг части

- **GIVEN** solver поместил часть задачи в спринт 3, но носители роли в спринте 3 загружены (80/40 исчерпаны)
- **WHEN** бэк выполняет пер-специалистов распределение
- **THEN** часть сдвигается на следующий свободный спринт/в заём; если конец квартала — «выполнится частично», версия не отклоняется

#### Scenario: Оптимизация после факта не переигрывает выполненное

- **GIVEN** загружен факт спринта 1 с completed_task_ids, план пересчитан
- **WHEN** пользователь запускает оптимизацию пересчитанной версии
- **THEN** выполненные по факту задачи отсутствуют в новой версии (не planned), ни один item не находится в спринтах ≤ 1

#### Scenario: Оптимизация без фактов не меняется

- **GIVEN** факты не загружены
- **WHEN** оптимизация запущена
- **THEN** расстановка доступна по всем спринтам 1..6, все не-Done задачи участвуют
