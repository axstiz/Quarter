## Why

Импорт датасета во второй workspace не создаёт задачи: `tasks.task_id` — глобальный первичный ключ. Пайплайн загрузки файла (`_upsert_task`) ищет запись только по `task_id` без учёта workspace и молча обновляет строки чужого workspace (`default`); демо-импорт (`import_dataset`) падает с IntegrityError по PK. В обоих случаях «Построить план» в новом workspace падает с «нет данных в базе». Спека workspace уже требует логической изоляции данных — реализация ей противоречит.

## What Changes

- **BREAKING (схема БД)**: первичный ключ `tasks` → составной `(workspace_id, task_id)`; `teams` → `(workspace_id, team_id)`. Внешний ключ `task_role_requirements.task_id` → составной `(workspace_id, task_id)`.
- Lookup'ы в пайплайне импорта (`_upsert_task`, зависимости, инженеры) фильтруют по `workspace_id` — повторный импорт того же датасета в другой workspace создаёт независимые копии, а не затирает чужие.
- Миграция для существующих развёртываний: пересоздание схемы (`docker compose down -v`) + повторный импорт демо-датасета; alembic в проекте нет, обратная совместимость схемы не требуется (демо-проект).

### Modified Capabilities

- `workspace`: добавляется требование, что идентичность сущностей датасета (задачи, команды) определяется парой `(workspace_id, бизнес-id)` — один и тот же `task_id` может существовать в нескольких workspace независимо.

## Impact

- Код: `src/db/models.py` (PK/FK), `src/db/staging.py` (lookup'ы upsert), `src/db/importer.py` (проверка демо-импорта), точечно `src/api/routes.py`/`src/api/crud.py`, если найдутся обращения к задачам без workspace-фильтра.
- API: контракты не меняются; меняется поведение импорта в не-default workspace (теперь данные действительно создаются).
- Данные: существующие БД требуют пересоздания (`down -v` + импорт).
- Тесты: новые на изоляцию импорта двух workspace с одинаковым датасетом; регресс всего набора.
