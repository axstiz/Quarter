Все задачи `- [ ]`: change spec-only, реализация отдельным change по этим пунктам.

## 1. Стратегия планирования (planning)

- [ ] 1.1 PlanORM: поле strategy ("priority"|"metrics", дефолт priority); хранение в версии плана
- [ ] 1.2 POST /plans/generate принимает опциональный strategy (422 на неизвестные значения)
- [ ] 1.3 Скоринг задач при strategy=metrics: (1) флаг заказчика planned_in_sprint=Да первыми; (2) дефицит закрытия инициатив (parent_id, остаток объёма vs ёмкость квартала, зависимости); (3) priority — тайбрейкер; детерминизм (проверка: повторный прогон = тот же план)
- [ ] 1.4 Reason плановых задач отмечает применение стратегии (например «по метрической стратегии: закрывает инициативу BR-151»)
- [ ] 1.5 Тест сравнения стратегий: демо-датасет, priority vs metrics — различие порядка/состава видно, оба плана валидны по SP- и role-гейтам

## 2. Отчёты (api)

- [ ] 2.1 GET /plans/{id}/optimization-report: сравнение с priority-эталоном (повторный прогон planner с приоритетом в памяти): KPI №1 прогноз, число закрываемых инициатив, отличия состава, продажа target_band
- [ ] 2.2 GET /plans/{id}/staffing-suggestions: симуляции переноса долей ставок (только между командами присутствия инженера), эффект на план/KPI, фильтр Bus Factor ≤ 1, пустой список при отсутствии безопасных вариантов
- [ ] 2.3 Согласование с 010: optimization-report не подменяет знаменатель initial-плана

## 3. Нормы KPI (metrics)

- [ ] 3.1 Константы норм: PI Predictability {80, 100}, Say/Do {90, 105}
- [ ] 3.2 MetricsReport: target_band + within_norm для quarter и sprint (факт и прогноз)
- [ ] 3.3 Тесты: 87% в норме, 72% Say/Do вне нормы, прогноз-пометка сохраняется
