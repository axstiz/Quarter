# Change: 016-person-planner (spec-only)

## Why

Планировщик сейчас работает в терминах часов ролей: задача требует «Роль → часы», planner расходует ёмкость носителей абстрактно — конкретные люди и их порядок не фиксируются и не выводятся. По ТЗ/PDF цель — «распределить людей и задачи для них так, чтобы решить как можно больше» (пример PDF: один senior .NET 80 ч/спринт растягивает DB-202 минимум на 2 спринта — рассуждение в терминах людей). Реальные цифры датасета (50 комбинаций «команда, роль» без носителя в своей команде, 9 ролей без носителей вообще) делают человеко-центричное распределение ключевой витриной. Решение лида (2026-09-17): planner должен отталкиваться от людей и их загруженности — расставлять задачи **по спринтам, по людям и по порядку для каждого человека**; плюс закрепления (pin) — жёсткие якоря, которые авто-пересчёт не трогает, остальные планируются вокруг.

## What changes

1. **planning** (ADDED «Назначение по людям»): каждая запланированная задача несёт назначения конкретных инженеров к ролям задачи (`task × role × engineer × sprint`); человеком-ёмкость 80/40 расходуется его назначениями; кросс-командный заём сохраняется (назначение инженера другой команды — с учётом суммарной ставки за спринт); отчётность назначений — в ответе плана.
2. **planning** (ADDED «Персональный порядок работ»): у каждого инженера — упорядоченный личный план по спринтам; незакреплённый порядок определяется планировщиком (зависимости, стратегия 013); человек MAY закрепить порядок (или отдельные позиции) — пересчёт сохраняет закреплённое.
3. **planning** (ADDED «Закреплённые назначения (pin)»): жёсткое закрепление (задача–человек–спринт и/или позиция в личном порядке) — pre-occupancy ёмкости до планирования остальных; конфликты (pin не влезает, зависимость нарушена закреплённым) — явные предупреждения и подтверждение развязки человеком, никакого молчаливого сдвига; pin выше приоритета и стратегии 013.
4. **api** (ADDED): `GET /plans/{plan_id}/people/{engineer_id}` — личный план (очередь по спринтам с порядком); назначения в ответе `GET /plans/{plan_id}`; ручки pin/unpin и фиксации порядка.
5. **star-map** (ADDED): личная карточка плана инженера — назначения, загрузка по спринтам (стык «возможности и загруженность»).
6. **api** (ADDED, cross-link 015): советы AI-советника не затрагивают пином-закреплённые позиции.

## Non-goals

- Реализации в этом change нет (spec-only) — это переход planner на человеко-модель, отдельный существенный change по tasks.md.
- Автопереприсвоение закреплённого при конфликте (только предупреждение и решение человека).
- Персональные ставки/команды инженеров — прежние (rights данных не меняются; change 008 кладёт это в workspace позже).

## Risks

- Смена модели planner глубже, чем 013 (сортировка): реализация — сами большой change; ограничение backward compatibility — дефолтное поведение и тесты сохраняются (назначения добавляются, «как планировалось ранее» не ломается).
- Появляются перекрёстные конфликты pin ↔ зависимости ↔ ёмкость: спека требует явных предупреждений и отсутствия тихих сдвигов — риск реализации в «мёртвой петле» разрешается документированием порядка резолва (см. design).
