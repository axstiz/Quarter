## 1. Обзор

**Продукт.** Сервис, помогающий составить выполнимый квартальный план разработки (6 спринтов × 2 недели = 12 недель), пересчитывать его по фактическим результатам спринтов и видеть риски загрузки и компетенций команд (звёздная карта + Bus Factor).

**Кому нужно.** Тимлидам команд разработки, ресурсным менеджерам, ИТ-директору.

**Почему.** Суммарной оценки задач недостаточно: выполнимость зависит от производительности команды, рабочего времени специалистов, потребности в разных ролях и связей между задачами. Отставание в одном спринте двигает цепочку зависимых работ и ставит под угрозу квартальные цели.

**Целевые критерии (вес из ТЗ):**
| Критерий | Вес |
|---|---|
| Корректность квартального плана (ресурс, трудозатраты, зависимости) | 30 |
| Качество пересчёта и предупреждений о рисках | 20 |
| Полнота звёздной карты и корректность Bus Factor | 15 |
| Понятность причин включения/переноса/отмены задач | 15 |
| Удобство работы с планом, рисками и профилями | 10 |
| Воспроизводимость запуска, качество README | 10 |

## 2. Целевое состояние (Definition of Done)

### A. Квартальное планирование
- Загрузка предоставленного датасета (xlsx → `scripts/split_dataset.py` → `dataset/*.csv` → БД).
- План на **шесть двухнедельных спринтов**.
- Ресурс команды = средняя фактическая производительность (velocity из team_history) × **0,8**.
- Доступное время специалистов: **до 80 ч/спринт** при полной занятости, **до 40 ч/спринт** при 0,5 ставки.
- **Потребность в ролях** для каждой задачи (данные task_role_requirements).
- **Зависимости**: блокирующая завершается не позже зависимой.
- Показ **причин** для каждой задачи: включена / перенесена (почему) / отменена (почему).

### B. Пересчёт по факту спринта (раз в 2 недели)
Раз в две недели загружается факт завершившегося спринта → пересчёт оставшейся части квартала. Показываются:
- выход прогнозной даты за пределы квартала;
- сдвиг цепочки зависимых задач;
- дефицит специалистов ролей на следующий спринт;
- изменения состава (запланированные / перенесённые / отменённые).
Связь факта и решения: пользователь видит, какие отклонения привели к изменениям и какие квартальные цели под угрозой. Прогноз до завершения квартала отличается от факта.

### C. Звёздная карта и Bus Factor (двухуровневое решение — согласовано)
- Состав команд, роли, грейды, заявленные компетенции инженеров.
- Распределение специалистов между командами (включая сотрудников в двух командах по 0,5).
- Доступность специалистов (часы/спринт по capacity_rate).
- **Bus Factor по компетенциям/ролям в областях company/team**; подсветка компетенций с единственным носителем.
- Методика расчёта показывается прямо рядом с показателем и областью (company/team).
- **На главной — виджет**: задачи текущего плана, зависящие от компетенций с Bus Factor ≤ 1 (топ-3 + счётчик). Полный расчёт — на странице карты.

### D. Метрики
- % выполнения квартального плана = завершённые за 12 недель инициативы / включённые в первоначальный план × 100%.
- % выполнения плана спринта = факт SP / первоначально запланированные SP × 100%.
- **База сравнения — первоначальный план** (изменение плана не подменяет знаменатель).
- Прогноз помечается как прогноз до конца квартала.

### Не в фокусе этапа
- Auth, мульти-user; экспорт отчётов; интеграции (ТЗ их не требует).
- Оптимизационный планировщик (MILP и т.п.) — жадная эвристика с объяснениями (последующие change).

## 3. Архитектура

```
xlsx (source of truth)
   └── scripts/split_dataset.py (uv, pandas) → dataset/*.csv
          └── db/importer → PostgreSQL (docker-compose)
                 └── бэкенд FastAPI (uv)
                       ├── api/       тонкие роутеры (HTTP↔сервисы)
                       ├── services/  бизнес-логика: planner, replanner, capacity,
                       │              dependencies, starmap, bus_factor, metrics
                       ├── domain/    pydantic-схемы (контракты API)
                       └── db/        SQLAlchemy async, models, importer
   фронтенд (SPA, делегирован) ──HTTP──> /api/v1 (Swagger: /docs)
```

**Текущие backend-ручки** (жирным — базовые для фронтенда):
- Планирование: **POST /plans/generate**, **GET /plans/{id}**, GET /plans/{id}/tasks/{task_id}/explanation
- Пересчёт: **POST /plans/{id}/sprints/{n}/facts**, **GET /plans/{id}/warnings**, GET /plans/{id}/diff
- Карта: **GET /teams**, GET /engineers/{id}, **GET /star-map/summary**, **GET /bus-factor**
- Метрики: **GET /plans/{id}/metrics**; данные: POST /data/import; GET /healthz

Спеки поведения: `openspec/specs/{planning,replanning,star-map,bus-factor,metrics,data,api,architecture, onboarding}`.

**Стек AI (согласовано):** LangGraph (`src/ai/pipelines/`) — несколько пайплайнов с loop'ами (нормализация, позже — AI-советник приоритетов). Провайдер — **GigaChat (Сбер)**; ключ через env `GIGACHAT_*`; без ключа — деградация до шаблонных маппингов + вопросов (спека onboarding). LLM-ответы всегда валидируются pydantic-схемами; решение о загрузке — за человеком.

## 4. Страницы (user flow, v0.3)

**Главный user flow:**
```
вход/регистрация → загрузка данных (датасет или вручную)
  → [опционально] AI-агент: разбор/нормализация/стандартизация → подтверждение загрузки
  → дашборд (команды, план, ПРИОРИТЕТЫ ВЫСТАВЛЯЕТ ЧЕЛОВЕК — AI может предложить)
  → цикл спринтов (факт → пересчёт → риски) → метрики
звёздная карта — параллельно после загрузки людей, с фильтрами
```

### Стр. 0 «Вход / Регистрация»
**Цель:** идентификация лидов и их команды (для демо — минимальный auth: email+пароль, роли admin/лид/наблюдатель).
**Элементы:** форма входа, регистрация, "войти как демо-пользователь".
**Замечание:** auth — change 005, не блокирует ни одну страницу (до его появления сервис открыт как сейчас).

### Стр. 0.1 «Загрузка данных» (модал → стр. после загрузки)
**Цель:** получить задачи и людей в сервис.
**Два пути:**
1. **Файл (основной):** xlsx/csv в формате датасета (или «подобном») → пайплайн split → импорт.
2. **РУЧНОЙ ВВОД (новое, согласовано):** заполнить вручную команды, проекты, задачи, людей — и то и то я вижу как базовую страницу-редактор.
3. **AI-агент-помощник (новое, согласовано):** при загрузке файла незнакомого формата — агент разбирает/нормализует/стандартизирует данные под наш формат и показывает diff «что поймёт сервис»; человек подтверждает. Спрашивать контекст (команды, роли) агент может, но решение о загрузке — за пользователем.
**Замечание:** source of truth остаётся xlsx (спека `data`); ручной ввод и AI-нормализация пишут прямо в БД и маркируются как «ручные данные» (не переписываются при следующем импорте).

### Стр. 1 «План квартала» — главная (дашборд)
**Цель:** увидеть команды, план на 6 спринтов и причины решений. Приоритеты выставляет человек.
**Элементы:**
- 6 колонок (спринты 1–6), в каждой — задачи команды (фильтр по команде сверху).
- Статус каждой задачи: planned (зелёный), перенесена (жёлтый, причина в tooltip/боке), отменена (красный), выполнена (серый, факт).
- **Приоритизация — у пользователя (согласовано):** панель «неразобранные задачи» с drag-n-drop порядок (AI-советник анализирует задачи, может доспросить контекст и предложить порядок — но **утверждает человек**).
- Кнопка «Сгенерировать план» (+ модал импорта данных, если БД пуста).
- **Виджет Bus-риска плана** (мини-виджет): «N задач плана зависят от компетенций с единственным носителем» + топ задач. **Клик открывает подробную панель уязвимостей команды** (какие компетенции, кто единственный носитель, какие задачи под угрозой) с углублением на страницу карты.

### Стр. 2 «Спринт: факт и пересчёт»
**Цель:** раз в 2 недели — загрузить факт спринта и увидеть, что изменилось.
**Элементы:**
- Селектор спринта (1..6), форма: введите выполненные SP + отметки выполненных задач.
- После отправки: блок перенесённых задач, 4 предупреждения (`warnings`), изменившиеся даты (`GET /plans/{id}/diff`), обновлённые причины.
**User flow:**
```
завершение спринта → загрузить факт → пересчёт →
  [выход за квартал | сдвиг цепочки | дефицит ролей | изменение состава]
  → решения по задачам → записать итог квартала при завершении 6го
```

### Стр. 3 «Звёздная карта»
**Цель:** увидеть состав и риски компетенций с фильтрами.
**Элементы:**
- Team-cards или force-graph: команда = кластер, инженер = узел (роль/грейд/ставка), выделение сотрудников с 2 командами (0,5 ставки каждой).
- **Фильтры (согласовано):** по команде, роли, грейду, компетенции, ставке — чтобы «выбрать тех или иных» людей (решарчи engineers).
- Панель справа при выборе: анкета инженера (роль, грейд, skills_declared, часы/спринт).
- Блок **Bus Factor**: фильтр областей (company / team), список (компетенция → число носителей), подсветка ≤1; текст методики и ограничений.
**Модели данных:** `GET /star-map/summary` (teams, fte_distribution, single_holder_competencies), `GET /teams`, `GET /engineers/{id}`, `GET /bus-factor`.

### Стр. 4 «Метрики квартала»
**Цель:** оценить выполнение от первоначальной базы сравнения.
**Элементы:**
- % выполнения квартального плана: факт (по завершённым спринтам) / прогноз (пометка «прогноз» до конца квартала).
- % выполнения по 6 спринтам (бар каждой).
- История диффов (снапшоты планов — после change 002).
**Модели данных:** `GET /plans/{id}/metrics` (quarter_completion_pct + is_forecast; sprint_completion_pct + is_forecast).

**Не отдельные страницы (согласовано):**
- Импорт датасета — модалка со стр. 1.
- Команды/дриллдауны — фильтры внутри страниц 1 и 3.
- Swagger — для API, не в меню продукта.

## 5. User flow по ролям

### Тимлид (основной владелец плана)
```
вход [стр.0] → загрузка данных [стр.0.1: файл + AI-нормализация / вручную]
→ дашборд [стр.1] → выставить приоритеты (drag-n-drop, AI может советовать)
→ план построен → клик-task → причина
→ (каждые 2 недели) [стр.2] факт спринта → риски → повтор
→ (конец квартала) [стр.4] итоги
```
### CTO / ресурсный менеджер
```
[стр.3] карта → фильтры (команда/роль/навык/ставка) → одиночные компетенции
→ Bus Factor ≤ 1 → задачи под угрозой (из виджета стр. 1)
```

### CTO / ресурсный менеджер
```
[стр.3] карта → одиночные компетенции (подсветка) → Bus Factor ≤ 1
        → задачи под угрозой (виджет стр. 1 / связь истории)
```

## 6. Handoff фронтендеру (самодостаточно)

- Все ручки с реальными схемами: Swagger `http://localhost:8000/docs` — код уже работает (change 001 в `develop`, «feat(planning): каркас сервиса...»).
- Подъём: README «Быстрый старт» (docker compose up; uv run uvicorn src.main:app) — только `/api/v1` и данные по любым страницам.
- Ответы API показываются без рендеринга HTML: JSON фoрмата (контракты в `src/domain/models.py` pydantic).
- Планирование без чита №2: если бэка недоступен — только стр. 1 в режиме только-чтение; каждая страница работает на данных, полностью.
- ВАЖНО: не менять `dataset/*.csv` вручную (правки только через xlsx/скрипт, спека `data`).

Подсказки по графе:
- Звёздная карта: force-directed graph (например `react-force-graph` / d3-force), узлы группируются по командам, вес = FTE, контур-«свечение» для узлов с единственными компетенциями.
- План: 6 конлайнов, drag/collapse не нужен; цвет от decision.
- Метрики: забирать численные значения и bar-charts, не подменять факт/прогноз цветом без подписи.
