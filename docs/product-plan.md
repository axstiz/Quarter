> Живой документ. Версия 0.4.2 — этап: бэкенд changes 001–004 готовы (архивированы); спеки 005–009 согласованы spec-only (auth, ui, jobs, workspaces, permissions); user flow дополнен workspace-ами (компании).
> Допилить: схемы после созвона (см. «Роадмап» и «Открытые решения»).

## 1. Обзор

**Продукт.** Сервис, помогающий составить выполнимый квартальный план разработки (6 спринтов × 2 недели = 12 недель), пересчитывать его по фактическим результатам спринтов и видеть риски загрузки и компетенций команд (звёздная карта + Bus Factor).

**Кому нужно.** Тимлидам команд разработки, ресурсным менеджерам, ИТ-директору.

**Почему.** Суммарной оценки задач недостаточно: выполнимость зависит от производительности команды, рабочего времени специалистов, потребности в разных ролях и связей между задачами. Отставание в одном спринте двигает цепочку зависимых работ и ставит под угрозу квартальные цели.

**Целевые критерии (вес из ТЗ):**
| Критерий | Вес |
|---|---|
| Корректность квартального плана (ресурс, трудозатраты, зависимости) | 30 |
| Качество пересчёта и предупреждений о рисках | 20 |
| Полнота звёздной карты и корректность Bus Factor | 15 |
| Понятность причин включения/переноса/отмены задач | 15 |
| Удобство работы с планом, рисками и профилями | 10 |
| Воспроизводимость запуска, качество README | 10 |

## 2. Целевое состояние (Definition of Done)

### A. Квартальное планирование
- Загрузка предоставленного датасета (xlsx → `scripts/split_dataset.py` → `dataset/*.csv` → БД).
- План на **шесть двухнедельных спринтов**.
- Ресурс команды = средняя фактическая производительность (velocity из team_history) × **0,8**.
- Доступное время специалистов: **до 80 ч/спринт** при полной занятости, **до 40 ч/спринт** при 0,5 ставки.
- **Потребность в ролях** для каждой задачи (данные task_role_requirements).
- **Зависимости**: блокирующая завершается не позже зависимой.
- Показ **причин** для каждой задачи: включена / перенесена (почему) / отменена (почему).

### B. Пересчёт по факту спринта (раз в 2 недели)
Раз в две недели загружается факт завершившегося спринта → пересчёт оставшейся части квартала. Показываются:
- выход прогнозной даты за пределы квартала;
- сдвиг цепочки зависимых задач;
- дефицит специалистов ролей на следующий спринт;
- изменения состава (запланированные / перенесённые / отменённые).
Связь факта и решения: пользователь видит, какие отклонения привели к изменениям и какие квартальные цели под угрозой. Прогноз до завершения квартала отличается от факта.

### C. Звёздная карта и Bus Factor (двухуровневое решение — согласовано)
- Состав команд, роли, грейды, заявленные компетенции инженеров.
- Распределение специалистов между командами (включая сотрудников в двух командах по 0,5).
- Доступность специалистов (часы/спринт по capacity_rate).
- **Bus Factor по компетенциям/ролям в областях company/team**; подсветка компетенций с единственным носителем.
- Методика расчёта показывается прямо рядом с показателем и областью (company/team).
- **На главной — виджет**: задачи текущего плана, зависящие от компетенций с Bus Factor ≤ 1 (топ-3 + счётчик). Полный расчёт — на странице карты.

### D. Метрики
- % выполнения квартального плана = завершённые за 12 недель инициативы / включённые в первоначальный план × 100%.
- % выполнения плана спринта = факт SP / первоначально запланированные SP × 100%.
- **База сравнения — первоначальный план** (изменение плана не подменяет знаменатель).
- Прогноз помечается как прогноз до конца квартала.

### Не в фокусе этапа
- Auth, мульти-user; экспорт отчётов; интеграции (ТЗ их не требует).
- Оптимизационный планировщик (MILP и т.п.) — жадная эвристика с объяснениями (последующие change).

## 3. Архитектура

```
xlsx (source of truth)
   └── scripts/split_dataset.py (uv, pandas) → dataset/*.csv
          └── db/importer → PostgreSQL (docker-compose)
                 └── бэкенд FastAPI (uv)
                       ├── api/       тонкие роутеры (HTTP↔сервисы)
                       ├── services/  бизнес-логика: planner, replanner, capacity,
                       │              dependencies, starmap, bus_factor, metrics
                       ├── domain/    pydantic-схемы (контракты API)
                       └── db/        SQLAlchemy async, models, importer
   фронтенд (многостраничный сайт, делегирован) ──HTTP──> /api/v1 (Swagger: /docs)
```

**Текущие backend-ручки** (жирным — базовые для фронтенда):
- Планирование: **POST /plans/generate**, **GET /plans/{id}**, GET /plans/{id}/tasks/{task_id}/explanation
- Пересчёт: **POST /plans/{id}/sprints/{n}/facts**, **GET /plans/{id}/warnings**, GET /plans/{id}/diff
- Карта: **GET /teams**, GET /engineers/{id}, **GET /star-map/summary**, **GET /bus-factor**
- Метрики: **GET /plans/{id}/metrics**; данные: POST /data/import; GET /healthz

Спеки поведения: `openspec/specs/{planning,replanning,star-map,bus-factor,metrics,data,api,architecture, onboarding}`.

**Стек AI (согласовано):** LangGraph (`src/ai/pipelines/`) — несколько пайплайнов с loop'ами (нормализация, позже — AI-советник приоритетов). Провайдер — **GigaChat (Сбер)**; ключ через env `GIGACHAT_*`; без ключа — деградация до шаблонных маппингов + вопросов (спека onboarding). LLM-ответы всегда валидируются pydantic-схемами; решение о загрузке — за человеком.

## 4. Страницы и функции (user flow v0.4.2 — от функционала)

**Главный user flow:**
```
вход (change 005) → «Мои компании» [стр.0.2]: выбрать или создать workspace (компанию)
  → далее ВСЕ шаги — внутри контекста выбранной компании:
  старт (БД компании пустая) → загрузка данных [стр.0.1]
    → дашборд «План квартала» [стр.1] (генерация плана, приоритеты, отмена задач — human-in-loop)
    → цикл спринтов [стр.2] (факт → пересчёт → риски)      ← раз в 2 недели
    → метрики [стр.4] (итоги квартала после 6-го спринта)
  звёздная карта [стр.3] — параллельно, доступна сразу после загрузки людей
```

**Контекст компании (workspace):** каждая страница работает в контексте выбранного workspace-а; текущая компания всегда показана в хедере (селектор-переключение); данные соседних компаний изолированы — не видны и не считаются в планах/метриках. Ручки workspace-ов (`GET/POST /workspaces`, участники/роли) появятся с change 008/009 — пока спеки согласованы, реализации нет.

Формат каждой страницы: **что видит → что делает → ручка API**. Auth отсутствует (change 005) — все страницы открыты; в flow не фигурирует.

### Стр. 0.1 «Загрузка данных»
**Цель:** получить задачи и людей в сервис. Три пути — от самого простого к ручному:

| Путь | Сценарий | Ручка |
|---|---|---|
| **А. Импорт датасета (главный демо-путь)** | кнопка «Импортировать датасет» → counts по сущностям. Для формата организаторов — без вопросов и подтверждений | `POST /data/import` |
| **Б. Свой файл** | xlsx/csv/json → job → превью маппинга колонок (polling) → ответы на вопросы (если незнакомый формат) → подтверждение → импорт | `POST /data/upload` → `GET /data/jobs/{id}` → `POST .../answers` → `POST .../confirm` |
| **В. Ручной ввод** | формы: команды, задачи, инженеры, зависимости — все поля кроме id опциональны, дозаполнение после импорта | CRUD: `POST/PUT/DELETE /teams, /tasks, /engineers, /dependencies` |

**Правила (важно для UI):**
- Путь Б: данные не попадают в БД без подтверждения пользователя (агент только предлагает маппинг).
- Статусы job: `uploaded | mapping | questions | ready | confirmed | failed`.
- Повторный импорт не затирает ручные записи (source=manual) — UI может писать «ваши ручные правки сохранятся».
- Если пользователь загрузил незнакомый формат без ключа GigaChat — деградация: шаблонный маппинг + ручные вопросы (без ошибки).
- **Импорт принадлежит выбранной компании**: данные и планы появляются в её workspace; импорт в одной компании не задевает соседние.

### Стр. 0.2 «Мои компании» (workspace-ы) — отдельная страница после входа
**Цель:** каждая компания — самостоятельный мир со своим датасетом, людьми, планами и участниками; страница — центр переключения между ними.

**Что видит:**
- Карточки своих workspace-ов: название, **моя роль в этой компании** (admin / editor / reader), наполненность (число задач/людей, есть ли план).
- Workspace по умолчанию с демо-датасетом (для совместимости и онбординга).

**Что делает:**

| Действие | Поведение | Ручки (после change 008/009) |
|---|---|---|
| Войти в компанию | переключение контекста; далее всё — внутри её данных | контекст-селектор |
| Создать компанию | создатель становится владельцем (role admin); компания пуста до импорта | `POST /workspaces` |
| Переименовать / удалить (admin) | удаление — с подтверждением | `PUT/DELETE /workspaces/{id}` |
| Участники и роли (admin) | приглашение участника, выдача/смена роли (editor/reader), удаление; читатели — view-only | ручки участников (009: матрица прав) |
| Увидеть свои права | роль в каждой компании видна на карточке | из `GET /workspaces` |

**Правила:** роль пользователя локальна по компании (в A — editor, в B — reader — не связаны); права раздаёт админ компании (не саморегистрация); удаление компании затрагивает только её данные.

### Стр. 1 «План квартала» — главная (дашборд)
**Цель:** увидеть план на 6 спринтов и причины решений; приоритеты и отмены — за человеком.

**Что видит:**
- 6 колонок (спринты 1–6); в каждой — задачи с цветом по decision: `planned` (зелёный), `postponed` (жёлтый, причина в tooltip/боке), `cancelled` / `cancelled_pending` (красный), `done_actual` (серый, факт).
- Блок «вне плана» — отложенные/отменённые задачи с причинами.
- Если БД пуста и план не сгенерирован — пустое состояние с кнопкой «Сгенерировать план» (ошибка 400 = подсказка «сначала импортируйте данные»).

**Что делает:**

| Действие | Поведение | Ручка |
|---|---|---|
| Сгенерировать план | 201 + plan_id; после генерации UI работает с этим plan_id | `POST /plans/generate` |
| Сменить приоритет задачи | панель/строка задачи, число (меньше — раньше). **Вступает в силу после пересчёта** — UI подсказывает «пересчитать план» | `PUT /tasks/{id}/priority` → `POST /plans/{id}/recompute` |
| Предложить отмену задачи (постоянно не помещается) | сервис помечает кандидата; задача → `cancelled_pending` | `POST /plans/{id}/tasks/{tid}/cancel-request` |
| Подтвердить отмену (лид) | второй клик: `cancelled_pending` → `cancelled`, задача остаётся видимой с причиной | `POST /plans/{id}/tasks/{tid}/confirm-cancel` |
| Выбрать версию плана | селектор версий (initial → recompute → …); актуальная — последняя в цепочке | `GET /plans` |
| Клик по задаче | карточка: summary, инициатива (parent_id), SP/часы, часы по ролям, причина решения | данные в `GET /plans/{id}`, отдельно `GET /plans/{id}/tasks/{tid}/explanation` |
| Фильтр по команде | клиентский фильтр по team_id | данные уже в ответе `GET /plans/{id}` |

**Правила:**
- Страница работает в контексте выбранной компании: план, версии и отмена — только её задачи (данные соседних workspace-ов не видны).
- Drag-n-drop приоритетов — деталь реализации (можно списоком); контракт — только число priority.
- После любого изменения приоритетов/отмен нужен пересчёт (`recompute`) — создаются новая версия, старые не пропадают.
- AI-советник приоритетов — **нет в бэке** (потенциальный будущий change); в UI не закладывать.

### Стр. 2 «Спринт: факт и пересчёт»
**Цель:** раз в 2 недели загрузить факт и увидеть, что изменилось.

**Что видит:** селектор спринта (1..6), план текущей версии, уже загруженные факты.

**Что делает:**

| Действие | Поведение | Ручка |
|---|---|---|
| Загрузить факт спринта | отметить выполненные задачи (SP авто из плана) + выполненные SP; **после загрузки создаётся новая версия плана** — UI переключается на `new_plan_id` из ответа | `POST /plans/{id}/sprints/{n}/facts` |
| Повторно загрузить тот же факт | получит 409 — UI блокирует повторную отправку | тот же |
| Кнопка «Пересчитать» (без факта) | создаёт ещё одну версию плана | `POST /plans/{id}/recompute` |
| Смотреть риски | 4 вида предупреждений с затронутыми задачами: `deadline_overflow` (выход за квартал), `dependency_shift` (сдвиг цепочки), `role_deficit` (дефицит роли на следующий спринт, с числами «нужно/доступно»), `composition_change` (изменения состава) | `GET /plans/{id}/warnings` |
| Смотреть сдвиги | какие задачи переехали из спринта в спринт + что стало «вне квартала» | `GET /plans/{id}/diff` |
| Смотреть факты по цепочке версий | какие спринты зафиксированы | `GET /plans/{id}/facts` |

**Правила:**
- Формула связи «факт → решение»: предупреждения содержат task_ids; UI связывает факт (что не выполнено) и следствие (что сдвинулось) — заголовки вида «из-за невыполнения X сдвинулось Y».
- Отмена задач-кандидатов после пересчёта — возврат на стр. 1 (двухшаговая отмена).
- Факты и версии планов принадлежат компании: снапшот-цепочка и факты изолированы по workspace.

### Стр. 3 «Звёздная карта»
**Цель:** состав команд и риски компетенций с фильтрами.

**Что видит:**
- Команды-кластеры с инженерами (роль/грейд/ставка); инженеры в двух командах по 0.5 — в обеих с пометкой parttime.
- Единственные носители компетенций — подсветка.

**Что делает:**

| Действие | Поведение | Ручка |
|---|---|---|
| Фильтры: команда / роль / грейд / навык / ставка | поиск людей | `GET /engineers?team_id=&role=&grade=&skill=&min_rate=` |
| Клик по инженеру | анкета: все команды (parttime), часы/спринт, **single_holder_alerts** (его уникальные навыки в его командах) | `GET /engineers/{id}` |
| Открыть команду | состав, capacity SP/спринт, история velocity | `GET /teams`, `GET /teams/{team_id}` |
| Открыть Bus Factor | список компетенций/ролей → число носителей, подсветка factor ≤ 1, области company/team, **текст методики показывать обязательно** | `GET /bus-factor`, сводка: `GET /star-map/summary` |

**Правила:**
- Карта показывает людей текущей компании (workspace); специалисты других компаний не видны.
- Данные доступны сразу после импорта людей — генерация плана не нужна.
- Граф (force-directed) или карточки — деталь реализации; контракт — JSON из ручек выше.
- Виджет «задачи плана под угрозой Bus-риска» (change 004 ✅): данные из единой ручки `GET /plans/{id}/bus-risk` — «N задач под угрозой» + список с holders (роль → носители); клик → панель уязвимостей → страница карты.

### Стр. 4 «Метрики квартала»
**Цель:** оценить выполнение от первоначальной базы сравнения.

| Что видит | Источник |
|---|---|
| % выполнения квартального плана — по **инициативам** (parent_id), знаменатель — инициативы первоначального плана | `GET /plans/{id}/metrics` → `quarter_completion_pct` |
| % по каждому из 6 спринтов (факт SP / запланированные SP) | `sprint_completion_pct` |
| Пометки **факт / прогноз** — до конца квартала значения прогнозные, UI обязан показывать пометку | `quarter_completion_is_forecast`, `sprint_completion_is_forecast` |
| База сравнения — первоначальный план (пересчёты не подменяют знаменатель) | метрики считаются по root-плану цепочки автоматически |

### Не отдельные страницы (согласовано)
- Импорт датасета — модалка со стр. 1 (или отдельная стр. 0.1 до первого импорта).
- Команды/дриллдауны — фильтры внутри страниц 1 и 3.
- Swagger `/docs` — для API, не в меню продукта.

## 5. User flow по ролям

### Консультант / админ-внешник (мультикомпании)
```
[стр.0.2] создать компанию (владелец=admin) → загрузить её датасет [стр.0.1]
→ пригласить участников → выдать editor/reader (матрица прав — change 009)
→ повторить для следующей компании; переключение — хедер/стр.0.2
```

### Редактор (editor) — лид компании, основной владелец плана
```
[стр.0.2] выбрать компанию
→ загрузка данных [стр.0.1: импорт датасета / свой файл + AI-нормализация / вручную]
→ дашборд [стр.1] → сгенерировать план
→ приоритеты (число, human) → пересчитать → новая версия плана
→ клик-task → причина решения
→ постоянные «не влезает» → предложить отмену → подтверждение
→ (каждые 2 недели) [стр.2] факт спринта → новая версия → риски/сдвиги → повтор
→ (конец квартала) [стр.4] итоги: факт vs прогноз от первоначального плана
```

### Читатель (reader) — наблюдатель
```
[стр.0.2] выбрать компанию → только просмотр:
[стр.1] план и причины · [стр.3] карта и Bus Factor · [стр.4] метрики (факт/прогноз)
```

### CTO / ресурсный менеджер (внутри компании)
```
[стр.3] карта → фильтры (команда/роль/навык/ставка) → единственные носители
→ Bus Factor ≤ 1 (company/team) + методика
→ задачи под угрозой: [стр.1] фильтр по задачам с ролями-одиночками (change 004 автоматизирует)
```
