# PostCode Challenge: квартальное планирование команд и звёздная карта

Сервис квартального планирования работ команд разработки и «звёздной карты» специалистов — решение по [заданию PostCode.md](задание%20PostCode.md).

## Быстрый старт

Требования: **docker** — для связки одной командой; без него [uv](https://docs.astral.sh/uv/) + Node.js 22 (для openspec и локального фронта).

### Связка одной командой (docker)

```bash
docker compose up -d --build
# http://localhost:5173 → /login → «Войти как администратор» → весь сценарий
# Swagger: http://localhost:8000/docs
```

Поднимаются: `db` (PostgreSQL 16, порт 5432) + `api` (uvicorn, порт 8000; dataset внутри
образа — импорт демо-датасета работает сразу) + `frontend` (nginx, порт 5173, проксирует
`/api`, `/auth`, `/workspaces`, `/permissions` на api).

### Полная связка с профилями (jobs + optimizer)

Профили compose: `jobs` — Redis + arq-воркер фоновых джобов (change 007), `optimizer` —
Timefold-сайдкар на Java 21 (change 018). Без профилей оптимизация отрабатывает эвристикой.

```bash
# 1) полный стек: db + api + frontend + redis/worker + optimizer
docker compose --profile jobs --profile optimizer up -d --build

# 2) проверить состояние (db/optimizer — healthcheck, остальные — Up)
docker compose --profile jobs --profile optimizer ps
curl -sf http://localhost:8000/healthz

# 3) залить демо-датасет (idempotentно, пересоздаёт данные; нужна демо-сессия editor/admin)
TOKEN=$(curl -s -X POST http://localhost:8000/auth/demo-login -H 'Content-Type: application/json' \
  -d '{"role": "admin"}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
curl -X POST http://localhost:8000/api/v1/data/import -H "Authorization: Bearer $TOKEN"
# или из UI: /login → демо-роль editor/admin → кнопка импорта на /data

# 4) сценарий: /plan → «Сгенерировать» → «Оптимизировать» (при живом optimizer —
#    режим solver; новая версия плана с assignments, личные планы /people/*, звёздная карта)
```

Первая сборка `optimizer` идёт через Maven Central по host-сети и занимает несколько минут;
повторные — из docker-кэша. Переменные solver (`OPTIMIZER_SEED`,
`OPTIMIZER_TIME_LIMIT_SECONDS`, `OPTIMIZER_STAFFING_GAIN_THRESHOLD`) — в
`docker-compose.yml`, секция `optimizer.environment`.

Только часть стека: `docker compose up -d db api` — без фронта (API на :8000);
`docker compose --profile optimizer up -d optimizer` — дотянуть solver к уже работающей связке.

Остановка/очистка:

```bash
docker compose --profile jobs --profile optimizer down          # остановить всё
docker compose down -v                                          # + удалить pgdata (пересоздание БД)
```

Старый `pgdata` с прошлой схемой (без колонок новых change'ей) пересоздавать через `down -v`,
затем импорт демо-датасета (шаг 3). **Обязательно после change 025** (составные PK
`tasks`/`teams`): старая схема несовместима, alembic-миграции нет — только пересоздание.

### Конфигурация (.env)

Сервисы `api` и `worker` подхватывают `.env` из корня репо (шаблон — `example.env`;
локальный запуск через uv читает его же). Ключевые переменные:

| Переменная | Default | За что отвечает |
|---|---|---|
| `POSTCODE_DATABASE_URL` | postgres://…@db:5432 (в compose) | подключение к БД |
| `POSTCODE_JOBS_MODE` | `auto` | `queue` — только Redis/arq, `sync` — только в процессе |
| `POSTCODE_LLM_PROVIDER` | `gigachat` | `gigachat` \| `ollama` \| `none` (см. «LLM-провайдеры») |
| `GIGACHAT_CLIENT_ID` / `GIGACHAT_CLIENT_SECRET` | — | ключи GigaChat (без префикса POSTCODE_) |
| `POSTCODE_OLLAMA_BASE_URL` / `POSTCODE_OLLAMA_MODEL` | `http://localhost:11434` | локальный Ollama |
| `POSTCODE_OPTIMIZER_BASE_URL` | `http://optimizer:8080` (в compose) | solver-сайдкар |

Ollama на хосте из контейнера: `POSTCODE_OLLAMA_BASE_URL=http://host.docker.internal:11434`
(на Linux добавить `extra_hosts: ["host.docker.internal:host-gateway"]` в сервис api).

## Датасет

Источник — `Датасет_с_правками_основной.xlsx`, лист «Датасет(обновленный)». В нём несколько таблиц последовательно накатаны на один лист; разделитель — титульные строки. Каждая таблица выгружена в отдельный CSV (данные до первой пустой строки внутри блока). Все преобразования выполняются только скриптом `scripts/split_dataset.py`, ручные правки не требуются.

| Файл | Содержимое | Строк |
|---|---|---|
| `tasks.csv` | 45 задач: стандартные поля задачи, Story Points, статусы, даты, плановые/итоговые результаты | 45 |
| `task_role_hours.csv` | фактически затраченное время по ролям для 6 задач (данные в листе есть только для них) | 6 |
| `task_role_requirements.csv` | потребность в часах по ролям для каждой задачи (long-формат: `role, task_id, hours`); нулевые строки отброшены | 307 |
| `task_dependencies.csv` | 16 строк зависимостей между задачами (типы: `has to be done before` / `is required for` / `depends on`); одна пара (SRV-4015→SRV-4016) продублирована в источнике — при импорте в БД дедуплицируется до 15 | 16 (15 уникальных) |
| `engineers_profiles.csv` | 34 инженера: команда, роль, грейд, компетенции, занятость (capacity_rate) | 34 |
| `team_history.csv` | история velocity спринтов по 5 командам | 12 |
| `reference_values.csv` | справочники: итоги разработки, причины расхождения планов, результаты закрытия задач | 19 |

### Преобразования и допущения

1. **Даты**: Excel-serial (`45995.514…`, от 1899-12-30) или строки с временем → `YYYY-MM-DD`. Время отбрасывается — планирование ведётся по дням.
2. **Колонки**: renamed в snake_case на английском, где совпадают смыслы, с сохранением русских заголовков ролей. Пример переименований: `Номер инициативы → initiative_no`, `плановый результат → planned_result`, `будет включено в спринт → planned_in_sprint`.
3. **`task_dependencies.csv`**: в исходном xlsx заголовки `blocked_task_id`/`dependency_type` смещены на одну колонку вправо относительно данных; сопоставление сделано по позициям (`blocking_task_id, blocked_task_id, dependency_type`), имена в CSV корректны.
4. **Инженеры в нескольких командах**: ENG-405, ENG-406, ENG-419, ENG-426 имеют по две записи (0.5 ставки в каждой) — записи оставлены как есть, логика доступности учитывает обе части.
5. **Пропуски**: пустые ячейки → пустая строка в CSV (`planned_in_sprint`, `customer_result` и т. п. для `ToDo/InProgress` задач); в строках без дат в `*_date` колонках — пустая строка.
6. **`task_role_hours.csv`**: заполнен только для 6 из 45 задач (для остальных в исходных данных нет фактических разбивок по ролям) — используется для расчёта фактической производительности по ролям.
7. Числа хранятся без разделителей и окончаний (истинные целые — как ints, дробные — с точкой); `capacity_rate` — дробь (0.5 / 1.0).

### Аномалии исходных данных (проверено сверкой xlsx ↔ CSV по ячейкам, 2026-09-17)

Нарезка данных в CSV **ничего не теряет**: воспроизведение разбора в памяти и попарное сравнение каждой ячейки каждого CSV с извлечением из листа дало 0 расхождений во всех 7 файлах. Ниже — аномалии **самого исходного датасета** (не нарезки) и то, как сервис с ними работает. Для проверяющих: каждая аномалия воспроизводится чтением `dataset/*.csv`, приводимые цифры посчитаны по CSV.

#### A. «Висячие» зависимости — ссылки на задачи вне датасета

4 строки зависимостей (3 уникальные пары) ссылаются на задачи, которых нет в `tasks.csv`:

| blocking | blocked | тип | комментарий |
|---|---|---|---|
| SRV-4013 | SRV-4014 | is required for | обеих задач нет в датасете |
| SRV-4015 | SRV-4016 | depends on **и** is required for | дубль пары с разными типами; отсюда 16 строк → 15 уникальных пар |
| SRV-4011 | SRV-4019 | has to be done before | SRV-4019 вне датасета |

Итого: из 16 строк зависимостей 12 соединяют существующие задачи (все 12 пар уникальны), 4 — «висячие» (+1 дубль). В нумерации SRV-серии вместо 4013/4014/4016/4019 присутствуют 4021+ — блоки вырезаны в источнике.

**Обработка сервисом**: зависимости с несуществующей стороной игнорируются планировщиком (задача считается не блокированной) — иначе одна ссылка на отсутствующую задачу заморозила бы половину SRV-цепочки. Игнорирование производится явным образом: `topo_order` строится только по задачам, присутствующим в плане.

#### Б. Фактические часы по ролям превышают оценку у всех 6 задач с данными

| task_id | сумма часов по ролям | estimated_hh | превышение |
|---|---|---|---|
| MOB-7011 | 345 | 180 | +91 % |
| SRV-4041 | 339 | 220 | +54 % |
| MP-102 | 288 | 186 | +55 % |
| DB-202 | 401 | 324 | +24 % |
| SRV-4011 | 190 | 160 | +19 % |
| KP-3898 | 226 | 194 | +16 % |

Статус этих задач в датасете различен; вероятное объяснение — в `task_role_hours` лежат суммарные трудозатраты роли за всю историю задачи (включая работу до оценки), либо оценки систематически занижены. **Обработка**: таблица импортируется и показывается витринно на карточке задачи (поле фактической разбивки по ролям); в расчётах планирования **не участвует** (решение лида, 2026-09-17) — накопленной базы на 6 задач недостаточно для пересчёта производительности. В витрине интерпретация «факт > оценка» показывается пользователю как есть («оценка занижена»), без авто-коррекции оценок.

#### В. InProgress-задачи без spent_time

Все 6 задач `InProgress` имеют пустой `spent_time` (из 45 задач поле заполнено у 39). Следствие: «остаток объёма» `estimated_hh − spent_time` для них равен полной оценке (и SP — полные), и сценарий «просрочена (overdue)» из спеки planning **на этом датасете не демонстрируется** — признака перерасхода (`spent > estimated`) в данных нет ни у одной задачи. Правило статуса реализовано и покрыто юнит-тестами на синтетических данных.

#### Г. Зависимости «Done → не-Done» (5 пар)

Например: `MP-101 (Done) блокирует MP-102 (InProgress)`, `AI-301 (Done) → AI-302 (ToDo)`, `DB-201 (Done) → DB-202`, `ASUKD-5222 (Done) → QA-9022`. С точки зрения процесса странно: блокер уже завершён, а зависимая не завершена. **Обработка**: planner исключает Done-задачи из планирования, заблокированные при этом свободны (зависимость считается выполненной) — это соответствует здравому смыслу, но означает, что в датасете «живых» межзадачных блокировок меньше, чем кажется по числу строк.

#### Д. Дефицит ролей внутри команд — системная особенность

- **8 из 12 внутри-датасетных зависимостей — межкомандные** (задача одной команды зависит от задачи другой); последовательность работ требует кросс-координации даже без учёта часов.
- **50 комбинаций (команда, роль)** в потребностях задач вообще без носителя в собственной команде — именно поэтому реализован кросс-командный заём (role requirement задачи закрывается инженером из другой команды).
- **9 ролей не имеют носителя во всей компании**: Аналитик 1С, Архитектор 1С, ДевОпс, Разработчик 1С, Разработчик BigData, Разработчик iOS, Руководитель проекта, Специалист поддержки, Специалист поддержки 1С. Задачи с такими ролями планируются через **виртуального держателя** с полной ставкой (допущение, change 003) — в причинах задач и на star-map это видно как риск.

#### Е. SP и часы не пропорциональны

Отношение `estimated_hh / estimation_sp` по 45 задачам: минимум 7.5, медиана 25, среднее 25.2, максимум 40.5 часов на 1 SP. Вывод: Story Points — независимая штучная оценка сложности, а не пересчёт часов. **Обработка**: две независимые шкалы планирования (SP-гейт против velocity×0.8; часовой гейт против лимитов ролей) — прямого коэффициента SP↔часы нет (допущение зафиксировано в change 003, решение №3 опроса).

#### Ж. Хронология объясняет демо-квартал

Даты задач: `planned_start` 2025-09-15 … 2026-07-16, `planned_end` 2025-10-15 … **2026-08-01**; фактические даты (`actual_start`/`actual_end`) заполнены только у 14/8 задач из 45. Согласованный старт демо-квартала — следующий незавершённый квартал после `max(planned_end)` (решение №12) → календарь строится от даты после 2026-08-01.

#### Как воспроизвести проверки

Скрипты сверки — ad-hoc (pandas: извлечение блоков листа по логике `scripts/split_dataset.py` и попарное сравнение с CSV). Автоматическая гарантия — `pre-push` хук: `uv run scripts/split_dataset.py` обязан воспроизводить `dataset/*.csv` byte-identично; расхождение содержимого листа и CSV ловится этим.

## openspec (для команды)

Спецификации для командной работы с AI-агентами — в папке [openspec/](openspec).

```bash
npm i -g @fission-ai/openspec   # раз (префикс npm в NixOS: npm config set prefix ~/.npm-global)
openspec validate               # проверка спеков
```

Workflow: `/opsx-propose "идея"` → ревью → `/opsx-apply` → `/opsx-archive`. См [.opencode/](.opencode) — команды для OpenCode.

## Contributing

1. Ветка от `main` — один короткий префикс (`feat/`, `fix/`, `spec/`).
2. Изменения сферы (service behavior) — через openspec change proposal (`/opsx-propose`), не напрямую в `openspec/specs`.
3. Перед MR: `openspec validate`, пересборка датасета (`uv run scripts/split_dataset.py`) должна сходиться по числу строк с README.

### Роли в команде

| Роль | Что делает |
|---|---|
| Тимлид | ревьюит proposal.md и дельту спеки в MR (approve/reject), принимает решения в спорах, следит за `openspec/changes/` |
| Разработчик | `/opsx-propose "идея"` → правит proposal по ревью → `/opsx-apply` → MR с кодом |
| AI-агент (OpenCode) | оформляет proposal, пишет код по tasks.md, вливает дельту спеки в `/opsx-archive`. Всё общение в чат агенту |

Правило: **MR с кодом, меняющим поведение сервиса, без Change ID = reject.**

### Полный цикл изменения

```
1. /opsx-propose "что делаем"      агент создаёт change (proposal.md + tasks.md + дельта спеки)
2. MR с change → ревью лидом       код ещё не пишется
3. /opsx-apply                     агент делает tasks.md, отмечает пункты
4. MR с кодом → ревью → merge
5. /opsx-archive                   дельта вливается в specs/, change уходит в архив
```

Спека (`openspec/specs/`) — контракт уже согласованного поведения; меняется последней, через `archive`.

```bash
# БД (PostgreSQL) и сервис

uv run uvicorn src.main:app --reload   # Swagger: http://localhost:8000/docs
```

### Аутентификация и workspace (changes 005/008/009)

```bash
# демо-вход одной кнопкой на UI (role=admin), возвращает JWT; роль — параметр API
curl -X POST localhost:8000/auth/demo-login \
     -H 'content-type: application/json' -d '{"role":"editor"}'

# дальше все /api/v1-ручки требуют заголовок
#   Authorization: Bearer <token>
# и (для не-default workspace) X-Workspace-Id: <id>
#
# роль вычисляется сервером по членству в workspace (таблица memberships);
# заголовки X-User-Role / X-User-Id игнорируются.
```

Фронтенд: dev-сервер с `VITE_API_MOCKS=false` проксирует и `/api`, и `/auth`; на экране
входа — одна кнопка «Войти как администратор» (change 024; выбор ролей и email/пароль из UI убраны,
серверные роли и JWT-ручки сохранены). Токен хранится в localStorage,
401 возвращает на `/login?expired=1`. Роли серверные: reader — только просмотр, editor —
план/факты/приоритеты/импорт, admin — подтверждение отмен и права.

Повторный импорт идемпотентен (bugfix 025): `task_role_requirements` и `team_history` мержатся
по ключам — Imported обновляют часы, manual не затираются; повторный confirm того же job'а — 409.

Читатель — только просмотр; редактор — план/факты/приоритеты; админ — подтверждение отмен, участники, матрица прав (`GET/PATCH /permissions/...`).

### Редактор данных (change 019)

`/data` (фронт): правки загруженного датасета таблицами — задачи, люди, команды, зависимости.
Правка ячейки → `PUT /tasks/{id}` / `PUT /engineers/{id}`; создание/удаление строк — POST/DELETE;
часы «роль → ч» — `PUT /tasks/{id}/role-hours` (замена набора, нулевые отбрасываются). Правки
переводят запись в `source=manual` (защита от затирания повторным импортом) и включают баннер
«данные изменились — постройте план заново» на странице плана. Идентификаторы не редактируются
(409 «task_id менять нельзя»). Висячие зависимости допускаются с пометкой «планировщик проигнорирует».

### AI-советник (change 015)

`GET /plans/{id}/advice?comment=...` — одноразовые советы по сводке состояния плана (риски, KPI, optimization-report, кадровые предложения): 4 типа (`task_move`, `staffing_shift`, `initiative_rescue`, `sprint_priority`), каждый с численным обоснованием и ожидаемым эффектом. **Совет одноразовый: весь контекст прогона — в одном комментарии (`comment`, ≤ 500 симв.); дозапрос/диалог не поддерживаются, комментарий никогда не сохраняется** и не влияет на план/пересчёт. Формат советов идентичен с LLM и без него: без ключа GigaChat советник работает деградационно на детерминированных отчётах ядра. Применение совета — только человеком через существующие ручки (recompute, priority, pin); закреплённые (pin) задачи в советах на перенос не фигурируют.

### Фоновые задачи (change 007)

По умолчанию upload-обработка идёт в процессе API (JOBS_MODE=sync или Redis не поднят).
С Redis/воркером (arq) — фоново:

```bash
docker compose --profile jobs up -d   # поднимает redis + arq-воркер
uv run uvicorn src.main:app --reload  # JOBS_MODE=queue | sync | auto (default: auto)
```

`POST /api/v1/data/upload` возвращает job сразу (status `uploaded`); воркер ведёт
задачу через `uploaded → mapping → questions|ready`, делает повтор (2 попытки),
по таймауту/ошибке — `failed` с причиной. Повторный прогон: `POST /api/v1/ai/normalize/{job_id}`.

### LLM-провайдеры (change 027)

LLM (нормализация колонок при импорте, AI-советник) настраивается через `.env`
(шаблон — `example.env`):

- `POSTCODE_LLM_PROVIDER=gigachat` (default) — Sber GigaChat, ключи `GIGACHAT_CLIENT_ID`/`GIGACHAT_CLIENT_SECRET`;
- `POSTCODE_LLM_PROVIDER=ollama` — локальный Ollama, OpenAI-совместимый endpoint:
  `POSTCODE_OLLAMA_BASE_URL` (default `http://localhost:11434`), `POSTCODE_OLLAMA_MODEL`;
- `POSTCODE_LLM_PROVIDER=none` — LLM отключён.

Без доступного провайдера (нет ключа, сервер не отвечает) оба сценария деградируют
без hard-fail: нормализация — шаблонный маппинг + ручные вопросы, советник —
детерминированные советы (`mode=fallback`).

### Оптимизация плана solver'ом (change 018)

Сайдкар Timefold (Java 21, порт 8080) живёт в compose-профиле `optimizer`:

```bash
docker compose --profile optimizer up -d --build   # сборка через host-сеть (Maven Central)
docker compose --profile optimizer ps              # health: /health
```

Бэк ходит в сайдкар по `POSTCODE_OPTIMIZER_BASE_URL` (default `http://localhost:8080`),
таймаут solve — `POSTCODE_OPTIMIZER_SOLVE_TIMEOUT_SEC` (default 60). Параметры solver:
`OPTIMIZER_SEED` (фиксированный seed → детерминированный черновик),
`OPTIMIZER_TIME_LIMIT_SECONDS`, `OPTIMIZER_STAFFING_GAIN_THRESHOLD` (порог выгоды переноса).

Контракт: `POST /api/v1/plans/optimize {plan_id}` — job выполняется синхронно
(queued → solving → ready|failed), `GET /api/v1/plans/optimize/{job_id}` — статус,
отчёт метрик до/после (те же KPI, что в `/metrics`, change 013: % инициатив, флаги
«в норме»), применённые переносы людей и score-разбивка по ограничениям.
Результат — новая версия плана `strategy=optimization`; откат — селектором версий.

**Деградация**: сайдкар недоступен → оптимизация отрабатывает эвристикой
(жадная метрическая стратегия 012), режим помечен `heuristic`, ошибки нет.
Черновик solver валидируется hard-правилами до записи версии (нарушение → 422,
версия не создаётся). Переносы людей между командами — только admin
(право `plans_optimize_staffing`), у editor — 403. Параллельный запуск в том же
workspace → 409.

**Двухступенчатый конвейер (change 022)**: solver оптимизирует только агрегаты
(части задач × спринты против ёмкости ролей и SP-гейта), а закрепление часов за
конкретными инженерами делает бэк после solve — тем же жадным распределителем,
что и обычный план (лимит 80×ставка, заём из других команд, виртуальный
держатель роли без носителей). Перед отправкой в solver каждая задача режется на
`k = min(6, ⌈часы ÷ 80⌉)` частей (SP и роль-часы пропорционально), поэтому задачи
растягиваются по спринтам и в solver-режиме. Часть, не разместившаяся по
пер-специалистов лимитам, сдвигается на следующие спринты; остаток помечается
«выполнится частично (остаток N ч — за пределами квартала)». 422 остаётся
только на структурные нарушения (зависимости, sole-holder, SP/роль-агрегат) —
пер-специалистов невыполнимость при делимых часах/SP невозможна структурно
(допущение). Solver-версии содержат assignments (task × role × engineer ×
sprint), поэтому личные планы и звёздная карта показывают их так же, как жадные.

**Демо-сценарий**: импорт данных → `POST /plans/generate` → кнопка «Оптимизировать»
на `/plan` (или `curl -X POST /api/v1/plans/optimize -d '{"plan_id": "<id>"}'`) →
новая версия с причинами «оптимизация (режим solver; score …)» →
`GET /plans/optimize/<job_id>` показывает дельту метрик и переносы.

### API (v1)

Импорт данных → план → факты спринта → риски и метрики:

```bash
curl -X POST localhost:8000/api/v1/data/import
curl -X POST localhost:8000/api/v1/plans/generate
curl localhost:8000/api/v1/plans/<id>               # план + причины решений
curl -X POST localhost:8000/api/v1/plans/<id>/sprints/1/facts \
     -H 'content-type: application/json' \
     -d '{"completed_sp": 10, "completed_task_ids": ["ONK-2475"]}'
curl localhost:8000/api/v1/plans/<id>/warnings      # 4 вида рисков
curl localhost:8000/api/v1/plans/<id>/diff          # сдвиги после пересчёта
curl localhost:8000/api/v1/plans/<id>/metrics       # факт/прогноз помечены
curl localhost:8000/api/v1/bus-factor               # расчёт + методика
curl localhost:8000/api/v1/plans/<id>/bus-forecast  # прогноз bus factor по плановой загрузке (change 023)
curl localhost:8000/api/v1/plans/<id>/bus-risk      # задачи плана под угрозой Bus Factor
curl localhost:8000/api/v1/star-map/summary
```

Всего ручек и схем — /docs (Swagger UI). До запуска `data/import` планирование недоступно (400).

Календарь квартала (change 010, решение №12): старт квартала — `max(planned_end) → fallback actual_end → календарный квартал`; `GET /plans/{id}` содержит `quarter_start`, `sprint_dates` (6 × start/end по 2 недели) и `date_forecast {start, end}` у каждой запланированной задачи; интервалы переносятся при пересчёте.

### Правила планирования (допущения, change 003)

- **Приоритет**: поле `priority` задачи (меньше — раньше). Seed при импорте: задачи заказчика (`planned_in_sprint='Да'`) → 10; остальные — 100 + исходный порядок файла. Меняется вручную: `PUT /tasks/{id}/priority`.
- **Статусы**: `Done` — вне планирования; `InProgress` — остаток по часам (`estimated_hh − spent_time`), SP пропорционально; перерасход помечается «просрочена (overdue)»; `ToDo` — полный объём.
- **Сп↔часы**: два независимых гейта — SP против capacity команды (velocity×0.8), часы против лимитов специалистов (80 ч полная ставка, 40 ч при 0.5 ставки). Прямой конверсии SP↔часы нет (допущение).
- **Кросс-командный заём**: роль задачи может закрывать инженер другой команды; суммарная его загрузка во всех обязательствах за спринт ≤ лимита ставки.
- **Роль без носителей** (обычно менеджерские, напр. «Руководитель проекта» — в датасете нет ни одного инженера с такой ролью): планирование учитывает её через **виртуального держателя** с полной ставкой; риск отмечается в причинах задач и на карте.
- **Разбиение задач**: задача может занимать несколько спринтов (SP/часы пропорционально); зависимые задачи стартуют после последнего спринта разбитой задачи. Частичное размещение помечается «выполнится частично (остаток — за пределами квартала)».
- **Отмена**: сервис предлагает отмену задач, не поместившихся в квартал; лид подтверждает (`cancel-request` → `confirm-cancel`); отменённые остаются видимыми с причиной.
- **Модель по людям (change 016)**: каждая роль задачи закрепляется за конкретным **носителем** — назначение `task × role × engineer × sprint` хранится в версии плана (поле assignments); личная очередь инженера реализуется через пин (закрепление задачи за спринтом/носителем: `POST/DELETE /plans/{id}/tasks/{tid}/pin`, конфликт ёмкости — 409; при пересчёте пин учитывается до расстановки остальных). Личный план — `GET /plans/{id}/people/{engineer_id}`. Лимиты соблюдаются суммарно по всем командам инженера (parttime в двух командах — 40+40).
- **Метрики**: % квартала — по **инициативам** (parent_id): знаменатель — инициативы с ≥1 задачей в первоначальном плане; завершённая инициатива = все её запланированные задачи done_actual. Прогноз помечается до конца квартала.

### Соглашение по коммитам

Conventional Commits: `тип(scope): описание` (кратко, по-русски, строчными). Scope — имя capability спеки или модуль (`dataset`, `data`, `ui`), необязателен, но приветствуется.

| Тип | Когда |
|---|---|
| `feat` | новая функциональность сервиса |
| `fix` | исправление бага |
| `spec` | изменение спек openspec (proposal/архив) |
| `data` | правки источника данных xlsx / скрипта разборки / перегенерация dataset |
| `docs` | только документация |
| `refactor`, `test`, `chore`, `ci`, `build`, `perf`, `revert` | стандартно |

Примеры: `data: нормализация дат в ISO`, `feat(planning): распределение по спринтам`, `spec: уточнение объяснения переноса задач`.

### Хуки (контроль локально, CI в проекте отключён)

Хуки лежат в `.githooks/`; включаются один раз после клонирования:

```bash
git config core.hooksPath .githooks
```

- `commit-msg` — отклоняет коммиты не по соглашению
- `pre-commit` — `openspec validate --all` + синтаксис `scripts/`
- `pre-push` — полная проверка перед пушем: validate спеков + воспроизводимость `dataset/` из xlsx

`.gitlab-ci.yml` оставлен как заготовка для будущего включения CI (валидатор спеков и воспроизводимость данных на MR).
